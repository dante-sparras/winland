# The config is the line-based syntax or Lua, and Lua becomes lines

Winland reads `winland.lua` when it exists and `winland.conf` otherwise, from `%APPDATA%\winland`. `--config` takes either, by its extension.

The pinned release, a Hyprland v0.56 commit (ADR 0008), reads only Lua (`hl.config`, `hl.bind`, `hl.monitor`, `hl.window_rule`), and its manual shows only that form. Most existing Hyprland configs and dotfiles use the line-based syntax (`bind = SUPER, Q, killactive`), so Winland keeps reading it and reads Lua as well.

A Lua config runs each time the config loads, and each `hl` call becomes the line the line-based syntax has for it: `hl.config({ general = { gaps_in = 5 } })` is `general:gaps_in = 5`. The parser and the core then read those lines as they read `winland.conf`, so both forms honor the same options and give the same warnings, which point at the Lua line that made them. Lua names an option with `.` for `:` and `_` for `-`, so a `col` part joins the next with a `.` again and the three names with a `-` get it back.

The runtime is Lua 5.4 from KeraLua, the C Lua that NLua ships as a native library. The pinned release uses Lua 5.5, which no .NET package offers; a config rarely uses what 5.5 adds, chiefly the `global` keyword. A Lua written in C# would be Lua 5.2, and building 5.5 from C would put a C compiler in the build and the release.

Winland runs elevated (ADR 0004) and a config is usually a file the user can write, so the Lua runs without what reaches the system: no `io`, no `debug`, no `os` beyond the clock, date and environment, no C modules and no binary chunks. `require` reads a module by name from the config's folder, and by path, wildcards included, as the pinned release does, through the same reader as the line-based config, which also lists what a wildcard matches, so a required file counts toward the config's trust (ADR 0007) and a change to it reloads the config. Each run of Lua has the pinned release's limit of processor time, 1.5 seconds for the config as it loads, and is stopped when it runs longer. Commands run through `hl.exec_cmd`, which Winland launches de-elevated as it does `exec`.

The manual's `hyprland.start` and `hyprland.shutdown` events are `winland.start` and `winland.shutdown`, as `hyprland.conf` is `winland.conf` (ADR 0002). Their handlers run while the config loads, so an `hl.exec_cmd` in them is `exec-once` and `exec-shutdown`. Handlers for the other events run on the Lua's thread when the core notices their event: the core only queues the events of each outcome there, since it notices them inside its lock, so a handler runs after the change that raised its event, and an event its own dispatch raises runs after it rather than inside it. The objects a handler gets, and those the `hl.get_*` queries return, name a window, workspace or monitor and read its fields from the core's query replies when they are read, as the pinned release's objects read live state.

The config's Lua keeps running after it loads, on a thread of its own, so it never runs inside the core's handling of an input: a bind that calls a Lua function names Winland's own `luafunction` dispatcher with the function's number, and the function, a timer, an event handler and a `winlandctl eval` are queued there and run in turn. What they dispatch goes through the commands `winlandctl` sends, so it is applied as a pipe command is. A reload replaces the Lua with the new config's.

A custom layout, `hl.layout.register`, follows the same rule, though the pinned release calls its `recalculate` inside the change that needs it. Registering one is the line `lualayout = lua:NAME`, so the core knows from the config alone which names select it, and a reload that drops the registration returns its Workspaces to dwindle. Its Layout is a core Layout like the others: it keeps the tiled Clients in order and asks an `ILayoutScripts`, which the Lua runtime implements, for their boxes whenever the order or the tiling area changes. The core holds its lock when it asks, and the layout's Lua may read windows through the pipe, so the request only queues a snapshot of the area and the targets: the Lua thread runs `recalculate` on the latest snapshot of each Layout, with the pinned release's 50 milliseconds, and sends the boxes back as the pipe command `layoutplace`, which the core applies when no newer request has replaced the one it answers. A layout message is queued the same way, and never dropped. Until the answer comes the Clients keep the boxes they had, or take an even grid when one has none, which is the pinned release's fallback for a layout that fails. Running the Lua inside the core's call instead would deadlock when it reads a window or when the Lua thread is waiting on the core, and waiting for the Lua thread with a timeout would stall every input behind a busy config.

The `hl` calls are built in phases. A call not built yet warns once that it is not honored yet and returns nothing, and the config runs on. A feature that exists only in the Lua form, and needs Lua to run while Winland runs, waits on those phases and is a Gap until then. The source under `docs/agents/hyprland/src/` decides which options exist and what their defaults are.
