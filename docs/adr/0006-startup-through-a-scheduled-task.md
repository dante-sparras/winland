# Winland installs itself and starts at logon

`winland install` asks for one UAC approval, stops a running Winland, copies `winland` into `C:\Program Files\Winland`, and registers a scheduled task that starts that copy through `winland-launcher.exe` at logon with the highest privileges. The task never starts the folder install was run from. The install folder is added to the machine `PATH`, a Start menu shortcut carries Winland's AppUserModelID, and Settings › Apps uninstalls by running `winland uninstall`. Winland starts through the task when one exists, and from then on starts at logon without a prompt. If another administrator approved UAC, install skips the immediate start so Winland never runs as the wrong account.

The launcher is NativeAOT. Before starting the managed daemon it removes all `CORECLR_`, `COMPlus_`, `DOTNET_`, `COR_` and `COREHOST_` variables. This covers profiler libraries, alternate JITs, startup hooks, dependency and runtime paths, and trace-file paths. The daemon also disables startup-hook support at build time. Clearing variables inside the daemon would be too late, because the runtime can load code before `Main`. The [runtime environment variables](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-environment-variables) are user-controlled even when Task Scheduler starts an elevated process. A small native launcher keeps the existing daemon build and its interop, without converting the whole daemon to NativeAOT. Updating an existing install also moves its task action to the launcher.

`winland install --user` asks for no approval. It copies Winland into `%LOCALAPPDATA%\Programs\Winland`, adds that folder to the user `PATH`, and starts it at logon from the user's Run key, unelevated and without a prompt. The Start menu shortcut and the Settings › Apps entry are per-user, and a Winland started from that copy never relaunches itself through UAC. `winland uninstall` stops Winland and removes the task or the Run key entry, the shortcut, the Settings › Apps entry, the `PATH` entry and the installed files, and keeps the config. `--purge` also removes the config, the logs and the state.

Machine installation and removal run elevated. After approval returns successfully, the original unelevated process removes a per-user install and, for uninstall, restores the invoking user's Windows settings and performs any purge. The elevated process never recursively deletes a user profile folder or edits the approving administrator's user install. Run these commands from a normal terminal so those user steps can finish.

The Run key and Startup folder can't start an elevated program silently, and a Windows service runs in session 0, where it can't touch the user's windows. The elevated task must start a file only administrators can change, or any program the user runs could replace what it starts, so the install puts Winland under Program Files itself instead of asking the user to copy it there.
