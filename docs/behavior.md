# Behavior

How Winland behaves. Terms are defined in [CONTEXT.md](../CONTEXT.md). An unknown keyword warns and is skipped. A value an Option cannot read warns `Invalid value '<value>' for <option>.` and the line is skipped, so the earlier value stays. A number outside an Option's range is clamped to it.

## Config files

Winland reads `%USERPROFILE%\.winland\winland.conf`, or the `.conf` file `--config` names. On first start, when that file does not exist and no `--config` was given, Winland writes a commented default there and then loads it. A later start leaves an existing file as the user left it. A `--config` path that is missing is an error, and Winland does not write the default in its place. A config, log or state left in `%APPDATA%\winland` or `%LOCALAPPDATA%\Winland` stays there. Winland does not read it and does not move it.

A line that ends with a backslash is joined to the next line, so a value that ends with a backslash, such as `$dir = C:\tools\`, takes in the line after it. Write such a path without the last backslash, or with `/`. A backslash at the end of a comment is part of the comment and joins nothing: `# path C:\dir\` leaves the next line alone, and a comment after a value that ends with a backslash warns `A backslash at the end of a comment does not join the next line.` An escaped `##` is not a comment, so a backslash after it still joins.

`source` reads another file in place of the line. A relative path is read from the config's folder, and a glob reads each file it matches in name order. A file is named the same however its path is spelled: paths are compared without case, after a relative path is joined to the config's folder. A `source` that names a file already being read, the config itself included, warns `Source '<path>' includes itself.` and is skipped. A glob passes over such a file without a warning, so `source = ./*.conf` in the config's own folder does not read the config a second time.

## Layout

`general:layout` is honored for `dwindle` and `scrolling`, written in any case. Any other value warns with its line number and is skipped.

`general:gaps_in` defaults to 4 and `general:gaps_out` to 8.

A tiled Client's minimum size moves a dwindle split where the minimums fit, and the neighbour takes what remains. Each side keeps at least the share the smallest split ratio leaves it. Where they do not fit, the side that needs more takes all of that but the other side's share, so no tile leaves the Monitor. A window cannot be smaller than its minimum, so a window below it grows around the middle of its tile and moves to stay inside the work area, over its neighbours. A minimum larger than the work area starts at its top left corner.

A `min_size` or `max_size` window rule holds a Client only while it floats, and a tiled Client keeps the window's own minimum, which Windows enforces. A maximum that cannot fill the tile floats the Client, the rule's or the window's own. When the window changes its own limits, a rule's minimum or maximum still wins over them.

A window whose maximum size cannot fill the tile it would get floats instead of tiling. This also holds when the Client is toggled back to tiled or dropped by a drag. A window that opens this way floats at the size of the tile it would have taken, kept inside its limits, in the middle of the work area. In dwindle that tile is half the tile it would split, or the whole Monitor on an empty Workspace.

`layout:single_window_aspect_ratio`, such as `4 3`, pads the only tiled Client of a Workspace to that width to height in every Layout. The padding is the part of the work area outside that ratio, split evenly between two sides, and it is taken off the Client's tile. `0 0`, the default, turns it off. The tile is left alone when half the padding is not more than a tenth of the work area's height or width. A maximized or fullscreen Client fills its area as before.

## Decoration

`decoration:rounding` is the corner radius in logical pixels and defaults to 8, which draws DWM's round corners. 0 draws square corners. A negative value warns and is skipped. The radius drawn is `rounding` multiplied by the scale of the Client's Monitor. A radius of 8 or 4 uses DWM's round or small round corner preference, which DWM scales with the window's DPI. Any other radius is cut from the window as a window region inside the visible frame, a circle at each corner, and is cut again when the window changes size. A radius larger than half the shorter side is cut to that half. A Client in fullscreen mode 2 and a Client on a Workspace with `rounding:0` draw square corners. A window that already has a region of its own keeps it, and its corners are not cut.

`decoration:blur:enabled` defaults to true and gives every Client DWM's acrylic backdrop (`DWMSBT_TRANSIENTWINDOW`). False gives it no backdrop (`DWMSBT_NONE`). A window or a Windows build that refuses the backdrop is left as it is. Acrylic stays according to that switch, including on a translucent Client. A translucent Client shows what is behind it, with no drawn blur. `no_blur`, from a window rule or `setprop`, turns that acrylic off for that Client. Every other `decoration:blur:*` keyword warns and is skipped. DWM's own shadow is left as Windows draws it.

The backdrop and the region are put back when the window stops being a Client and on a clean exit. After a crash the next start removes each region Winland had cut, so it is not taken as the window's own region. The backdrop goes back to the type the window had, or to the system choice when that cannot be read.

Winland draws each Client's border itself, outside the window's frame: `general:border_size` pixels wide, default 2 (or the window's own `border_size`), in `general:col.active_border` on the focused Client and `general:col.inactive_border` on the others. When `general:col.active_border` is unset, that border is the Windows accent color and changes when Windows changes the accent. A color set in the config overrides the accent. `general:col.inactive_border` defaults to `0xff404040`. A border color is one color, written as `rgba()`, `rgb()`, or `0xAARRGGBB`. A gradient or an angle warns and is skipped, and the previous color stays. A change of border color blends in the OkLab space. The border's inner corners follow the window's rounding and its outer corners are rounded to match, less a little for a corner flatter than a circle; a square window has a square border. The border takes the window's opacity. A fullscreen Client, a minimized or hidden one, and one with `decorate 0` have no border, and `border_size 0` draws none. DWM's own one-pixel border is turned off while Winland runs. The border is four click-through windows kept just above the Client in the z-order, so a window raised over the Client covers its border too, and they follow the window as it moves, animates or is dragged. A Group's border, `group:col.border_*`, is one color the same way.

`decoration:active_opacity`, `decoration:inactive_opacity` and `decoration:fullscreen_opacity` are fractions from 0 to 1 and default to 1. A value outside that range is clamped. A Client in fullscreen mode 2 uses `fullscreen_opacity`. A maximized Client uses the active or inactive fraction, and so does every other Client.

An `opacity` window rule takes one or two fractions. One fraction is used for the active, inactive and fullscreen Client alike. Two set the active and the inactive fractions, and leave fullscreen at 1. Each multiplies the configured fraction. Any other token, or a third fraction, warns and the rule is skipped. The last matching `opacity` rule wins. `opaque` forces the fraction to 1, and a trailing `0` turns that off. The last matching `opaque` rule wins.

Windows disables a window while a modal dialog it owns is open, so a disabled Client that owns another Client is shadowed by a modal, and that owned Client is modal. A shadowed Client takes no focus, as with `no_focus`: a click or `focuswindow` leaves focus where it is, and the pointer passes over it. A disabled Client that owns no Client is not shadowed. `decoration:dim_inactive`, `decoration:dim_strength`, `decoration:dim_modal`, `decoration:dim_special` and `decoration:dim_around` warn and are skipped.

An alpha below 255 adds `WS_EX_LAYERED` and sets the window's alpha. The window's previous extended style is restored when it stops being a Client, on a clean exit, and after a crash for every window this program layered. A window that was already layered is left alone. A window that refuses the layered style is skipped.

## Shell windows

The taskbar, the Start menu, Search and the other flyouts the shell opens from the taskbar are left unmanaged, so opening Start does not split the screen. Winland knows the taskbars by their window classes `Shell_TrayWnd` and `Shell_SecondaryTrayWnd`, and the flyouts by their processes `StartMenuExperienceHost.exe`, `SearchHost.exe`, `SearchApp.exe`, `ShellExperienceHost.exe` and `ShellHost.exe`. A window rule that forces a window to be adopted, such as `float`, `tile` or `workspace` on `class:.*`, still adopts a flyout it matches.

By default the taskbar stays as Windows has it, and Clients tile in the work area, so the strip it reserved stays clear. `general:hide_taskbar` defaults to false. True hides the taskbars and sets them to auto-hide while Winland runs, so the work area takes in that strip. They are hidden again when the shell shows or recreates them. A clean exit shows them with the state they had before. A crash leaves a marker of that state in `%USERPROFILE%\.winland`, and the next start puts it back: with the option on, the taskbars are hidden again, and with it off they stay as Windows had them. Changing the option, on reload or with `keyword`, applies at once and the Clients are laid out again in the work area that leaves.

A layered window that input passes through, such as a screen overlay an application draws over the desktop, is left unmanaged too: it cannot be clicked or focused, and Winland draws such surfaces as layers it never tiles. A window rule that forces adoption still adopts it.

## Window rule matches

A `windowrule` is an effect, a comma, and the fields it matches, such as `windowrule = float, class:^(kitty)$, title:Settings`. Its `class`, `initial_class`, `title`, `initial_title`, `exe` and `aumid` patterns are regular expressions that must match the whole field, so `title:Notes` does not match a window titled `Release Notes`. `initial_class` matches the class the window had when it appeared, including an empty one, and `class` matches the class it has now. `initial_title` matches the title the window had when it appeared, and `title` matches the title it has now. A rule matches what a window is, not what state it is in: any other field warns `Unsupported window rule match '<field>'.` and the rule is skipped, and a rule with no field warns `Malformed window rule.` When the class or the title changes, a rule that matches on `class` or `title` is read again, and its opacity, properties and focus effects follow. Effects that apply only as the window appears, such as `float` and `workspace`, stay as they were. A pattern that starts with `negative:` matches when the rest of the pattern does not, so `class:negative:kitty` matches every class but `kitty`. A pattern that is not a valid regular expression warns with its line number and the rule is skipped.

## Window properties

`getprop WINDOW PROP` answers a window property, and `setprop WINDOW PROP VALUE` sets it. The properties are `animation`, `min_size`, `max_size`, `opacity`, `opacity_inactive`, `opaque`, `active_border_color`, `inactive_border_color`, `border_size`, `rounding`, `decorate`, `focus_on_activate`, `no_anim`, `no_blur` and `no_focus`. `j/getprop` answers a one-member JSON object, such as `{"opacity": 0.5}`. A property is what `setprop` set, else what a window rule gives, else the config's value. `getprop` with too few arguments answers `not enough args`, for no window `window not found`, and for an unknown property `prop not found`.

A bool takes `toggle`, which flips what is set, or false when nothing is, and otherwise is true for `1` or text starting with `true`, `yes` or `on`. A number takes `relative N` to add to its value. `unset` drops what `setprop` set. `min_size` and `max_size` take two expressions over the window's size and place, as a `size` rule does, and the window is held to them at once. `opacity` and `opacity_inactive` take a fraction. A border color takes one color. A gradient, an angle, or more than one token changes nothing. A value that does not parse changes nothing.

The opacities and `opaque` change the window's alpha. `decorate` with 0 takes away the border and a Group's tab bar. `no_focus` keeps the window from taking focus. `focus_on_activate` wins over `misc:focus_on_activate` for that window. `min_size` and `max_size` hold its size. The border colors, `border_size` and `rounding` change how it is drawn. `no_blur` turns that Client's acrylic backdrop off, `no_anim` moves, fades and recolors the window at once, and `animation` sets the style the window opens and closes with (see [Animations](#animations)).

A window rule sets a property with the effect of the same name: `border_size`, `rounding`, `border_color`, `animation`, and the bool properties such as `no_blur` or `decorate 0`. A bool effect with no value is true. `border_color` takes one color for the active border, or two colors for the active and the inactive borders. An angle, or any further color, warns and the rule is skipped. A value that does not parse warns and the rule is skipped. A window's own `border_size`, from a rule or `setprop`, replaces the configured border around its tile, multiplied by its Monitor's scale like the configured one.

## Exec rule blocks

A rule block on `exec`, `exec-once`, `exec-shutdown`, or the `exec` dispatcher applies to the first window mapped by that process or a child of it. Every effect a window rule honors is honored there too, including `move`, `size`, `center`, `monitor` and `no_close_for`. Any other effect warns and is skipped. The command still launches. An unclosed rule block warns and does not launch. A known effect with a bad argument warns and does not launch.

## Launching

`exec`, `exec-once` and `exec-shutdown` run the command through `cmd.exe /d /s /c "<command>"`, so cmd syntax such as `&&` and redirection works and every quote in the command is kept as written.

A console program started through `exec` shares cmd's console, which has no window, the way a program started by `sh -c` has no terminal, so a background tool stays out of sight and its redirections and pipes work. To see a console program, start it inside a terminal, for example `exec = wt pwsh`.

Every program Winland starts runs as the normal user. An elevated Winland drops its administrator rights for the launch, so `exec`, `exec-once`, `exec-shutdown`, a bind's `exec`, and a command on the pipe all start the program de-elevated. A program that needs administrator rights asks for them itself.

A window that opens while Winland runs opens on the focused Monitor, wherever its program put it, so a Windows Terminal window opens on the Monitor with the focus and not where Terminal's last window was. A window with an owner that is a Client, such as a dialog, opens on its owner's Monitor. A window that was already open when Winland started stays on the Monitor it is on. A window rule's `monitor` or `workspace`, and the Workspace below, win over this.

A program `exec` or a config `exec` line starts opens its window on the Workspace it was started on, without switching to it. That is the special workspace the focused Monitor shows, or its Workspace. `exec-once` and `exec-shutdown` start programs without it. Every process the program starts holds the same Workspace. The first window that opens uses it up, and it lapses after 10 seconds. A window rule's `workspace` wins over it, and a window that comes back after a restart keeps its own Workspace.

## Window placement

A new floating Client opens at the size it asked for, centered in the work area of its Monitor. One that has an owner, the window Windows names as its owner, such as an application's dialog, opens over the middle of that owner when the owner is a Client. A window that reports no size opens at 640 by 400. A tiled Client is placed by its Layout. `togglefloating` floats a tiled Client around the center of its tile, at the size it last had while floating, or at the size it asked for when it has not floated yet, in every Layout.

A floating Client that changes its own size within 2 seconds of opening is put back at the rectangle Winland opened it at, once. Electron applications restore their saved bounds just after the window is shown, which would undo the centering and the `move`, `size` and `center` rules. A move that keeps the size is left alone, and a later resize is the application's or the user's. A placement by `movewindowpixel`, `resizewindowpixel` or `centerwindow` ends that wait.

A Client that opens floating is kept on screen, also one a `move` rule places. So is a floating Client that starts floating, or that a Dispatcher moves or resizes. Both are measured against the work area. The border around the frame counts for the second and not for the first, because Winland applies it to a new Client before the border is known. The Client is moved, without resizing it, to lie wholly inside, so a Client larger than the area lines up with its right and bottom edges.

A Client that comes back after a restart keeps the rectangle it had, whether it floated, its pin and its fullscreen modes, as the recovery file recorded them, before the window rules. Each Monitor shows the Workspace it showed, and a dwindle Workspace's tiles are arranged as they were: every split cuts its box in two, so the rectangles the tiles had give each split's direction and ratio again. A Workspace with a tile that did not come back, or whose rectangles do not make such a tree, keeps the order the tiles came back in. A recovery file written before these were recorded leaves them to the rules.

A Client whose application hides it, without minimizing it, stops being a Client, as an unmapped window does in Winland, and it is adopted again when the application shows it. The windows Winland hides itself, for a Workspace it does not show, stay Clients.

`size` and `move` take two expressions, x then y, split at the first whitespace, so an expression cannot contain a space. An expression is numbers, `+ - * / ^`, parentheses, a unary minus, the constants `_pi` and `_e`, the one-argument functions `abs`, `sqrt`, `sign`, `rint`, `exp`, `ln`, `log`, `log2`, `log10`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `sinh`, `cosh` and `tanh`, and the variables `monitor_w`, `monitor_h`, `window_x`, `window_y`, `window_w`, `window_h`, `cursor_x` and `cursor_y`. Positions are local to the Monitor the Client opens on. Numbers are physical pixels, like `min_size`. A `min_size` or `max_size` rule also takes two expressions, read when the window opens. A size below 1 leaves that limit unset. A rule that is not two expressions, or uses a name that is not listed, warns with its line number and is skipped. So does an expression nested more than 256 levels deep in parentheses, signs, exponents and functions. A `%` is not part of an expression, so `50%` warns. A value that cannot be computed, such as a division by zero, leaves the Client where it would open without the rule.

`size` sets a floating Client's size, then the minimum and maximum size clamp it. Every Layout keeps a floating Client inside its minimum and maximum, also when the window changes them. `window_w` and `window_h` are the size the window asked for. A tiled Client keeps that size as its pseudo size. `pseudo` toggles it in every tiled Layout: the Client stays in its tile and is shown centered at that size, or scaled down to fit the tile while keeping its aspect when the size is larger. With no size of its own it is 1280 by 720. Toggling again fills the tile. `move` places a floating Client's top left corner, and `window_w` and `window_h` there are the size after `size`. `center` centers a floating Client in the work area, which is also where it opens without a rule. `move` and `center` replace each other: the last matching one wins. A trailing `0` turns `center` off. Neither moves a tiled Client.

`monitor` opens the window on that Monitor, before a `workspace` rule picks the Workspace. It takes the same selectors as `focusmonitor`. Without a trailing `silent` that Monitor is focused. `unset` and a Monitor that does not exist keep the Monitor the window opened on.

`movewindowpixel` and `resizewindowpixel` take two numbers, a comma and a window selector. The numbers are added to the window's position or size. After `exact` they replace it. A trailing `%` is a percentage of the position or size, or of the focused Monitor after `exact`. Text that is not two numbers leaves the window as it is. `movewindowpixel` moves a floating Client and leaves a tiled one. `resizewindowpixel` resizes through the Layout, so a floating Client grows from its center and a tiled Client changes its split. A size below one pixel answers `error: Invalid size`, and a fullscreen or maximized Client answers `error: Window is fullscreen`. A selector that matches nothing answers `error: moveWindow: no window` or `error: resizeWindow: no window`.

`movewindow` with a direction moves a floating Client against that edge of the work area, with its border inside the area.

`centerwindow` centers the active floating Client in its Monitor's work area. A tiled or fullscreen Client answers `error: No floating window found`. A window selector after a comma acts on that window in place of the active one, without focusing it. A selector that matches nothing answers `error: window not found`.

A Workspace's floating Clients stay above its tiled ones, whichever is focused. Windows brings a window it focuses to the top, so when a tiled Client becomes the active window, the floating Clients shown are put back above it in their order. A floating Client that is focused comes to the top of the floating ones. One a fullscreen Client keeps under itself stays there. `bringactivetotop` raises the active Client above every window that is not topmost. `alterzorder` takes `top` or `bottom`, a comma and a window selector. After it, and after `bringactivetotop`, the pointer is handled as if it moved where it is, so with `input:follow_mouse` the window now under the pointer takes the focus. The window under the pointer is the topmost floating one there, in the stacking order, before any tile. Without a match it uses the active Client when that Client floats, and otherwise does nothing. Any other position answers `error: Bad z-order position: <position>`. The adapter changes the z-order with `SetWindowPos` and `HWND_TOP` or `HWND_BOTTOM`, without moving, sizing or activating the window. `clients`, `activewindow`, `workspaces`, `activeworkspace` and `monitors` answer in Winland's text form without `j/` and in its JSON form with it, the same fields in both: a block per entry with its fields indented a tab, an address without its `0x`, and `yes`, `no`, `true`, `false`, `1` or `0` as Winland writes each. With no window `clients` answers `no open windows` and `activewindow` `Invalid`. `clients` lists the Clients from the bottom of the stacking order to the top: a new Client opens on top, and `bringactivetotop` and `alterzorder` move one. A window Windows raises by itself is not followed.

`movecursortocorner` warps the cursor to a corner of the active Client: 0 bottom left, 1 bottom right, 2 top right, 3 top left. Any other number answers `error: Corner must be 0 - 3`, and text that is not a number answers `error: moveCursorToCorner, arg has to be a number`. A window selector after a comma, as in `movecursortocorner 2,class:kitty`, warps to that window instead, without focusing it.

`togglegroup`, `changegroupactive`, `fullscreen` and `moveintogroup` take a window selector after a comma and act on that window in place of the active one, without focusing it. A selector that matches nothing answers `error: window not found`.

## Border resize

`general:resize_on_border` defaults to false. The grab ring is looked for on the Workspace shown on the Monitor under the pointer, its special workspace first when one is open there, the floating windows from the top of the stacking order down. While a maximized or fullscreen Client covers that Workspace only a floating window allowed over it has a ring. When it is on, a press in the grab ring around a Client resizes that Client. The ring is `general:border_size` plus 15 logical pixels outside the Client. A press inside the Client is left to the Client. Floating Clients are tested first, topmost first, so a floating Client's ring over a tile still resizes the floating Client. A rounded corner is not a grab: the ring is measured from the square frame. While a special workspace is open on the focused Monitor, only its Clients have a ring. A maximized or fullscreen Client has no ring, and neither do the Clients behind it.

While border resize is on, the outcome names the cursor for the edge under the pointer: `top_side`, `bottom_side`, `left_side`, `right_side`, `top_left_corner`, `top_right_corner`, `bottom_left_corner`, or `bottom_right_corner`. The corner zone is the border plus 10 pixels. While a drag holds a window the outcome names `grabbing` for a move and the grabbed corner for a resize. Windows lets a program set the pointer only over its own windows, so Winland shows these by replacing every system cursor with the matching Windows one, the four-headed arrow for `grabbing` and the two-headed arrows for the sides and corners, and loads the user's own cursors again when the outcome names none, at exit, and on the next start after a run that did not exit cleanly.

## Mouse drag

A mouse button that runs a bind is swallowed, so the window under the pointer does not get it. A wheel notch that runs a bind is swallowed too.

A drag that picks up a fullscreen or maximized Client ends that mode first. A floating Client is then put under the pointer by its middle.

`bindm` binds a mouse button to `movewindow` or `resizewindow`. A press takes the Client under the pointer, or the one whose border is under it, focuses it, and drags it until that button is released. When Windows drops the mouse hook during a drag the release cannot be seen, so the drag ends where the pointer is once the hook is put back. The `mouse` dispatcher in an ordinary bind, as in `bind = SUPER, mouse:272, mouse, movewindow`, is the same action. It takes only `movewindow` or `resizewindow`. Bound to a key, as in `bind = SUPER, Z, mouse, movewindow`, it drags the window under the pointer while the key is held: the key's repeats are swallowed and its release drops the window. A press with no Client under the pointer does not drag, and when the drag is all its bind does the press goes on to whatever is under the pointer, the desktop say, and so does its release. The mouse hook asks the core without waiting, so a press made while the core is busy is kept. A Client that closes while it is dragged or resized, by a bind, its border or the system, ends that drag.

While a `movewindow` drag moves a Client, as soon as the Client's middle lies on a Monitor whose shown Workspace is not the Client's, the Client joins that Workspace, or the special workspace when one is open there, and `movewindow` is told each time. The drag continues on that Workspace. A tile the drag lifted stays floating until release, then drops into that Workspace's Layout at the pointer, and a floating Client keeps its rectangle. A floating `resizewindow` joins the same way when its middle crosses. A tiled resize does not. A release with no move, whose middle is already on another Monitor, still joins the Workspace that Monitor shows.

`binds:drag_threshold` defaults to 0. Above 0, the Client is not picked up until the pointer has moved farther than that many pixels from the press. The drag then starts from that point, so the Client does not jump.

`movewindow` moves a floating Client with the pointer. A tiled Client is lifted out of the Layout and floats at its tiled size, centered on the pointer. On release it drops back into the Layout at the pointer. A Client that closes while it is dragged ends the drag, and nothing is dropped on release. The same happens when a dispatcher moves it to another Workspace during the drag. In dwindle it splits the tile under the pointer, or the nearest tile, and goes on the half the pointer is over.

A Client that the system moves by its title bar is dragged the same way. A tiled Client is lifted out of its Layout when the move starts, and the other tiles close the gap. When the move ends it is dropped back in where the pointer is, by the same rule as a `movewindow` drop in that Layout. A maximized or fullscreen Client leaves that mode when its title is taken. A floating Client stays where it is dropped, and one the system resizes keeps the size it is left at. `clients` and `activewindow` report that frame, and for a resize they follow the border while it is held. A drag that starts on a sizing border is a resize: a tiled Client changes its split while the border is held, as `resizewindow` does. The window is asked what is under the pointer when the drag starts. A window that answers with a border or with its title settles it. A window that answers with nothing or with its client area, as a terminal does when it snaps its size to its character grid as the sizing begins and so pulls its border out from under the pointer, is told by its first change: a change in its size is a resize, and a change in its position alone is a move. Its neighbours follow the border, the system sizes the Client itself, and the Client takes its Layout rectangle when the border is let go. Where the Layout stops the border short of the pointer, as against a neighbour at its minimum size, the Client is held at its Layout rectangle while the pointer is past it, so it does not cover its neighbours. A maximized or fullscreen Client goes back to covering the area when the border is let go. In dwindle, a split keeps its direction while a resize changes its shape only with `dwindle:preserve_split` on, which the starter config sets. 

`resizewindow` resizes a floating Client from the grabbed corner. That is the corner nearest the pointer. A tiled Client changes its split ratios instead. `resizewindow 1` keeps a floating Client's aspect ratio: the side that grew more sets the size and the other follows. `resizewindow 2` does not keep it. With no argument the `keep_aspect_ratio` window rule or property decides.

A mouse resize of a tile moves the edges on the grabbed corner's side and keeps the opposite edges in place, so the tiles on the far side do not change. A tile against a monitor edge moves its other edge. `resizeactive` has no corner and moves the nearest split on each axis. `resizeactive exact` names the window's size, so a tile grows by the difference from the window it shows, not from the tile with its gaps and border.

In the scrolling Layout `movefocus`, and the dispatchers that look for a neighbour in a direction, stop at the ends of the strip and of a column instead of wrapping around, so `movefocus` goes on to the neighbouring Monitor. Only `layoutmsg focus` wraps. `movefocus` and `layoutmsg focus` scroll the strip to the Client they focus. The strip follows focus that a dispatcher, a click or a Group change gives. Focus the pointer gives follows only when at least 0.4 of the Client shows.

In the scrolling Layout a resize keeps the camera where it is. A column's far edge does not move past the viewport, and grabbing its near edge moves the camera with it so the far edge stays put. A row trades space with the row on the grabbed edge. `resizeactive` has no corner, so a row trades with the row before it, and the first row with the row after it.

## Cursor and input

These cursor keys are honored: `no_warps`, `inactive_timeout` and `hide_on_key_press`. Any other `cursor` key warns and is skipped.

`no_warps` defaults to false. True stops Winland moving the cursor when focus or the Workspace changes.

`inactive_timeout` is seconds from 0 to 20, default 0. Above 0 the cursor hides once it has been still for longer than that. `hide_on_key_press` hides it on a key press until the mouse moves. A cursor hidden for any reason stays hidden when Winland moves it, as `movefocus` does. A touch screen that moves the pointer or touches down hides it until the mouse moves, and a pen does not. Windows tells them apart by the signature it puts on the mouse input it makes from touch and pens. The cursor is hidden through the system magnifier, so it is hidden over every program, and it comes back when Winland exits, even when Winland is killed.

`input:follow_mouse` is the one input key honored. A key that would write a Windows setting warns and is skipped. That includes mouse speed and acceleration, wheel lines, key repeat, Num Lock, `left_handed`, every `input:touchpad:`, `input:tablet:` and `input:touchdevice:` key, and the keyboard layout keys `kb_layout`, `kb_variant`, `kb_options`, `kb_model`, `kb_rules` and `kb_file`. Winland does not change those Windows settings, and it does not load or switch a keyboard layout. `switchxkblayout` and `devices` are not commands. Binds read keys in the layout the foreground window is using.

Winland turns the turns of a high resolution wheel, which Windows sends in parts of a notch, into whole notches. It takes a mouse wheel turn that is not a whole multiple of 120. The touchpad is never taken. The first turn of a run, the same axis and direction with under half a second between turns, sends a notch at once, and after that one notch goes out for every 120 units the turns add up to. A wheel that sends whole notches is untouched.

A wheel turn over the ring around a window, not inside it, is the border and, with `resize_on_border`, the grab area around it (`border_size` plus 15 logical pixels), where Windows would send the turn to whatever lies under the cursor, usually nothing. The lookup never waits for the core: when the core is busy the turn is left to Windows. Winland posts a wheel message to the window at the nearest point inside its tile without moving the cursor. A turn that runs a bind goes to the bind first. A turn over no window, such as a gap or the desktop, is left alone.

A `device[name]` line, and every field inside a `device[name]` block, warns `Unsupported keyword` and is not applied. Nothing is stored for that device.

`input:follow_mouse` defaults to 1. 0 leaves keyboard focus where it is when the pointer moves. 1 moves it to the Client under the pointer when the pointer moves. A move after the pointer has been still for half a second does not move it yet. 2 and 3 do not move keyboard focus when the pointer moves. 3 also keeps the focused Client when a click would take it. The names `disabled`, `follow`, `detached`, and `separate` are 0, 1, 2, and 3.

On a Workspace with a maximized or fullscreen Client, that Client owns the pointer. The tiles behind it take no focus when the pointer passes over them. A maximized Client takes the focus only where it is drawn, and a fullscreen one wherever the pointer is.

In modes 0 and 2, moving between a tiled Client and a floating Client moves keyboard focus. Moving between two Clients of the same kind does not. Mode 3 does not do so.

Closing a Client focuses the nearest remaining tiled Client, or the nearest floating Client when no tiled Client is left, or the most recently focused Client when the one that closed was floating.

Moving the pointer onto another Monitor focuses that Monitor.

Modes 2 and 3 cannot choose which window receives pointer input. The window under the pointer still receives it. Those modes only decide keyboard focus.

The keyboard and mouse hooks run on a thread of their own. It only decides whether a key or button is swallowed and hands everything else to the bind worker, so a window that stops answering, or a reload, never holds up the keyboard or the mouse, or makes Windows drop the hooks for being slow. Pointer moves that arrive while the bind worker is busy collapse into the newest one.


## Touchpad swipe

`gesture = fingers, direction, workspace` switches Workspace with a swipe, so `gesture = 3, horizontal, workspace` does it with three fingers. The direction is `horizontal` or `vertical`. Fingers run from 2 to 9. Any other direction, action or argument, including `mod:`, `scale:` and `unset`, warns and the line is skipped. A gesture matches once the fingers have moved 5 pixels: the larger axis picks horizontal or vertical, and the first gesture with that direction and finger count takes the swipe. A swipe is a touchpad gesture of three or more fingers, so a two-finger swipe gesture never matches. A locked session does not swipe.

The swipe follows the configured direction, not the one the fingers took. `horizontal` reads rightward travel and `vertical` downward. `gestures:workspace_swipe_invert` defaults to true, which turns that around, so fingers moving left go to the next Workspace and fingers moving right go to the previous one. The next and previous Workspaces are `m+1` and `m-1` on the focused Monitor. There is no previous Workspace before the first.

`gestures:workspace_swipe_distance` is the travel of a full swipe, in pixels from 0 to 2000, default 300. A touchpad's travel is counted at about 300 pixels per inch, 12 per millimetre. When the fingers lift, the Workspace changes once the swipe has covered half of that distance, or when its average speed per update is at least 30. A swipe shorter than 2 pixels never changes the Workspace. Swiping on past the last Workspace creates the next one, unless the Workspace swiped from is empty. Once the swipe has moved 10 pixels one way, moving back the other way counts as no travel.

While the fingers move, the Workspace swiped from follows them: a whole swipe moves it by the monitor's width, and the Workspace it goes to comes in beside it, from the right for the next one and the left for the previous one. A `slidevert` or `slidefadevert` style on the `workspaces` animation swipes up and down instead. Pinned and minimized Clients stay where they are. When the fingers lift, a switch slides both Workspaces on from where they are with the `workspacesIn` and `workspacesOut` animations, and a swipe that falls short slides the Workspace back and the other one away, which is then hidden. This follows the fingers even with `animations:enabled` false; the lift then lands at once.

Fingers that come down together are a swipe once their middle has travelled a millimetre. Two fingers that travel are a scroll, which no gesture takes.

Winland reads the fingers as raw input from a precision touchpad. A touchpad that is not a precision touchpad does not swipe. Raw input cannot be consumed, so Windows also acts on the same fingers. Turn its gestures off for the finger count you configure: open Settings, then Bluetooth & devices, then Touchpad, expand Three-finger gestures (or Four-finger gestures), and set Swipes to Nothing. Otherwise a three-finger swipe both switches the Winland Workspace and switches apps or desktops in Windows.

## Special workspaces

`special` and `special:` address the special workspace named `special:special`. `special:name` addresses `special:name`. The same address works in `workspace`, `movetoworkspace`, `movetoworkspacesilent`, and a window rule's `workspace` effect. A trailing `silent` on the rule does not show the special workspace.

When the focused Client closes while a special workspace is open on its Monitor, a Client elsewhere does not take the focus: the special workspace's Client focused last does.

When a special workspace opens on a Monitor, a floating Client on it whose middle is off that Monitor is brought onto it: by the offset between the Monitors when its middle is on another one, and otherwise to the Monitor's middle.

`togglespecialworkspace` shows that special workspace on the focused Monitor, or hides it when it is already shown there. The argument is the name, and an empty name is `special`. `workspace special:name` shows it and does not hide it again. One special workspace is shown on a Monitor, over the normal Workspace, whose Clients stay shown. Showing a special workspace that is open on another Monitor moves it. The normal Workspace stays the active one.

The special workspace closes when its last Client leaves. The Monitor's special workspace hides when its normal Workspace changes. Focusing a Client on the normal Workspace closes the special workspace. The pointer reaches the Clients of an open special workspace, tiled or floating, before the Clients of the normal Workspace under it. Where the special workspace has no Client, a pointer hit is not taken away from a window underneath it, so a click there still focuses that window and closes the special workspace.

Opening a special workspace emits `activespecial` and `activespecialv2` as `name,monitor` and `id,name,monitor`. Closing one emits them with an empty name. In events and text replies the unnamed special workspace is id -99, another special workspace -98, then -97, in name order. The JSON replies write a Workspace as its `address`, an `id` only when it is numbered, its `type`, `normal` or `special`, its `name`, and `monitor`, the Windows name of the Monitor it is on. The `specialWorkspace` of a Monitor with none open has empty strings and no `id`. A special workspace belongs to no Monitor. It opens on the focused one, and when the Monitor showing it is unplugged it is shown on the focused Monitor that remains, in place of any special workspace shown there. It is not a Guest, so it stays on that Monitor when the other comes back.

A `workspace` rule names a Workspace by its number and is honored for `monitor`, `default`, `persistent`, `gapsin`, `gapsout` and `layout`. A number in a workspace rule, such as `workspace = 3`, is that Workspace on every Monitor, and `monitor:` narrows the rule to the Monitors it matches. It does not move the Workspace onto that Monitor. Anything but a number in place of it warns `A workspace rule names a Workspace by its number, not '<text>'.` and the rule is skipped. A persistent Workspace stays when it is empty, and it is made on each enabled Monitor the rule matches. A Monitor shows a Workspace that holds Clients before an empty one. It shows Workspace 1 when that Workspace exists, and opens it when the number is free, before it shows a higher empty Workspace. When 1–10 are all in use, it shows an empty one of those before it makes a number above 10. A special workspace is never persistent. `default` selects the Workspace a Monitor shows when it has none. `gapsin` and `gapsout` replace the general values on that Workspace. `layout` names the Layout the Workspace uses in place of `general:layout`: `dwindle` or `scrolling`. Any other name warns and uses dwindle. The Layout is chosen when the Workspace is created and again when the config changes, and a Workspace that changes Layout keeps its Clients. Later rules for the same Workspace override earlier ones.

Any other field of a workspace rule warns and is skipped, and the rest of the rule still applies.

A workspace filter such as `r[1-3]` matches workspaces that already exist. It is not a workspace address, so `workspace`, `movetoworkspace` and `movetoworkspacesilent` do not switch on it.

A floating Client that `movetoworkspace` or `movetoworkspacesilent` moves onto a Workspace on another Monitor keeps its place relative to the Monitor.

## Monitors

Winland does not change a monitor's mode, resolution, refresh rate, position, scale, transform, mirror, bit depth, color, HDR, variable refresh, or whether it is enabled. A `monitor` line that is not a reserved area warns "Monitor settings other than a reserved area are not honored." and is skipped. The monitor stays where Windows put it, at the scale Windows reports. A line that only names a monitor matches and changes nothing.

`reserved_area` and `addreserved` take top, bottom, left and right, in logical pixels. Each edge is multiplied by the monitor's scale, rounded half away from zero, and subtracted from the work area Windows reports. Values below zero count as zero. A later reserved area replaces an earlier one. A later line that only names the monitor keeps the reserved area already chosen. An empty name is the rule for every monitor a named rule does not match.

When Windows reports a monitor disabled, or it is unplugged, each of its Workspaces that holds Clients becomes a Guest on the focused Monitor that remains, or on the first remaining enabled Monitor, or on the `FALLBACK` Monitor when none is enabled. A Guest keeps its Groups, fullscreen Clients and pinned Clients. It is numbered one past the highest Workspace number already in use on that Monitor, and at 11 or above when Workspaces 1 to 10 are all in use. A hole below that highest number stays empty, and a number that is already taken is skipped. Empty Workspaces vanish, a persistent one included. A Workspace that is already a Guest keeps the home it had. A special workspace is not a Guest: one that was shown is shown on the Monitor that takes the others, in place of any special workspace shown there. A pinned Client stays shown on that Monitor. The number the Monitor was showing, when that Workspace is not a special workspace, is remembered under the Monitor's identity, including when the Workspace was empty and vanished. When the Monitor comes back, its Guests return under those old numbers before any persistent Workspace is made again, and it shows the Workspace it showed when it left, made again when that one had vanished. An explicit move of a Workspace onto a Monitor clears the Guest, and unplugging is the only way a Workspace becomes one. It comes back by its identity, the make, model and serial from its EDID, not by its `\\.\DISPLAYn` name, so a dock that renames the port keeps the Workspaces on that Monitor. The identity is those three joined by spaces. Identical monitors, with the same make, model and serial, are numbered in the order they were first seen: the first keeps that identity, and each later one has ` #2`, ` #3` and so on after it. A monitor with no model and no serial has no such identity and comes back by its Windows name. `desc:` matches a prefix of the identity, or of the friendly description when the monitor has no model and no serial. `disable` and `disabled` in the config warn and leave the monitor enabled. When no monitor Windows reports is enabled, the Workspaces move to a `FALLBACK` Monitor of 1920x1080 at 0,0, and go back when a monitor is enabled again.

The `monitors` reply reports what Windows reports: the size, position, scale and refresh, `currentFormat` from the bits per channel, and `colorManagementPreset` `srgb` when none is reported. `description` is the Monitor's identity, and the friendly name when it has no model and no serial. `make`, `model` and `serial` are the EDID values, empty when Windows did not report them. `sdrBrightness`, `sdrSaturation`, `sdrMinLuminance` and `sdrMaxLuminance` are 1, 1, 0.2 and 80 when none is reported. `hardwareDetails` is `backend` `windows`, with `hdr`, `chroma` and `bt2020` from Windows and `vrrCapable` false. `transform` is 0, `mirrorOf` is `none` and `vrr` is false, because Winland does not record a rotation, a mirror or variable refresh that it does not change.

## Dispatchers

A command for the running Winland, such as `winland dispatch` or `winland clients`, goes down the pipe and never asks for UAC or starts Winland. An argument `winland` does not know prints the usage and asks for no approval either.

`winland` reads an argument that starts with `-` as a flag unless it is a number. A number may have a fraction and one trailing comma, so `winland dispatch splitratio -0.1` and `winland dispatch moveactive -50, 0` pass their numbers to the dispatcher.

In dwindle, `layoutmsg splitratio` changes the split of the focused Client's parent, by a delta or with `exact` to a value, clamped from 0.1 to 1.9. It answers `error: splitratio requires an arg` without a ratio, `error: cannot alter split ratio on no / single node` for a Client with no sibling, and `error: bad layoutmsg 'splitratio'` for a ratio that does not parse, in that order.

`cyclelayout` changes the Layout of the focused Workspace, and of the Special workspace when one is open on the focused Monitor. It goes from dwindle to scrolling to floating and back to dwindle. `back` goes the other way, and any other argument goes forward. A Client that was tiled floats while the Workspace is floating, and tiles again when the Workspace leaves floating. One that was already floating stays floating. The Workspace keeps that Layout until the config is loaded again, which puts it back on the Layout the config names, and a restart does too. `general:layout` does not accept `floating`. `activeworkspace` reports the Layout as `tiledLayout`.

`closeall` asks every Client on every Workspace to close, Special workspaces included, as `closewindow` does, so an application can still ask to save. It then shows Workspace 1 on the focused Monitor. A Special workspace that was open there is closed, so Workspace 1 is what shows.

`movecursor X Y` puts the cursor at that point on the desktop and handles it as a pointer move, so focus follows it as it follows the mouse. `cursor:no_warps` does not stop it. Coordinates may be split by a space or a comma.

`forcerendererreload` returns ok and does nothing. Reloading a renderer has no Windows meaning.

A window selector `stableid:` takes the `stableId` that `clients` reports, in hex, and matches it exactly.

`killwindow` ends the process that owns the Client, read from the window again when the kill runs. A Store app's frame belongs to ApplicationFrameHost, which hosts every Store app, so its Client's process, `pid` in `clients` and the `pid:` selector are the app hosted in the frame. ApplicationFrameHost itself is never ended: a frame that hosts no app is left alone.

`cyclenext` focuses the next Client on the focused Client's Workspace, in the order the Clients opened, and wraps around. A window selector after a comma names the Client instead, and the cycle runs on that Client's Workspace, then focuses the Client it lands on and shows that Workspace when it was not the one on screen. `prev` goes the other way. `tiled` or `floating` alone takes only that kind of Client, and both or neither take either. Minimized Clients, hidden Group members and `nofocus` Clients are skipped. With nothing focused, the first Client on the focused Monitor's Workspace takes focus. Other words are ignored.

`swapwindow` exchanges two Clients, by a direction or a window selector. A Client on another Workspace trades Workspaces with the focused one, each taking the other's slot, and the focus stays on the shown Workspace with the Client that came onto it. A Client in a Group does not swap across Workspaces. The answers are Winland's: `error: Can't swap fullscreen window`, `error: No window to swap with in that direction`, `error: No window to swap with` and `error: Can't swap a window with itself`.

`dpms` asks for display power on, off, or toggled. An empty monitor list addresses every display. A monitor name that matches none of the enabled monitors still addresses every enabled monitor. The adapter posts `SC_MONITORPOWER` to Winland's own window, which turns every display off or on together, and does not wait for any other window. Turning the displays on also sends a zero mouse move, because Windows does not reliably honor the "on" command. Tests do not send either. Windows itself wakes the displays on any input, so the displays come back on, but `dpmsStatus` stays false until a `dpms` turns them on. The displays turn off and on at once. `animation = fadeDpms` warns that the animation does not exist.

`movefocus` in dwindle, with a direction from a tiled Client look at the Clients whose edge touches or slightly overlaps that side and shares more than a pixel of it. Among them it picks the one focused most recently, and a Client that was never focused comes after every one that was. A tie goes to the Client that opened first.

In dwindle, `movefocus` and `swapwindow` with a direction from a floating Client look only at floating and covering Clients. A candidate's center must lie within 90 degrees of the direction. One within 54 degrees beats a wider one, and among those the nearest center wins. A tile is never picked.

`movefocus`, `cyclenext`, `focusurgentorlast` and `focuscurrentorlast` move the cursor to the middle of the window they focus. Leaving a fullscreen window for another on its Workspace does not move the cursor, and `cursor:no_warps` stops it.

`movefocus` continues onto the neighbouring Monitor when nothing in that direction can take focus. There it picks the Client the way the Layout does, choosing the most recently focused among the Clients whose edge touches or slightly overlaps the side and shares more than a pixel of it. A Client that floats looks at floating Clients first and a tile at tiles first, then at the other kind. A fullscreen Client covers its whole Monitor, floating or not, and counts as a tile. A Client with `nofocus` is never picked. `movewindow` continues when the point just outside the Client lies on another Monitor, and the Client goes in at that point there. A tile that meets the edge of the work area less `gaps_out` reaches the Monitor's edge for that point, so it crosses. The Workspace it left is laid out again. Scrolling also continues when the move cannot be made inside the Workspace. A window selector after a comma names the Client, which moves on its own Workspace and Monitor. A direction leaves the focus where it was when that Client is not the focused one. A direction onto the neighbouring Monitor does not follow when the Client was not focused. `mon:` follows unless silent. A relative monitor selector stays relative to the focused Monitor.

A Workspace with a fullscreen or maximized Client offers no window to `movefocus` in a direction, so focus continues onto the neighbouring Monitor or stays.

`workspace N` shows Workspace N of the focused Monitor. The same number on another Monitor is another Workspace, and there is no named Workspace: `name:` and a bare name answer `error: no such workspace`. `movetoworkspace` and `movetoworkspacesilent` read the number the same way. `m+N` and `m-N`, and `e+N` and `e-N`, walk the focused Monitor's Workspaces, and `e` walks the same list as `m`. `r+N` and `r-N` step from the number that Monitor is showing, and `r-1` from Workspace 1 stays on 1. `empty`, `next` and `previous_per_monitor` stay on the focused Monitor. `previous` can still show a Workspace on another Monitor, from the history. A special workspace opens on the focused Monitor, and one that another Monitor is already showing focuses that Monitor. When the focused Monitor changes, the cursor goes to the middle of the Client it focuses, or to the middle of the Monitor for a Workspace without a Client. `cursor:no_warps` stops it.

`binds:workspace_back_and_forth` defaults to 0. With 1 or `all_monitors`, `workspace` asking for the Workspace the focused Monitor shows goes to the Workspace visited before it, on any Monitor. With 2 or `per_monitor` it goes to the one visited before it on the focused Monitor. Without such a Workspace the Monitor stays where it is. The history keeps a visit to a Workspace that was removed until it is read for a previous Workspace. That read drops the visits to removed Workspaces, except the newest one of each Monitor before that Monitor is seen again further down. `true` and `false`, as older configs write it, are 1 and 0.

`changeworkspaceid CURRENT NEW` gives a numbered Workspace on the focused Monitor a new number. Both words are numbers from 1 to 4294967295, which keeps a Workspace number in 32 unsigned bits. The new number must be free on that Monitor. A special workspace cannot change its number, and a Guest keeps the number it had at home. A selector that is not two such numbers answers `error: invalid workspace id`. A first number that names no such Workspace, or a number that is taken, answers `error: bad workspace`. The Workspace keeps its Clients and its place in the Workspace history, so `workspace previous` reaches it under the new number. The workspace rules for the new number apply. The change emits `changeworkspaceid>>OLD,NEW,MONITOR` and no other event.

`focusmonitor`, `movecurrentworkspacetomonitor`, `moveworkspacetomonitor` and `swapactiveworkspaces` address a Monitor by its name, a `desc:` prefix of its identity, a direction, `current`, a relative `+N` or `-N`, or its id. Changing the focused Monitor emits `focusedmon`. `focusmonitor`, and `movefocus` onto another Monitor, put the pointer in the middle of a Monitor with nothing to focus, unless `cursor:no_warps` is set. A Monitor with a special Workspace open gives the focus to that Workspace's window. Moving a Workspace onto another Monitor emits `moveworkspace`. `workspace` and `workspacev2` are emitted when a Monitor's shown Workspace changes and the focus may follow that change, and when `swapactiveworkspaces` changes the Workspace the focused Monitor shows. Focusing a Monitor that already shows its Workspace emits `focusedmon` and not `workspace`. A Monitor coming or going emits neither.

Moving the Workspace a Monitor shows onto another Monitor leaves its pinned Clients on the source Monitor, on the Workspace that Monitor shows next. The Workspace keeps its number when that number is free on the destination, and otherwise takes the first free positive number, so a hole can be filled. `swapactiveworkspaces` numbers both sides that way after both have been lifted, so each can keep its number and two Monitors can both show Workspace 3. The move clears a Guest. A special workspace has no number, and moving it only changes which Monitor shows it. A window moved onto a Monitor lands on the Workspace that Monitor is showing. Moving or swapping a normal Workspace does not move the special workspace shown on that Monitor. The cursor is not forced to the center of the destination Monitor. Warps follow the cursor settings.

`pin` toggles whether a floating Client is pinned. A fullscreen or maximized Client does not qualify. `enable` and `on` pin it. `disable` and `off` unpin it. A window selector after that word, or in place of it, chooses the Client. A tiled Client does not qualify. Changing the pin emits `pin` with the address and `1` or `0`. The same request again emits nothing. A pinned Client moves onto the Workspace its Monitor is showing, and it is not hidden when that Monitor switches Workspace. Unpinning leaves it on that one Workspace. A pinned Client that is focused stays focused across the switch. Changing whether a Client floats clears the pin and does not emit `pin`. `movetoworkspace` and `movetoworkspacesilent` do not move a pinned Client onto a special workspace, and `movetoworkspace` still opens that special workspace on the focused Monitor and keeps the Client focused.

`fullscreen` and `maximize` do nothing to a pinned Client while `sync_fullscreen` is true, and `fullscreenstate` sets only its client mode. While `sync_fullscreen` is false, they leave the client mode and set the internal mode back to 0. A pinned Client is not raised above other windows. Placement does not change z-order. A window owned by a pinned Client, such as its dialog, opens pinned when it floats.

## Fullscreen

`fullscreen` toggles the focused Client. An argument of `1`, `maximize`, or `maximized` toggles maximize. Any other argument, including `0` and `2`, toggles fullscreen. A second argument `set` or `unset` forces that mode on or off. An unrecognized second argument does nothing. A last word `default` asks for the default fullscreen below instead of the Layout's. `maximize` is the same toggle as `fullscreen 1`.

Mode 0 is the layout slot. Mode 1 resizes the Client to its Workspace's work area less `gaps_out`, or to the whole work area for a floating Client, and keeps its border inside that area. A maximized Group member leaves room for its bar, floating or tiled. Mode 2 resizes it to the monitor rectangle and drops the border. The window's frame style comes back when it leaves mode 2, when it stops being a Client, and on a clean exit. The style it had is recorded, and after a crash the next start writes it back. While a Client is in mode 1 or 2, the dwindle tree is not refit, and mode 0 restores that same slot. `movewindow` in a direction, `swapwindow`, and the dwindle `togglesplit`, `swapsplit`, `rotatesplit` and `movetoroot` refuse a Client in mode 1 or 2. `rotatesplit` refuses without an error. One covering Client replaces another on the same Workspace. Moving that Workspace onto another Monitor resizes the covering Client to the destination. A Client moved to another Workspace or Monitor keeps both its modes there and replaces a covering Client already there. A Layout change on reload keeps them too.

Winland stores a client mode beside the internal mode, which `clients` reports as `fullscreenClient`. `fullscreen`, `maximize` and a maximize request from the window set it equal to the internal mode, and so do the `fullscreen` and `maximize` window rules. It is not sent to the application. Windows has no fullscreen state separate from the window rectangle, so an application that asks to be fullscreen is not observed, and a maximized Client does not return to maximized after the application leaves fullscreen on its own.

On a Workspace with the scrolling Layout, a tile that goes fullscreen or maximized is laid out by the Layout. It moves to a column of its own, which becomes as wide as the Monitor when fullscreen and as wide as the view when maximized, and the column is fitted into view. The Client covers the Workspace only while its column fills the view. A fullscreen one then fills the Monitor without a border. A maximized one fills the work area less `gaps_out`, keeps its border, and leaves `gaps_in` on each side that has a column next to it. When focus moves to another column the strip scrolls as usual, and the Client keeps its mode, its height and its place on the tape. Several tiles can hold such a mode at once, and a floating Client that goes fullscreen does not end it. Leaving the mode gives the column back the width it had and fits it into view again. A tile that comes to share its column, by `consume` or a move, leaves the mode. A floating Client, a tile in another Layout, and a request with `default` use the default fullscreen. `clients` reports which in `fullscreenHandler`: `scrolling` for a Client the scrolling Layout holds and for a tile in that Layout that is not fullscreen, and `default` otherwise. A fullscreen Client that moves to another Workspace keeps the default fullscreen, and keeps the scrolling Layout's when it lands in another scrolling Layout.

Each window has Winland's `allowedOverFullscreen` flag, which `clients` reports and which is true until a fullscreen takes it. When a Client goes fullscreen or maximized the default way, every other window on its Workspace that is not pinned loses the flag, and gets it back when that ends. On a scrolling Workspace, the floating windows that were open when a tile went fullscreen lose it, while floating windows opened after keep it; showing another held tile, or a floating fullscreen ending, applies that again. A floating window that opens, floats, is raised with `alterzorder top` or is focused over a default fullscreen gets the flag, and `alterzorder bottom` takes it. A window without the flag while a Client covers its Workspace is reported as neither `visible` nor `acceptsInput`. A floating one is lowered behind the covering Client then, and raised again when it gets the flag back.

Focusing a tiled Client on a Workspace where another Client is fullscreen or maximized ends the covering Client's mode. That covers `focuswindow`, a window that takes the foreground, and a tiled window that opens there. A floating Client is focused over the covering one and changes nothing, and a window that opens with a fullscreen rule takes its own mode. Focusing a tile beside a Client the scrolling Layout holds fullscreen changes nothing either: the strip scrolls to the tile. A tiled window that opens there still ends the mode.

A focused fullscreen or maximized Client that closes passes its mode to nothing. Neither the Client that takes the focus nor the Group member that takes its place takes the mode.

When Winland starts, it adopts the windows that are already open. When a Client is minimized, by its button, `Win+Down`, `Win+M` or a double click, Winland restores it at once and the Client keeps its place. A window that is already minimized when Winland starts is not adopted until it is restored, and a minimized window is not put back into the Layout when Winland restarts.

A Client's maximize request is maximize mode 1: its maximize button, `Win+Up` or a double click on the title bar maximizes it, and asking again leaves it. It acts on that Client, whichever window has focus. The system's own maximized state is undone, so the Client fills the work area as `fullscreen 1` does. A window that opens maximized while Winland runs asked for it before it mapped, which Winland ignores, so it is tiled like any other window. Its maximize button works as usual afterwards. A window that was maximized before Winland started is adopted maximized.

A `fullscreen` window rule requests mode 2. A `maximize` window rule requests mode 1. A trailing `0` turns that flag off. `fullscreen_state` sets the two modes, for example `2 0`, and wins over those flags. A popup window with no caption that already covers its monitor is not adopted.

## Modifiers

A modifier list in a bind and `sendshortcut` is read as Winland reads it: the list is upper-cased and each modifier name found anywhere in it counts, so `SUPER SHIFT`, `SUPER_SHIFT`, `SUPER+SHIFT`, `$mainMod_SHIFT` with `$mainMod = SUPER`, and `super shift` are the same. `SUPER`, `WIN`, `LOGO`, `MOD4` and `META` are the Windows key, `ALT` and `MOD1` are Alt, `CTRL` and `CONTROL` are Ctrl, and `SHIFT` is Shift. `CAPS` is the Caps Lock key and `MOD2` the Num Lock key while they are held, not their lock. `MOD5` is AltGr held, on a keyboard layout that has it, where the right Alt key is `ISO_Level3_Shift` and not Alt. No key holds `MOD3`, as on Winland's default keymap, so a bind that needs it never fires. `binds` reports them in `modmask` with Winland's bits: 2, 16, 32 and 128. `sendshortcut` sends a key without them, since holding Caps Lock or Num Lock down would turn its lock over. A list that names none of them warns `Invalid modifier` and the bind is skipped.

A bind on a modifier key, such as `Super_L`, is matched on its press without that key's own modifier, so `bind = , Super_L` runs when Super goes down alone. On the release the mask includes the key's own modifier, so `bindr = SUPER, Super_L` runs when Super is let go and `bindr = , Super_L` never runs: its press swallows Super, and its release matches nothing and is swallowed too. Super and its release still reach Windows under `bindr = SUPER, Super_L`, so Winland sends a mask key before the release, and Start does not open.

A release bind matches the modifiers its key went down under, so `bindr = SUPER, Q` does not run for a Q pressed before Super. A release bind on one key is skipped when, while its key is held, a bind catches another key or any other key is let go: `bindr = ALT, Alt_L` does not run after Alt+P ran `bind = ALT, P`, and `bindr = SUPER, Q` does not run when Super is let go before Q.

## Sending keys

`sendshortcut` takes modifiers, a key, and a window selector. It sends the key with exactly those modifiers down. A modifier the user holds that is not named is let go around the key and pressed again after it, if the user still holds it then. A `sendshortcut` bind presses the key on the press and releases it on the release. From the pipe it presses and releases at once. A number above 9 and `code:N` are keycodes, `mouse:272` to `mouse:276` are the left, right, middle, side and extra buttons, and anything else is a key name in the focused window's keyboard layout. An empty selector sends to the focused window. A bad argument answers `invalid args`, `invalid modifiers`, `invalid mouse button`, `invalid key`, `key not found`, or `window not found`, after the dispatcher name.

A sent key is tagged, so Winland's own hooks let it through and it never runs a bind.

Every 2 seconds, and on unlock, Winland lets go of a modifier that Windows holds down but the user is not holding, such as one whose release was lost. A modifier a `sendshortcut` press left down on purpose is kept. The check waits while the keyboard hook may have missed a key.

## Urgency

A window that takes the foreground is handled as an activation request, which honors one only with a fresh input serial. A window that takes the foreground with no click or key just before it has none, so the focus goes back, whatever `misc:focus_on_activate` says. A window of one program that takes it right after a click in a Client of another program has one: it keeps the focus only with `misc:focus_on_activate`, default false, or a `focus_on_activate` window rule or property, which wins. Any other change after a click or key is the user's own: a click on the window itself, a key such as Alt+Tab, a click on a window Winland does not manage such as the taskbar, the Start menu or a notification, and a window of the program that was clicked. A Client is urgent when it flashes for attention, and when it takes the foreground and the focus is sent back. Each emits `urgent` with the Client's address. The focused Client flashing is not urgent. Focusing a Client clears its urgency.

`focusurgentorlast` focuses the first urgent Client in Workspace order and switches to its Workspace. With none, it reads the focus history from its oldest end: with a Client focused it takes the second oldest, and with none the oldest. That is the Client focused before the current one only while two Clients have been focused, and it can be the focused Client itself, which changes nothing. With neither it answers `error: window not found`.

`focuscurrentorlast` focuses the Client focused before the newest one in the focus history, and switches to its Workspace. With fewer than two Clients in the history it answers `error: History too short`.

## Animations

`animations:enabled` defaults to true. False, or the Windows setting **Animation effects** turned off, moves every window at once.

`bezier = NAME, X0, Y0, X1, Y1` names a cubic Bézier curve. `default` (0, 0.75, 0.15, 1) and `linear` are always defined. `animation = NAME, ONOFF, SPEED, CURVE[, STYLE]` sets one node of the animation tree. SPEED is in tenths of a second. A node that is not set takes the values of its nearest set parent, and `global` starts at on, 8, `default`. Both lines are read in config order and may also be written inside `animations { }`. A missing node, a speed that is not above 0, or a curve not defined above the line warns and is skipped. A CURVE of `spring:NAME` names a spring curve, from a `spring` line: a mass on a spring with damping, let go at rest and pulled to its goal, solved exactly as Winland's animation library steps it. A node on a spring runs until the spring is within 0.001 of its goal and slower than 0.001 a second, so its SPEED changes nothing, and an underdamped spring overshoots and bounces before it settles. A style that is not valid for its node warns and is still kept.

These nodes animate:

- `windowsIn` and `fadeIn` when a window is adopted. The default style `popin [N%]` grows it from N percent of its size, at least 5 pixels, around its middle. `slide [top|bottom|left|right]` brings it in from the nearest monitor edge or the side named. The window fades in from transparent.
- `windowsOut` and `fadeOut` when Winland closes a Client. The window plays the same style in reverse and fades out, and is then asked to close. A window's own `animation` style, from an `animation` window rule or `setprop`, replaces the `windowsIn` and `windowsOut` style it opens and closes with, and keeps the node's curve and speed. A window that is still shown 1.5 seconds later is put back on its Layout rectangle at its full alpha. With both off, or with animations off, the window is made transparent at once and asked to close, so nothing it draws while it closes shows, and one still shown 1.5 seconds later is opaque again.
- `windowsMove` when a shown Client gets a new Layout rectangle, from wherever it is at that moment. A dwindle tile that `resizeactive` or `resizewindowpixel` resizes, and the tiles that make room for it, move at once. Floating Clients animate. A window dragged or resized with the mouse moves at once. The windows its Layout moves to make room for a tile lifted out by a drag, or dropped back in, animate, and a mouse resize moves every window at once. A Client going into or out of fullscreen mode 2 moves between its rectangle and the Monitor's the same way: its frame is dropped or put back when the motion starts, and it is drawn by a stand-in while its size changes. One that stays fullscreen, such as on a Monitor change, is put in place at once.
- `workspacesIn` and `workspacesOut` when a Monitor switches Workspace, and `specialWorkspaceIn` and `specialWorkspaceOut` when a special workspace is shown or hidden. Styles are `slide`, `slidevert`, `fade`, `slidefade` and `slidefadevert`, with an optional travel percentage such as `slidefade 20%` and an optional side. A Workspace with a higher number comes in from the right. A `slide`, `slidevert` or `slidefade` travels the monitor's width or height. A special workspace also fades. A leaving window is hidden when its motion ends. A workspace rule's `animation:` style replaces the node's style: a switch plays the style of the Workspace switched to, for the Workspace that leaves too, and a special workspace shows with its own style and hides with the style of the special workspace that replaces it on its Monitor, or its own.
- `fadeSwitch` when a Client's opacity changes, for example between `active_opacity` and `inactive_opacity`.
- `border` when a Client's border color changes. The colors blend in the OkLab space.

The adapter moves each window with `SetWindowPos` and sets its alpha with `WS_EX_LAYERED`, once per composed frame, on a thread of its own, so binds and window events are never kept waiting. A frame does not wait for the window to take it, so a window that is slow to lay itself out does not hold up the others, and a window still busy with the last frame skips the next ones until it catches up or three frames have passed. A frame that keeps the size only moves the window. The steps of a drag that is still held are sent the same way, and the drag's end places every window exactly. A window already on its Layout rectangle is not moved again, and the moves Winland makes are not taken for the user's, so the window's size limits are not read again for them. A motion that starts while another runs carries on from where the window is. A placement that arrives without a motion stops the window's movement, so the window always ends on its newest Layout rectangle, and a hidden window is put back on its Layout rectangle while hidden. A window cannot be made smaller than its own minimum size, so a small `popin` start is held at that minimum.

A window whose size changes during a motion is given the size it rests at when the motion starts, so it lays itself out once: a window that grows, one that shrinks, and the `popin` style of `windowsIn` and `windowsOut`. A window that shrinks across or down keeps its larger width or height until the motion ends, and then takes its size. A closing window keeps its size and is not moved at all. Until the motion ends the window is made transparent and a window of Winland's own shows a DWM thumbnail of it in each frame's rectangle. The picture is scaled by the same amount across and down, as little as covers the rectangle, and what does not fit is cut off on the right and bottom, so a window never shows its content stretched: a `popin` grows the whole picture evenly, and a tile that changes shape shows its content at its own size, cut off at the moving edge, as a window does while its edge is dragged. A window that has not yet painted its new size shows what it painted before at the same scale, and the area it gained repeats a column and a row of its picture just inside its border. A window that paints with GDI tells when it has painted; one that draws with DirectX does not, and shows what it painted before for the first 50 milliseconds after it takes its larger size. A window that was transparent before the motion, such as one that opens, has nothing painted before. A window takes several frames to paint a new size, so a window resized on every frame would show its unpainted area along its growing edges or lay itself out on every frame. The window's border follows the stand-in's rectangle each frame, not the window's own. While a motion fades a window, its border is drawn with the same alpha. A window its program already made layered cannot be made transparent, and is resized on every frame instead, and so is one whose picture cannot be shown. A motion that only moves a window, such as a slide, moves the real window. When a closing window's motion ends it stays transparent while it is asked to close; one that stays open is put back on its Layout rectangle.
## Groups

A Group is one tile that holds several Clients. Only the shown member is in the Layout. The other members are hidden and keep their Workspace, so they are listed by `clients` with `hidden` true and their `grouped` list. They are recorded as hidden, shown again on a clean exit, and shown again after a crash, like any hidden Client. A Group is not rebuilt after a restart; its members come back as separate Clients.

`togglegroup` makes the focused Client a Group of one, and on a grouped Client ends the Group. Ending a Group leaves the tile to the last member and gives every other member its own tile. A fullscreen Client leaves fullscreen first. Making a Group emits `togglegroup>>1,ADDRESS` and ending it emits `togglegroup>>0,ADDRESS` with the first member, one address only.

`changegroupactive` shows the next member, or the previous one with `b` or `prev`. A number picks the member at that position, counted from 1, and 0 or less picks the last. The shown member keeps the tile's place, size, floating and fullscreen state in every Layout. Each time the shown member is placed, the hidden members are placed at the same frame, so a member is already in place when it is shown. A hidden window stays hidden when it is moved. Focus moves to the newly shown member when the Group was focused. A window that is not grouped is an error, and so is a Group of one. `movegroupwindow` swaps the shown member with the next one, or the previous one with `b` or `prev`, in the Group order. `focuswindow` on a hidden member shows it first. When the focused shown member closes, the member focused most recently is shown and focused, and otherwise its neighbour.

`moveintogroup` with `l`, `r`, `u`, `t`, `d` or `b` moves the focused Client into the Group of the Client in that direction. The moved Client becomes the shown member and is focused, and it emits `moveintogroup`. With nothing in that direction on its Workspace, the Client looks onto the Monitor in that direction, joins the Group of the Client there that `movefocus` would pick, and takes the focus on that Monitor. `moveoutofgroup` takes the focused Client, or the Client a window selector names, out of its Group into its own tile, next to the Group, and emits `moveoutofgroup`. The removed Client is focused. A window selector after a comma names the Client.

A `movewindow` mouse bind pressed on a tab of a Group of more than one takes that member out of the Group and drags it alone, and it is dropped as any dragged window is. On a Group of one, between tabs, or with `resizewindow`, the drag takes the window under the pointer as anywhere else. A window dragged with a `movewindow` mouse bind, or by its title bar, and dropped on a Group joins it. `group:drag_into_group` defaults to 1: a window dropped on a member joins after the current member, and one dropped on the tab bar joins at the tab under the pointer. 2 takes it only on the tab bar, and 0 never. A dragged Group brings every member. A floating window does not join a tiled Group.

A window that opens while a Client of a Group is focused, on the same Workspace, joins that Group after the shown member and is shown. A dialog does not join, and a floating window does not join a tiled Group. Moving the shown member to another Workspace or Monitor takes the whole Group with it.

`group:col.border_active` and `group:col.border_inactive` color the border of a grouped Client. A gradient is not a border color, and the previous color stays.

Winland draws the tab bar itself, in its own window just above the shown member in the z-order, and puts it back there whenever the shown member is raised or shown, or any window changes its place in the z-order, so a window raised over the member's tile covers the bar too and the member raised again brings it back. A tiled Group's bar takes the top of the tile and the shown member is placed below it. A floating Group's bar sits above the window. From the bottom up the bar is `gaps_out`, the indicator (`indicator_height`), `indicator_gap`, the title row (`height`, when `render_titles` or `gradients` is on) and, with `keep_upper_gap`, another `gaps_out`. Tabs share the width with `gaps_in` between them. `stacked` gives each tab its own such row across the whole width instead, the first member at the top, so the bar is one row per member plus the upper gap; a click or a drop picks the row. Sizes are logical pixels multiplied by the Monitor's scale. The tab of the focused Client uses `col.active` and `text_color`, and the others use `col.inactive` and `text_color_inactive`. A color's alpha is kept. `rounding` (default 1) and `rounding_power` (default 2, a circle) round the indicators' corners. With `round_only_edges`, on by default, and more than one tab, only the outer corners of the first and last indicator are round. `gradients` fills each tab's title row behind its title with a vertical gradient of that tab's `col.*` colors: the first color nearest the bottom, and a single color filling the row. It is rounded by `gradient_rounding` (default 2), `gradient_rounding_power` and `gradient_round_only_edges` in the same way. The indicators take only the first color of a `col.*` gradient. `group:groupbar:blur` warns and is skipped. `font_family` (default `misc:font_family`), `font_size`, `font_weight_active`, `font_weight_inactive`, `text_offset` and `text_padding` are honored. Titles are antialiased: they are drawn white on black into a mask with grayscale antialiasing, and each title's color is laid over the bar as much as the mask covers each pixel, so their edges blend with the strip and the tab colors under them. Titles are read from the windows and redrawn within a second of a change. `enabled` false or `disable_when_only` with one member draws no bar and takes no space. A fullscreen Client in mode 2 has no bar, and neither has a Group whose shown member has `decorate 0`, from a window rule or `setprop`. `priority` (0 to 6, default 3) places the bar among the decorations on a window's top edge. The bar is the only one, so the value is kept and changes nothing.

A click on a tab focuses that member, and a click between tabs focuses the shown member. A middle click closes the member when `middle_click_close` is on. The wheel shows the next or previous member when `scrolling` is on, and moves the focus to it only when the member it replaces had the focus.

## IPC pipe

A client has 5 seconds after it connects to send its request line. One that sends nothing in that time is disconnected. After the reply the Daemon waits up to 30 seconds for the client to close. Each client is served on its own and an idle `events` subscriber holds no thread, so a slow or silent client never keeps another, or a bind, waiting.

The pipe refuses clients on other machines. When another process already holds the pipe name, the Daemon fails to start and says so, instead of sharing the name with it.

An event that names a Workspace also names its Monitor, in the field just after the Workspace name or id. `openwindow` is `address,workspace,monitor,class,title`. `movewindow` is `address,workspace,monitor` and `movewindowv2` is `address,id,name,monitor`. `workspace` is `name,monitor` and `workspacev2` is `id,name,monitor`. `createworkspace` and `destroyworkspace` follow `workspace`, and their v2 forms follow `workspacev2`. `destroyworkspace` carries the id, the name and the Monitor from before the Workspace was removed. `changeworkspaceid` is `old,new,monitor`. `focusedmon`, `activespecial` and `moveworkspace` already name the Monitor and are not given another. Before any Monitor is reported the Monitor name is empty. A JSON Workspace is `address`, `id` when it is numbered, `type`, `name` and `monitor`, the Windows name. A list entry keeps `monitorID` as well. Two Workspaces can both be `3`, and `monitor` tells them apart. The text reply for a Client names the Monitor its Workspace is on. A crash-recovery snapshot records a Client's Monitor by that Monitor's identity, the same string a returning Monitor is recognized by, and the Workspace by the number it is showing. A Guest is recorded on the Monitor showing it, under the number it is showing there, not under its home. A special workspace is recorded by its name. An older snapshot that stored the Monitor as a number is not read.

`keyword NAME VALUE` applies one config line at once. An option such as `misc:focus_on_activate` replaces its value. A line that may repeat, such as `windowrule`, `workspace`, `monitor` or a bind, is added after the lines already read, so a window rule applies to the windows that open next and a workspace rule merges into the rule for the same Workspace. `exec` and its variants and `source` answer `error: keyword 'NAME' is not applied live`, because they launch a program or load a file, which happens only when the config is read. A keyword the config would warn about answers with that warning. A keyword with no value answers `error: invalid keyword`, but for the `input:kb_` options, which it sets to nothing. `reload` drops every line `keyword` added.

`misc:font_family`, default `Sans`, is the font of the text Winland draws: the tab bar when `group:groupbar:font_family` is empty. The generic names `Sans`, `sans-serif` and `system-ui` are Segoe UI, `Serif` is Cambria and `Monospace` is Consolas; any other name is used as it is.

`debug:disable_logs` false, true by default, also writes the log to `winland.log` beside the state file, emptied at each start. Winland's standard error is written whatever this says, since it is where Windows tools and the run script find its errors, and an elevated Winland writes no log file, since a folder the user can change could send a write by name where only administrators may write.

`kill` waits for a click: the next press of any mouse button ends the program of the Client under the pointer, emits `kill>>ADDRESS`, and goes to neither window, nor does its release. Escape gives up instead and goes no further. A click on no Client ends nothing. Either way the wait is over. The pointer keeps its shape while it waits.

A config that is read or reloaded with warnings shows one notification: `Winland: N config errors`, then the first warning with its file and line. A later load replaces that notification, including a reload of the same errors. A load with none shows nothing and takes the previous notification away. `winland configerrors` and the event stream list every warning. Clicking the notification opens the file the first warning names, in the program Windows opens that type with, or in Notepad when the type has none.

A batch, `[[BATCH]]` or `winland --batch`, splits: at every `;`, brackets or not, and each command is trimmed. `\;` puts a `;` in a command and `\\` a backslash, and a backslash before anything else stays as it is. So a Windows display name in a batch is written `\\\\.\\DISPLAY1`, and a rule block with more than one rule `[float\; tile]`. The replies are joined by two empty lines, and a command left empty, as after a last `;`, replies as an unknown command does. Flags before the batch, such as `j/[[BATCH]]` or `winland -j --batch`, apply to each command it splits into.

With no window, `clients` replies `no open windows` and `activewindow` replies `Invalid`. With `j/` they reply `[]` and `{}`.

`getoption NAME` answers one Option Winland reads, with the value Winland applied. The reply is a JSON object with `option`, the value under its type (`int`, `bool`, `float`, `str`, `vec2`, `css` or `gradient`) and `set`, true when a line the config applied set that Option. A color is a `str` in the form `0xAARRGGBB`, and the value is always one the config reads. An unknown name answers `no such option`.

## Virtual desktops

Winland's Workspaces are not Windows virtual desktops. A shown Client that a virtual desktop switch cloaks stops being a Client, and it is adopted again when it is uncloaked. A Client Winland has hidden stays a Client on its Workspace while it is cloaked, so it comes back when its Workspace is shown.

## Notification area

Winland shows an icon in the notification area with the number of the Workspace the focused Monitor is showing, including the number a Guest is showing there. Switching Workspace changes that number. A special workspace has no number, and the icon keeps the number of the Workspace underneath. The tooltip names the Workspace. `general:tray_icon` defaults to true. False removes the icon, and a reload or `keyword` applies the change at once.

The icon also carries that notification as a balloon. `general:tray_icon` false adds an icon only for the balloon and removes it once the balloon is dismissed or clicked. A click on the balloon opens the file, as Edit config does.

A click or a right-click on the icon opens its menu: Reload, Edit config, Open log and Quit. Reload reads the config again, as `winland reload` does. Edit config opens the config Winland is reading in the program Windows opens that file's type with, or in Notepad when the type has none. For `winland.conf` that program is the editor for `.conf`. Open log opens `winland.log` beside the state file the same way. Quit runs `exit`, which stops Winland and puts its windows back.

The icon comes back when Explorer starts again. Winland runs elevated and Explorer does not, so the icon's callback and the `TaskbarCreated` message are let through the window's message filter. Without that, Windows drops them and the icon never answers a click or a restart of Explorer.

## Daemon

One Daemon runs per session. A second `winland` started in the same session prints "Winland is already running in this session." and exits with code 1. A Daemon started with a different `WINLAND_PIPE` counts as a separate instance.

`winland install` asks for one UAC approval, stops a running Winland, and copies the folder `winland` was run from into `C:\Program Files\Winland` (ADR 0006). In a release zip that folder is `winland\`. The logon task starts `C:\Program Files\Winland\winland.exe` at logon with the highest privileges, and never the folder install was run from. That folder is added to the machine `PATH`, so a new terminal can run `winland`. A shortcut in the common Start menu carries Winland's AppUserModelID, `Winland.Winland`, and Settings › Apps lists Winland. Its uninstall runs `winland uninstall`. Winland then starts. An elevated install also removes a per-user install, so logon starts only one. `--no-logon` installs without the logon task, and removes one an earlier install made. `--no-start` leaves Winland stopped when install finishes. Install finds the running Winland by the process that answers on its pipe, so the unelevated `winland install` waiting on the UAC approval is not taken for it. When the UAC prompt is declined, `winland install` exits with code 1223.

`winland install --user` asks for no approval. It copies into `%LOCALAPPDATA%\Programs\Winland`, adds that folder to the user `PATH`, and starts Winland at logon from the user's Run key as `"<that folder>\winland.exe" --no-elevate`. The Start menu shortcut and the Settings › Apps entry are per-user, and the shortcut starts Winland with `--no-elevate`. `--no-logon` leaves out the Run key entry, and `--no-start` leaves Winland stopped, as they do for an elevated install. A Winland whose executable is in that folder never relaunches itself through UAC. It leaves an elevated install in place, because removing that needs an administrator.

`winland uninstall` stops Winland and removes the logon task or the Run key entry, the shortcut, the Settings › Apps entry, the `PATH` entry and the installed files. It keeps `%USERPROFILE%\.winland`. It puts back every Snap and touchpad value recorded there, and it does that before `winland uninstall --purge` deletes the folder. Uninstalling a per-user install asks for no approval. Uninstalling the copy under Program Files asks for one, and then removes a per-user install as well. A link in the folder being copied is refused. Uninstall removes a link in an installed folder itself and does not follow it.

`winland update` follows one channel. Stable is the newest published release on GitHub. Dev is one rolling prerelease on the tag `dev`, rebuilt from `main` after CI passes, with a version such as `0.1.0-dev.42+439da64`. A plain `winland update` uses the channel saved in `%USERPROFILE%\.winland\channel`, and stable when that file is missing. `winland update --channel stable` or `winland update --channel dev` writes that choice and then updates. The install script installs stable unless it is run with `-Channel dev`.

On stable, Winland reads `version.json` from that published release. When its version is the running one, Winland says it is up to date and stops. On dev, Winland reads `version.json` from the `dev` release. When the commit in that file is the running build's commit, Winland says it is up to date and stops. A different commit is installed. Switching from dev to stable installs the newest stable release even when that version is older. Otherwise Winland downloads `Winland-win-x64.zip` and `SHA256SUMS` from the chosen release. A zip whose SHA-256 does not match is refused and nothing is changed. When the hash matches, the running Winland is stopped, the files in the install folder this command was run from are replaced, and the new version is started when Winland was running. A Winland that was not running stays stopped. That folder is `C:\Program Files\Winland` or `%LOCALAPPDATA%\Programs\Winland`. The config is kept. An update of the Program Files copy asks for one UAC approval for the replace. An update of a `--user` install asks for none. Run from a folder that is not an install, it says to run `winland install` and stops. Winland never checks for updates by itself.

`scripts/install.ps1` is the one-line install. In Windows PowerShell 5.1 or PowerShell 7 it is run as `irm https://raw.githubusercontent.com/dante-sparras/winland/main/scripts/install.ps1 | iex`. It prints the Winland banner, then reads the newest published release and shows its version. When Winland is not installed it asks two questions, and Enter means yes: start Winland when you sign in, and start Winland now. It then downloads `Winland-win-x64.zip` and `SHA256SUMS`, stops when the SHA-256 does not match, unzips to a temporary folder, and runs `winland install`. A no to the first question adds `--no-logon`, and a no to the second adds `--no-start`. The script always installs for every user, so Windows asks for one administrator approval. Then it runs `winland tweaks --off` on the installed copy, unelevated, so the settings belong to the signed-in user. That command reads each setting once, records the old values in `%USERPROFILE%\.winland\windows-settings.json`, and then turns them off. `--touchpad` is added on a PC with a precision touchpad, which is one whose status value `Enabled` exists at `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\PrecisionTouchPad\Status`, including when that value is 0. The script ends with the version, the install folder and the config file, and says how to start Winland when it is not running. The temporary folder is removed when the script is done. When stdin is not interactive, both answers are yes. When Winland is already installed, the script asks nothing and runs `winland update`. A failure is one red line, and the terminal stays open. A declined UAC prompt says that nothing was installed.

Run as `& ([scriptblock]::Create((irm <that address>))) -Channel dev`, the script installs the newest `dev` release and then runs `winland update --channel dev`, which saves the dev channel and downloads nothing. On an installed Winland it runs `winland update --channel dev`.

`winland tweaks --off` turns Snap windows off with `SystemParametersInfo` (`SPI_SETWINARRANGING` and `SPIF_UPDATEINIFILE | SPIF_SENDCHANGE`). `--touchpad` also sets `ThreeFingerSlideEnabled` and `FourFingerSlideEnabled` to 0 under `HKCU\Software\Microsoft\Windows\CurrentVersion\PrecisionTouchPad`. 0 means those swipes do nothing. A value that was absent is recorded as absent, and uninstall removes it again rather than writing a guessed number. Winland writes no Windows setting while it is running. These two commands are the exception, and only after the install script has asked.

Saving the config or a file it sources reloads it. `misc:disable_autoreload` defaults to false, and true leaves a saved config unread until `winland reload`. Setting it back to false, with `keyword` or that reload, makes saving reload again.

On log off and shut down, Winland shows its hidden Clients and puts back what it changed only once Windows says the session is ending, not when it first asks. A shutdown that another program cancels leaves Winland running as it was. Closing Winland's console does the same cleanup on the Daemon's message loop. Windows ends the process five seconds after the console closes. A loop that does not take the cleanup within three seconds has it run on the closing thread instead, and a cleanup the loop has started is waited for until four and a half seconds have passed. Once the cleanup has put a frame, an effect, an alpha or a border back, a command or a key that is still being handled does not change it again before the process ends.

An error that nothing handles still shows every hidden Client and puts back the frames, effects, alpha, taskbar and input settings Winland changed before the process ends. When the error is on another thread than the main one, the state file is kept, so the next start rejoins the Clients to their Workspaces. A process that is killed outright cannot do this, and the next start shows what it left hidden. A clean exit keeps the state file too, as it was before the cleanup, so a restart puts every Client back where it was. The state file is written on a thread of its own, with the newest state, at most four times a second, so a process killed within that quarter second can leave a slightly older state. A hidden Client is shown again on that start when its process and window class match, even if its title changed; a shown Client rejoins its Workspace only when its title matches too.

The state file is `%USERPROFILE%\.winland\state.json`, or the file `WINLAND_STATE` names. Winland writes, replaces and deletes it with administrator rights, so an elevated Winland uses only a folder the user could already empty: one the user owns, or may delete and rename entries in. It follows `WINLAND_STATE` only to such a folder, and otherwise logs why and uses the default. A folder only administrators can write is refused, because any program the user runs can set `WINLAND_STATE`, and the file it names would be replaced and then deleted. The folder is checked where it really is, through a junction on the way, and the file and its `.tmp` are never followed when they are links: a link there is deleted itself, and nothing is read through it.
