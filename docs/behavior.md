# Behavior

How Winland behaves for the options, dispatchers and window rules it honors. What it does not honor is in [gaps.md](gaps.md), what it adds to Hyprland is in [extensions.md](extensions.md), and terms are defined in [CONTEXT.md](../CONTEXT.md).

## Config files

A line that ends with a backslash is joined to the next line, so a value that ends with a backslash, such as `$dir = C:\tools\`, takes in the line after it. Write such a path without the last backslash, or with `/`. A backslash at the end of a comment is part of the comment and joins nothing: `# path C:\dir\` leaves the next line alone, and a comment after a value that ends with a backslash warns `A backslash at the end of a comment does not join the next line.` An escaped `##` is not a comment, so a backslash after it still joins.

`source` reads another file in place of the line. A relative path is read from the config's folder, and a glob reads each file it matches in name order. A file is named the same however its path is spelled: paths are compared without case, after a relative path is joined to the config's folder. A `source` that names a file already being read, the config itself included, warns `Source '<path>' includes itself.` and is skipped. A glob passes over such a file without a warning, so `source = ./*.conf` in the config's own folder does not read the config a second time.

### Lua config

`winland.lua` in `%APPDATA%\winland` is read in place of `winland.conf` when it exists, as the pinned release reads a Lua config. Each `hl` call becomes the config line for it, which is read as the line-based config is, so the same options are honored, and a warning names the Lua line that made it and, for a required file, that file (ADR 0013).

- `hl.config(table)` sets each value whose key is not a section: `{ general = { gaps_in = 5 } }` is `general:gaps_in = 5`. `col = { active_border = ... }` names `general:col.active_border`. A gradient is `{ colors = { ... }, angle = 45 }`, a gap per side `{ top = 10, right = 0, bottom = 0, left = 4 }`, a list its items with spaces between, and a number for a color option its `0xAARRGGBB` value.
- `hl.env(name, value)` is `env = name,value`.
- `hl.exec_cmd(command, rules)` is `exec`, which runs on every load, with the rules table as its window rule block: `{ workspace = 2, float = true }` is `[workspace 2; float]`. In an `hl.on("winland.start", ...)` handler it is `exec-once`, and in `winland.shutdown` it is `exec-shutdown`. The manual's `hyprland.start` and `hyprland.shutdown` are those events.
- `hl.on(event, fn)` takes the pinned release's event names, warns with the list of them for an unknown one, and returns a subscription whose `remove()` stops the handler and whose `is_active()` says whether it was removed. An event's handlers run in the order they were added. The start and shutdown handlers run while the config loads. The others run on the Lua thread once Winland notices their event, after what was queued before it, with the event's arguments: `window.open_early` and then `window.open`, `window.close` and then `window.destroy`, `window.kill`, `window.title`, `window.class`, `window.update_rules`, `window.urgent`, `window.pin` and `window.fullscreen` get the window; `window.minimize` the window and true when it was minimized, false when it was restored; `window.active` the window and the focus reason, a bit set: 65536 when a window opens, 4 for `focuswindow`, 8 for `moveintogroup` and `moveintoorcreategroup`, 1024 for `changegroupactive` and for `movefocus` inside a group, 256 for `movefocus`, `cyclenext`, `focuscurrentorlast` and `focusurgentorlast` on one workspace (512 when the window that lost the focus is fullscreen on that workspace, not when it is maximized, and 2 when `movefocus` reaches another monitor; 2048 when `focuscurrentorlast` or `focusurgentorlast` shows another workspace on this monitor, and 2 when that workspace is on another), 2 for master `cyclenext` and for `focusmonitor`, `movetoworkspace`, `movetoworkspacesilent`, `moveoutofgroup` and `toggleswallow`, 2048 for `workspace` on the same monitor and 2 when that changes monitor, 4096 for `togglespecialworkspace`, 8192, 16384 or 32768 when the focused window closes (a tile, a floating window, or a group member), 262144 when nothing is left to focus, 1 when the pointer moves onto the window, 16 for a click on it, 128 when an activation is accepted under `misc:focus_on_activate` and for monocle `cyclenext`, and 0 when the change has no equivalent; `window.move_to_workspace` the window and the workspace; `workspace.active` the workspace a Monitor newly shows when the focus may follow that change, and the Workspace `swapactiveworkspaces` leaves on the focused Monitor. Focusing a Monitor that already shows its Workspace does not run it. `setworkspace` on a Monitor that is not focused does not run it for the Workspace that Monitor shows; when that takes the Workspace the focused Monitor was showing, it runs for the Workspace that Monitor shows next. A Monitor coming or going does not run it. `workspace.created` and `workspace.removed` get the workspace; `workspace.special_active` and `workspace.move_to_monitor` the workspace and the monitor; `monitor.added`, `monitor.removed` and `monitor.focused` the monitor; `monitor.layout_changed` nothing, when the monitors are laid out again, as in the pinned release: when one comes or goes, when one's mode, position, scale, orientation or mirror changes, and after a reload applies the monitor rules, but not for a change of work area alone; `keybinds.submap` the submap's name, `""` for the default one; `input.keyboard.key` each key the user presses or lets go, a key a bind takes too, with its XKB keycode, the time Windows stamped on it in milliseconds, and 1 when it went down or 0 when it came up, and not again for each repeat Windows sends while it is held; `config.reloaded` nothing; `config.props_refreshed` true when the refresh ran as scheduled, after a reload has read the config or when the outermost Lua call that changed the config, such as a bind's function calling `hl.config`, returns, and false when `hl.exec_scheduled_prop_refresh_immediately` ran it at once, as in the pinned release, which runs one refresh for all the changes of a call and none for a change its handlers make; and `config.unload` nothing, when a reload replaces the config's Lua and when Winland exits. No window, as `window.active` gets when nothing has the focus, and `workspace.special_active`'s workspace when the special workspace closed, are nil. A window that is gone, such as the one `window.close` gets, reads nil for every field. Each handler has 50 milliseconds. An error or the limit stops that handler, the log says so, and the other handlers still run. An event a handler's own `hl.dispatch` raises runs after that handler and is not handed to it again, which the log notes once, and handlers that raise each other's events stop 32 deep, as in the pinned release. `window.update_rules` runs for a window when it appears, and when its class, title, float, fullscreen, pin, tags, group, workspace, focus, or modal state changes. A window on a workspace that is not shown is left out. The events Winland has no equivalent for are taken and never run (see [gaps.md](gaps.md)).
- The `hl.get_*` queries answer while Winland runs, from its query replies: `get_windows` with the `monitor`, `workspace`, `floating`, `mapped` (true unless given), `class`, `title` and `tag` filters, `get_window`, `get_active_window`, `get_urgent_window`, `get_last_window`, `get_workspaces`, `get_workspace`, `get_active_workspace`, `get_active_special_workspace`, `get_last_workspace`, `get_workspace_windows`, `get_monitors` (with `{ all = true }` the disabled monitors too), `get_monitor`, `get_active_monitor`, `get_devices`, `get_monitor_at`, `get_monitor_at_cursor`, `get_cursor_pos`, `get_current_submap`, `get_config` (a gap per side is `{ top, right, bottom, left }`, an option Winland does not report is nil and why), `version` and `get_loaded_plugins`. `get_layers` is always empty, since Windows has no layer surfaces. A window takes a window selector or object, a workspace any selector a dispatcher takes, the relative forms such as `e-1` too, read on the focused monitor and found without making the workspace, and a monitor its id, name or `desc:`. A workspace's `id` is its number, nil for a named or special one, its `name` its display name and its `addressable_name` the name a selector takes, and it shows as `HL.Workspace(ADDRESS:NAME)`. A device from `get_devices` is a `pointer` or a `keyboard` with the fields of Winland's `devices` reply, under the pinned release's names, such as `default_speed`, `active_keymap` and `caps_lock`. While the config loads they find nothing: nil, an empty list, `""` for the submap. The windows, workspaces, monitors and groups they return, and those an event hands its handlers, have the pinned release's fields, read when they are read, so a field shows what a dispatch before it did. Within one call the replies are read once until a dispatch runs. An `hl.dsp` dispatcher takes such an object where it takes a selector. The urgent window, the last window, a window's `focus_history_id` and the last workspace come from the events since the config was loaded. Objects are read-only: setting a field warns. `HL.Monitor:set_workspace(selector)` shows the workspace on that monitor, read from it, moving it there first when another monitor has it, and `HL.Monitor:set_special_workspace(name)` opens that special workspace there, `""` the unnamed one, and with nil closes the one open. The focus stays on the monitor it is on, and the cursor does not move. Only when that monitor is the focused one does the focus go to the window last focused on what it shows. `HL.Group:add(window, index)` puts the window into the group at that index, or where `group:insert_after_current` puts it, and shows it there: a window on another workspace or monitor moves to the group's, a window in another group brings every member of that group in order, its own fullscreen ends, and the group's fullscreen goes to it. It warns, and changes nothing, for an index out of range, a denied group, or a lock on groups, on the group or on the window's own group. `HL.Group:remove(window or index)` takes that member out, back into the layout beside the group, and warns for a window that is not a member. A group object names the group of the window it was read from, and two are equal when they name one group.
- `hl.bind(keys, dispatcher, options)` is a `bind` line: `hl.bind("SUPER + SHIFT + Q", hl.dsp.window.close())` is `bind = SUPER SHIFT, Q, killactive`. The key string's modifier names come first, and more than one key after them is a chord, `binds` with the keys joined by `&`. Each option is its bind flag: `locked` `l`, `release` `r`, `repeating` `e`, `long_press` `o`, `mouse` `m`, `non_consuming` `n`, `transparent` `t`, `ignore_mods` `i`, `dont_inhibit` `p`, `click` `c`, `drag` `g`, `submap_universal` `u`, `auto_consuming` `a`, and `description` or `desc` `d` with its text. `device` is flag `k`, written after those flags, and its field follows the description: `+` and the names matches only those devices, `-` matches every other device, and `inclusive` left out is true. A name in that list is matched as written, in the spelling the `devices` reply uses. The bind is honored only when `non_consuming` is set. A device bind that would consume the key warns once and is not registered, because Windows names the keyboard only after the key is delivered. The bind returns a keybind object with the pinned release's fields, such as `display_key`, `handler` (`HL.Dispatcher(close)`, or the function), `modmask` and its flags. `set_enabled(false)` unbinds its keys and `set_enabled(true)` binds them again, and `remove()` or `unbind()` unbinds them for good, after which its fields read nil.
- Each `hl.dsp` call names the line dispatcher with the same effect and its argument: `hl.dsp.focus({ direction = "left" })` is `movefocus l`, `hl.dsp.focus({ workspace = 3 })` is `workspace 3`, `hl.dsp.window.move({ workspace = 3, follow = false })` is `movetoworkspacesilent 3`, `hl.dsp.window.float()` is `togglefloating`, and `hl.dsp.layout("togglesplit")` is `layoutmsg togglesplit`. A `window` selector goes where the line dispatcher takes one. `hl.dsp.window.drag()` and `hl.dsp.window.resize()` are `movewindow` and `resizewindow`, the action of a `mouse = true` bind or of the `mouse` dispatcher otherwise. `hl.dsp.group.lock({ all = true })` is `lockgroups`, `hl.dsp.group.lock_active()` is `lockactivegroup` and notes once that it is deprecated, and `hl.dsp.reload_config()` is `reload`, which a bind runs through a Lua function. A dispatcher shows as `HL.Dispatcher(name)`, and one given more arguments than it takes warns and returns nothing. A call with no line dispatcher, among them `hl.dsp.global`, `hl.dsp.window.signal` and `hl.dsp.focus({ last = true })`, or with a `window` where the line dispatcher acts only on the focused window, makes a bind that warns once that it is not honored yet and makes no line. `hl.dsp.force_idle` warns instead that it has no Windows meaning: Windows does not let a program set how long the user has been idle, and Winland reports idle to no listener.
- `hl.unbind(keys)` is `unbind = MODS, KEY`, and `hl.unbind("all")` is `unbind = all`.
- `hl.define_submap(name, [reset,] fn)` is `submap = name` (or `submap = name, reset`), the lines `fn` makes, and then the submap around it again, or `submap = reset`.
- `hl.monitor({ output, mode, position, scale, ... })` is `monitor = output, mode, position, scale`, with `preferred`, `auto` and `auto` for a field it leaves out: `hl.monitor({ output = "", mode = "preferred", position = "auto", scale = "auto" })` is `monitor = , preferred, auto, auto`. `transform`, `mirror`, `bitdepth`, `cm`, `sdr_eotf`, `sdrbrightness`, `sdrsaturation`, `vrr`, `icc`, `supports_wide_color`, `supports_hdr`, `sdr_min_luminance`, `sdr_max_luminance`, `min_luminance`, `max_luminance` and `max_avg_luminance` follow as options, such as `, transform, 1`. `disabled = true` is `monitor = output, disable`, and `reserved` or `reserved_area`, a number or `{ top, right, bottom, left }`, is a second line, `monitor = output, addreserved, top, bottom, left, right`.
- `hl.window_rule({ name, enabled, match = { ... }, effect = value, ... })` is a `windowrulev2` line for each effect, with the matches after it: `hl.window_rule({ match = { class = "^kitty$", float = true }, border_size = 0 })` is `windowrulev2 = border_size 0, class:^kitty$, float:true`. An effect that is true has no value, a false `float` is `tile` and a false `tile` is `float`, another false effect is `effect false`, and a list is its items with spaces between. The match and effect names are the line's, so Winland's own, such as the `ignore` effect and the `exe` and `aumid` matches, work too, and one the line does not take warns as it does there. A rule that is not `enabled` is still a line, with `ruleon:0`, so it can be turned on later. The line also carries `ruleid`, which names that rule. It returns a rule object: `set_enabled(bool)` turns every effect of that rule off or on and matches its dynamic effects again on the windows already open, `is_enabled()` says whether it is on, and two objects are equal when they are the same rule. A call with the `name` of an earlier rule adds to that rule: a match it names replaces that match, its effects are added, and its `enabled` replaces the rule's (a call that leaves `enabled` out turns the rule on). `hl.layer_rule` makes `layerrule` lines the same way, which warn as that keyword does. The object it returns only warns: Windows has no layer surfaces, so `set_enabled` and `is_enabled` change nothing, and naming that rule again changes nothing.
- `hl.workspace_rule({ workspace, ... })` is `workspace = workspace, field:value, ...`: `monitor`, `default`, `persistent`, `gaps_in` and `gaps_out` (`gapsin`, `gapsout`), `float_gaps`, `border_size` (`bordersize`), `no_border`, `no_rounding` and `no_shadow` (the opposite of `border`, `rounding` and `shadow`), `decorate`, `on_created_empty` (`on-created-empty`), `default_name` (`defaultName`), `layout`, `animation`, and each of `layout_opts` as `layoutopt:key:value`. A gap is a number or `{ top, right, bottom, left }`. A rule that is not `enabled` is still a line, with `ruleon:0`. The line carries `ruleid`. It returns a rule object with `set_enabled` and `is_enabled`, as `hl.window_rule` does. `set_enabled` stamps the rule onto the workspaces already there and matches window rules again. A second call for a workspace that already has an enabled rule merges into that rule and returns it, and does not change whether it is enabled. A call while that rule is off adds a new one.
- `hl.curve(name, { type = "bezier", points = { { x0, y0 }, { x1, y1 } } })` is `bezier = name, x0, y0, x1, y1`. A `spring` curve takes `mass`, `stiffness` and `damping`, or the older `dampening`, each above 0.5, and is `spring = name, stiffness, damping, mass` (see [extensions.md](extensions.md)).
- `hl.animation({ leaf, enabled, speed, bezier, style })` is `animation = leaf, 1, speed, bezier[, style]`, and `animation = leaf, 0` when `enabled` is false. With a `spring` in place of a bezier the curve is `spring:name`, as the pinned release names it.
- `hl.gesture({ fingers, direction, action, ... })` is `gesture = fingers, direction, action`: `mods` is `mod:MODS` and `scale` is `scale:S` before the action, a scale from 0.1 to 10 or from -10 to -0.1, which turns the gesture around, `disable_inhibit = true` is `gesturep`, `scroll_move` is `scrollMove`, `cursor_zoom` is `cursorZoom`, and `workspace_name` for `special`, `mode` for `float` and `fullscreen`, and `zoom_level` and `mode` for `cursorZoom` follow the action. An action that is a Lua function, or a table of `start`, `update` and `finish` functions, is `gesture = fingers, direction, luafunction, N` (see [extensions.md](extensions.md)). A table runs `start` when the swipe takes the gesture, `update` for that movement and each one after it, and `finish` when the fingers lift, each with one table: `phase` (`start`, `update` or `end`), `direction` (`LEFT`, `RIGHT`, `UP` or `DOWN` as the fingers went, and for `end` the configured one, such as `HORIZONTAL`), `type` (`swipe`) and `time_ms`, with `fingers` and `delta` (`{ x, y }`, the movement of that update) for `start` and `update`, and `cancelled` for `end`. Each call may run for 0.05 seconds. A single function runs once when the fingers lift, with nothing, for 0.1 seconds. A table field that is not a function, or a table with none of them, warns and makes no gesture. A swipe that a command of the Lua itself makes runs the functions before that command returns, as in the pinned release.
- `hl.device({ name, field = value, ... })` is `device[name]:field = value` for each field, with each space in the name a `-`. `tags`, `sensitivity`, `scroll_factor` and `rotation` are kept. A bind's device list matches a tag as it matches the device's name, in that spelling. A consuming bind that lists a tag is refused the same way, and is not registered. Any other field warns as that per-device option does.
- `hl.permission(binary, type, mode)`, or a table of them, is `permission = binary, type, mode`, which warns as that keyword does.
- A comma in a bind's description, a bind's device name, a window rule's match or value, a monitor's name, mirror or icc path, a workspace rule's selector, monitor, command, display name, layout, animation or layout option, a gesture's workspace name or mods, a curve or spring name, an animation's style or curve, an env name or value, or an exec rule's effect is kept: the line the Lua writes holds a private-use character in its place, which the parser turns back into a comma after it splits the line. A permission's binary is written the same way, and that keyword is still unsupported, so the comma is not applied. A device line is not split, so a comma in a device's text stays as written, and a field that is not honored still warns. A comma in a monitor mode, position, scale or number, a workspace rule's flag or size, a gesture's mode or zoom, an animation's leaf, or a permission's type or mode warns that it is not honored yet and is left out.
- A bind whose dispatcher is a Lua function, `hl.bind("SUPER + X", function() ... end)`, is `bind = SUPER, X, luafunction, N`, and the function runs when the keys are pressed (see [extensions.md](extensions.md)).
- `hl.dispatch(dispatcher)` runs an `hl.dsp` dispatcher and returns `{ ok = true, pass_event = false }`, or `{ ok = false, error = message }` with the error reported. Called while the config loads, it runs once Winland runs. Given a Lua function, it calls it and returns what it returns, or success.
- `hl.layout.register(name, { recalculate = fn, layout_msg = fn })` registers a custom layout as `lua:name`, and is the line `lualayout = lua:name`, so `general:layout` and a workspace rule's `layout` select it by that name. A name already registered, an empty one, or a table with no `recalculate` warns and registers nothing. `recalculate(ctx)` gets the tiling area, `ctx.area`, a box `{ x, y, w, h }`, and the tiled windows in the layout's order, `ctx.targets`, each a target with its `index`, its `window` and its current `box`, and places each with `target:place(box)` or `target:set_box(box)`, which are the same in the pinned release. Winland takes gaps and the border off the box as in its other layouts. `ctx:grid_cell(i, cols[, rows])`, `ctx:column(i, n)`, `ctx:row(i, n)` and `ctx:split(box, side, ratio)` give the pinned release's boxes. A new window joins the end of the order, `movewindow` moves a window one place back or on in it, and `swapwindow` exchanges two. `layoutmsg` calls `layout_msg(ctx, message)` and then `recalculate`. The layout runs on the Lua thread, never inside Winland's handling of an input, with the pinned release's 50 milliseconds for each call, after the change it answers (ADR 0013): until it answers, the windows keep their boxes, and a window with none yet makes every window take a cell of an even grid, as a layout whose `recalculate` fails does. The focus moves between its windows by where they are.
- `hl.timer(fn, { timeout = ms, type = "repeat" | "oneshot" })` calls `fn` after `timeout` milliseconds, again and again with `repeat`, and returns the timer: `set_enabled(false)` stops it, `set_enabled(true)` starts it again, `set_timeout(ms)` starts it with a new timeout, and `is_enabled()` says whether it is running. A repeating timer repeats at the timeout it was made with, as in the pinned release, and a one-shot timer that fired is gone. A reload stops the timers of the config it replaces.
- `hl.notification.create({ text, duration, icon, color, font_size })` shows a notification at once and returns it. `duration`, or `timeout`, or `time`, is the lifetime in milliseconds, and one below 1 is shown for 1. `icon` is a name (`warning`, `warn`, `info`, `hint`, `error`, `err`, `confused`, `question`, `ok`, `none`) or a number 0 to 6, and none when left out. `color` is a number or a color string, and 0, the default, takes the icon's color. `font_size` defaults to 13. `hl.notification.get()` lists the ones on screen, oldest first. An `HL.Notification` has `pause`, `resume`, `set_paused`, `is_paused`, `set_text`, `set_timeout`, `set_color`, `set_icon`, `set_font_size`, `dismiss`, `get_text`, `get_timeout`, `get_color`, `get_icon`, `get_font_size`, `get_elapsed`, `get_elapsed_since_creation` and `is_alive`. Pausing stops its timeout, and the time it has already spent stays until the last pause ends. Two objects that pause the same notification both have to resume it. Collecting a paused one resumes its pause. It shows as `HL.Notification(0xID)`, or `HL.Notification(expired)` once it is gone, and two that are gone compare equal. A bad argument warns and the call returns nil. A create while the config is first read exists immediately and is shown once Winland runs. `get` during that read lists only the ones created during it. A reload's config, while it is read, does not see the ones already on screen; a bind or an eval after that Lua starts does.
- `hl.is_key_down(key)` answers whether the user holds a key, named as a keysym, such as `"a"` or `"Super_L"`, or given as its XKB keycode, as the pinned release reads its input state. It counts a key a bind swallows. A name that is no key warns `Unknown keysym: "key"`, with `did you mean "Return"?` for `Enter`, and a keycode below 8 warns `hl.is_key_down: invalid keycode N`. While the config is first read every key is up.
- `hl.plugin.load(path)` is `plugin = path`. An empty path warns `hl.plugin.load: path must not be empty`.
- `hl.exec_scheduled_prop_refresh_immediately()` runs the prop refresh a change from Lua scheduled, if any, at once, so `config.props_refreshed` gets false. Winland applies each change as it is made, so only the event moves. `hl.clear_crashed_lockscreen()` does nothing, since Winland draws no lock screen.
- While Winland runs, an `hl` call that sets something, such as `hl.config` in an eval, is sent as a `keyword`, and its warnings and errors go to the log, or to the eval's reply.

The Lua is Lua 5.4. It has no `io`, `debug`, `dofile` or `loadfile`, its `os` has only `time`, `clock`, `date`, `getenv` and `difftime`, and `load` takes text, not compiled chunks. `require("a.b")` reads `a\b.lua` or `a\b\init.lua` from the config's folder. As in the pinned release, a name that starts with `/`, `./`, `../` or `~/` is a path: from the config's folder, or the home folder for `~`, it reads that file, or the file with `.lua` added, or the `init.lua` in that folder. The same with a backslash, and a path that starts with a drive such as `C:\`, are paths too. A path with a wildcard (`*`, `?` or `[...]`) requires each file it matches, in name order, and gives a table of what each returned, `true` for a file that returned nothing, and `require` fails when it matches no file. Every file `require` reads or lists goes through the same reader as the config, so it counts toward the config's trust (ADR 0007), and a change to it reloads the config. A module that is not found is an error. A required file that fails as it runs warns where it failed and gives an empty table, and the config runs on, as in the pinned release. Any other error stops the config at that line and warns with the error. The lines made before it stay. The config's Lua keeps running after it loads, on a thread of its own, so it never runs inside Winland's handling of a key or a window: a bind's function, a timer, an event handler and an eval wait their turn there. Each has the pinned release's limit of processor time, after which it is stopped the same way and the log says so: 1.5 seconds for the config as it loads, 100 milliseconds for a bind's function and a dispatch, 50 for a timer and an event handler, and 250 for an eval. `print` writes to the log, or to a `repl` reply.

`winlandctl eval <lua>` runs Lua in the config's Lua and replies `ok`, or the errors. Code that is an expression is run as `return <code>`. Code that does not load replies `error: 3` and the error, the status of the first load as in the pinned release. `print()` with nothing to print prints nothing. A batch can hold `eval` and `repl` commands. `winlandctl repl <lua>` replies with what the code printed and returned instead, as `tostring` shows it. With a Lua config, `winlandctl dispatch` with a call in its argument is `eval 'hl.dispatch(...)'`, as in the pinned release, and `winlandctl dispatch workspace 2` still runs the line dispatcher. Without a Lua config, `eval` and `repl` reply `eval is only supported with a Lua config`.

## Layout

`master:center_ignores_reserved` defaults to false. True centers a centered master on its Monitor rather than on the work area, as in the pinned release. The strips left and right of the work area, such as a taskbar or an `addreserved` rule, count toward the width the master is centered in and its share of it, and the side stacks keep to the work area.

`dwindle:special_scale_factor`, `master:special_scale_factor` and `misc:animate_mouse_windowdragging` are read and change nothing, as in the pinned release, which defines them and never reads them.

`general:layout` is honored for `dwindle`, `master`, `monocle`, and `scrolling`, and for `lua:NAME`, a custom layout a Lua config registers (see [Lua config](#lua-config)). Any other value warns with its line number. Dwindle still runs when the named layout is not available, and for a `lua:NAME` nothing registered, without a warning, as in the pinned release. When monocle's shown tile closes or is minimized, the tile focused most recently is shown in its place, as in the pinned release, and otherwise the next one.

A tiled Client's minimum size moves a dwindle split or a master stack where the minimums fit, and the neighbour takes what remains. Each side keeps at least the share the smallest split ratio leaves it in dwindle, and a fifth of an even share in a master stack. Where they do not fit, the side that needs more takes all of that but the other side's share in dwindle, and a master stack keeps its even split, so no tile leaves the Monitor. A window cannot be smaller than its minimum, so a window below it grows around the middle of its tile and moves to stay inside the work area, over its neighbours, as the pinned release places a window with `misc:size_limits_tiled`. A minimum larger than the work area starts at its top left corner.

`misc:size_limits_tiled` defaults to false. A `min_size` or `max_size` window rule then holds a Client only while it floats, as in the pinned release, and a tiled Client keeps the window's own minimum, which Windows enforces whatever the option says. True makes the rule's minimum hold a tiled Client too, as above. A maximum that cannot fill the tile floats the Client either way, the rule's or the window's own, as in the pinned release. When the window changes its own limits, a rule's minimum or maximum still wins over them.

A window whose maximum size cannot fill the tile it would get floats instead of tiling. In master that tile is a share of the whole Monitor: a master needs the master fraction of its width and all of its height, and a slave needs the rest of the width and the height divided by one less than the number of tiles. This also holds when the Client is toggled back to tiled or dropped by a drag. A window that opens this way floats at the size of the tile it would have taken, kept inside its limits, in the middle of the work area, as in the pinned release. In dwindle that tile is half the tile it would split, or the whole Monitor on an empty Workspace. In master it is the whole Monitor on an empty Workspace, the master's size with `new_status = master`, half the Monitor beside a lone master, or a slave's share.

`layout:single_window_aspect_ratio`, such as `4 3`, pads the only tiled Client of a Workspace to that width to height in every Layout, as in the pinned release. The padding is the part of the work area outside that ratio, split evenly between two sides, and it is taken off the Client's tile. `0 0`, the default, turns it off. `layout:single_window_aspect_ratio_tolerance` defaults to 0.1 and leaves the tile alone when half the padding is not more than that share of the work area's height or width. A maximized or fullscreen Client fills its area as before.

## Decoration

`decoration:rounding` is the corner radius in logical pixels and defaults to 0, which draws square corners. A negative value is ignored. `decoration:rounding_power` defaults to 2 and is clamped to 1 through 10: 1 cuts a straight corner, 2 a circle, and a larger value is squarer. The radius drawn is `rounding * rounding_power / 2`, multiplied by the scale of the Client's Monitor. A circle of radius 8 or 4 uses DWM's round or small round corner preference, which DWM scales with the window's DPI. Any other radius or power is cut from the window as a window region inside the visible frame, following `|x|^p + |y|^p = r^p` at each corner, and is cut again when the window changes size. A radius larger than half the shorter side is cut to that half. A Client in fullscreen mode 2 and a Client on a Workspace with `rounding:0` draw square corners. A window that already has a region of its own keeps it, and its corners are not cut.

`decoration:blur:enabled` defaults to true and gives every Client DWM's acrylic backdrop (`DWMSBT_TRANSIENTWINDOW`). False gives it no backdrop (`DWMSBT_NONE`). A window or a Windows build that refuses the backdrop is left as it is. DWM's backdrop cannot be tuned, so only `decoration:blur:xray` changes how a Client blurs.

With `decoration:blur:enabled` and `decoration:blur:xray` on (it defaults to false), a Client that Winland makes translucent (an alpha under 255 from `active_opacity`, `inactive_opacity`, `fullscreen_opacity`, an `opacity` rule or dimming) shows the blurred wallpaper under it, as the pinned release shows its precomputed blur under a window: the wallpaper alone, with no window in it, not what is really behind the Client. Winland reads each monitor's wallpaper with the shell's `IDesktopWallpaper` (the picture, the fit mode, `Center`, `Tile`, `Stretch`, `Fit`, `Fill` or `Span`, and the background color, which a solid color uses), fits it to the monitor as Windows does and blurs it once on a worker thread with the pinned release's dual Kawase blur, then draws it in a click-through layered window kept just below the Client in the z-order, cut to the Client's frame and rounded like the window, the way the drawn shadow is stacked. Until the first blur finishes, which takes about a second a monitor, the Client has no backdrop. The picture is made again within a second of a change of the wallpaper (a slideshow included), of the monitor layout, or of the blur options. A Client with a backdrop of this kind has DWM's backdrop turned off (`DWMSBT_NONE`) so the two do not stack. A Client that is fully opaque has none and keeps DWM's backdrop, as does every Client when `xray` is off. The wallpaper is only read: Winland never sets it. The options the blur reads are the pinned release's, with its defaults and ranges: `size` (8, 0 to 100) is the distance of the filter taps in pixels, `passes` (1, 0 to 10, used as 1 to 8) is how many times the picture is halved and doubled again, `contrast` (0.8916, 0 to 2) and `brightness` (1, 0 to 2) are applied to the wallpaper before the blur (brightness above 1) and after it (brightness below 1), `vibrancy` (0.1696, 0 to 1) and `vibrancy_darkness` (0, 0 to 1) raise the saturation of the colors in each down pass, and `noise` (0.0117, 0 to 1) adds a hash of the pixel's place. `ignore_opacity` (default true) draws the backdrop fully opaque under the translucent window, as the pinned release does; false gives it the window's own alpha. The backdrop fades with a window that a motion fades. These options change nothing while `xray` is off, and `decoration:blur:special`, `popups`, `input_methods`, `new_optimizations` and `variant` are not honored. `decoration:shadow:enabled` defaults to true and leaves DWM's shadow alone. False sets DWM's non-client rendering policy to disabled (`DWMNCRP_DISABLED`), so DWM draws no shadow and none of the rest of the window frame it draws.

DWM's shadow cannot be tuned, so Winland draws the pinned release's shadow itself once the config sets any of `decoration:shadow:range`, `render_power`, `sharp`, `color`, `color_inactive`, `offset` or `scale`, and then turns DWM's shadow off on every Client as `enabled = false` does. A config that sets none of them keeps DWM's shadow, as before: drawing the pinned release's default shadow would turn off the frame DWM draws on every window that did not ask for it. The drawn shadow follows the pinned release's shader. Its box is the window and its border grown by `range` (default 4) logical pixels, scaled about its middle by `scale` (default 1, from 0.05 to 2, drawn at no more than 1) and moved by `offset` (default `0 0`, each from -250 to 250), all multiplied by the Monitor's scale. Its corners follow the border's outer corners and `rounding_power`. It is full inside the box and falls to nothing over `range` pixels at the edges and round the corners, as `(distance / range) ^ render_power`, where `render_power` is 1 to 4 and defaults to 3. `sharp`, default false, draws the box flat in its first color with no falloff. `color`, default `0xee1a1a1a`, is the focused Client's and `color_inactive` the others', falling back to `color`, and each takes a gradient with an angle as a border color does. The shadow takes the window's opacity and is cut away under the window, inside its corners. It is click-through layered windows kept just below the Client in the z-order, around the window and not under it, and they follow the window as the border does. `decoration:border_part_of_window`, default true, is the only thing that decides whether the border is inside that box: false grows the box from the window alone, so the border is drawn over the shadow and the corners follow the window's own. It changes nothing else, as in the pinned release: the glow, the hit area for a click or a resize, and the rounding are the same either way. It applies to the shadow Winland draws, so it has no effect while DWM's own shadow is in use. A fullscreen, minimized or hidden Client, one with `decorate 0`, and a shadow whose colors are all clear have none. The `fadeShadow` animation fades the shadow from its old colors to its new ones when focus moves, mixing them in OkLab, and the `shadowangle` animation, off by default, turns a gradient shadow once round when its window opens and each time it is focused, and with the `loop` style keeps turning, as in the pinned release.

`no_shadow`, from a window rule or `setprop`, and `shadow:0` on a workspace rule turn the shadow off for that Client: Winland draws none, and DWM's is turned off as `enabled = false` does.

`decoration:glow:enabled` defaults to false. True draws the pinned release's inner glow inside each Client's edge, following its shader: it is strongest at the window's edge and falls to nothing `decoration:glow:range` (default 10, from 0 to 100) logical pixels in, times the Monitor's scale, as `(1 - distance / range) ^ render_power`, where `decoration:glow:render_power` is 1 to 4 and defaults to 3. The distance to the edges is smoothed where two edges meet, so the glow rounds the corners, and it is cut to the window's corners less a pixel. `decoration:glow:color`, default `0xee33ccff`, is the focused Client's and `decoration:glow:color_inactive` the others', falling back to `color`, and each takes a gradient with an angle as a border color does. The glow takes the window's opacity. It is four click-through layered strips along the inside of the window's edge, kept just above the Client in the z-order like the border, so the middle of the window is not covered and a window raised over the Client covers its glow too. A range of 0, a fullscreen, minimized or hidden Client, one with `decorate 0` or `no_glow`, and a glow whose colors are all clear draw none. The `fadeGlow` animation fades the glow to its new colors when focus moves, and the `glowangle` animation, off by default, turns a gradient glow as `shadowangle` turns the shadow.

The backdrop, the rendering policy and the region are put back when the window stops being a Client and on a clean exit. After a crash the next start removes each region Winland had cut, so it is not taken as the window's own region. The backdrop goes back to the type the window had, or to the system choice when that cannot be read. The rendering policy goes back to following the window style.

Winland draws each Client's border itself, outside the window's frame, as the pinned release does: `general:border_size` pixels wide (or the window's own `border_size`), in `general:col.active_border` on the focused Client and `general:col.inactive_border` on the others. A border color is a color, written as `rgba()`, `rgb()`, or `0xAARRGGBB`, or a gradient of up to ten of them followed by an angle such as `45deg`. A gradient runs across the border's whole box at that angle and blends in the OkLab space, as the pinned release's shader does. The border's inner corners follow the window's rounding and its outer corners are rounded to match, less a little for a corner flatter than a circle; a square window has a square border. The border takes the window's opacity. A fullscreen Client, a minimized or hidden one, and one with `decorate 0` have no border, and `border_size 0` draws none. DWM's own one-pixel border is turned off while Winland runs. The border is four click-through windows kept just above the Client in the z-order, so a window raised over the Client covers its border too, and they follow the window as it moves, animates or is dragged. A Group's border, `group:col.border_*`, and the border of a window that may not be grouped, `general:col.nogroup_border*`, take gradients too. The `borderangle` animation, off by default, turns a gradient border once round when its window opens and each time a window is focused, and with the `loop` style keeps turning, as in the pinned release.

`decoration:active_opacity`, `decoration:inactive_opacity` and `decoration:fullscreen_opacity` are fractions from 0 to 1 and default to 1. A value outside that range is clamped. A Client in fullscreen mode 2 uses `fullscreen_opacity`. A maximized Client uses the active or inactive fraction, and so does every other Client.

An `opacity` window rule supplies up to three fractions: active, inactive and fullscreen. One fraction is used for all three. Two fractions set active and inactive and leave fullscreen at 1, which then multiplies the configured fullscreen fraction. Each fraction multiplies the configured fraction unless the next token is `override`, which uses the rule's fraction alone. The last matching `opacity` rule wins. `opaque` forces the fraction to 1, and a trailing `0` turns that off. The last matching `opaque` rule wins.

`decoration:dim_inactive` defaults to false and `decoration:dim_strength` defaults to 0.5. When dimming is on, an inactive Client's fraction is multiplied by `1 - dim_strength`. Inactive windows are dimmed by tinting them toward black. That tint cannot be drawn on a window here, so dimming lowers the window's alpha instead. The `fadeDim` animation eases that change, apart from the `fadeSwitch` animation that eases the opacity. `decoration:dim_modal` defaults to true. A Client shadowed by a modal moves that dim halfway toward 1 before the alpha is taken. Windows disables a window while a modal dialog it owns is open, so a disabled Client that owns another Client is shadowed by a modal, and that owned Client is modal. With `general:modal_parent_blocking`, default true, a shadowed Client takes no focus, as with `no_focus`: a click or `focuswindow` leaves focus where it is, and the pointer passes over it. A disabled Client that owns no Client is not shadowed. `decoration:dim_special` defaults to 0.2 and multiplies the alpha of Clients on a Monitor whose special workspace is open, except the Clients on that special workspace. A window with the `dim_around` property, from a window rule or `setprop`, dims everything under it on its Monitor by `decoration:dim_around`, default 0.4, times its own opacity, as in the pinned release. Winland draws a black, click-through layer over that Monitor and keeps it just below the window in the z-order, so a window raised above it is not dimmed. Clicks pass through the layer to the windows under it.

An alpha below 255 adds `WS_EX_LAYERED` and sets the window's alpha. The window's previous extended style is restored when it stops being a Client, on a clean exit, and after a crash for every window this program layered. A window that was already layered is left alone. A window that refuses the layered style is skipped.

## Shell windows

The taskbar, the Start menu, Search and the other flyouts the shell opens from the taskbar are left unmanaged, so opening Start does not split the screen. Winland knows the taskbars by their window classes `Shell_TrayWnd` and `Shell_SecondaryTrayWnd`, and the flyouts by their processes `StartMenuExperienceHost.exe`, `SearchHost.exe`, `SearchApp.exe`, `ShellExperienceHost.exe` and `ShellHost.exe`. A window rule that forces a window to be adopted, such as `float`, `tile` or `workspace` on `class:.*`, still adopts a flyout it matches.

While Winland runs, the taskbars are hidden and set to auto-hide, so the work area takes in the strip they reserved. They are hidden again when the shell shows or recreates them. A clean exit shows them with the state they had before, and so does the next start after a crash.

A layered window that input passes through, such as a screen overlay an application draws over the desktop, is left unmanaged too: it cannot be clicked or focused, and the pinned release draws such surfaces as layers it never tiles. A window rule that forces adoption still adopts it.

## Window rule matches

A window rule's `class`, `initialClass`, `title`, `initialTitle`, `exe` and `aumid` patterns are regular expressions that must match the whole field, as in the pinned release, so `title:Notes` does not match a window titled `Release Notes`. `initialClass` and `initial_class` match the class the window had when it appeared, including an empty one, and `class` matches the class it has now. `initialTitle` and `initial_title` match the title the window had when it appeared, and `title` matches the title it has now. When the class or the title changes, a rule that matches on `class` or `title` is read again, and its opacity, properties, tags, idle inhibit and focus effects follow. Effects that apply only as the window appears, such as `float` and `workspace`, stay as they were. A pattern that starts with `negative:` matches when the rest of the pattern does not, so `class:negative:kitty` matches every class but `kitty`. A pattern that is not a valid regular expression warns with its line number and the rule is skipped. `misc:swallow_regex` and `misc:swallow_exception_regex` also match the whole field, and take no `negative:` prefix, as in the pinned release.

A `windowrulev2` can also match on a window's state: `float`, `fullscreen`, `pin`, `focus` and `group` take 1 or 0, `fullscreen_state_internal` and `fullscreen_state_client` take a mode, and `workspace` takes a workspace selector such as `w[tv1]` or `n[s:web]`. `modal` takes 1 or 0 and matches a window whose owner Windows has disabled, as a modal dialog's owner is. The older names `floating`, `pinned` and `onworkspace` are read too. As in the pinned release, the property effects of every rule are matched again whenever a window's state changes, so `border_size 0, float:0, workspace:w[tv1]` removes the border only while the window is the single tile on its Workspace, and the Workspace is laid out again when a border changes. The other effects are applied once, when the window opens. Then, as in the pinned release, the rules are matched with the tags the rules give the window and the Workspace it opens on, while it is not yet floating, focused, pinned, fullscreen or in a Group, so `float, tag:dialog` and `float, workspace:name:scratch` float a window as it opens. Where the window opens is still decided by the first match. A `border_color` rule with `focus:1` and only an inactive color gives that color to the active border, and one with `focus:0` and only an active color gives it to the inactive border, as in the pinned release.

## Window properties

`getprop WINDOW PROP` answers a window property, and `setprop WINDOW PROP VALUE` sets it, as the pinned release's `getprop` request and set_prop dispatcher do. The properties, their kinds and the forms of the replies are the pinned release's: `j/getprop` answers a one-member JSON object, such as `{"opacity": 0.5}`. A property is what `setprop` set, else what a window rule or workspace rule gives, else the config's value. `getprop` with too few arguments answers `not enough args`, for no window `window not found`, and for an unknown property `prop not found`.

A bool takes `toggle`, which flips what is set, or false when nothing is, and otherwise is true for `1` or text starting with `true`, `yes` or `on`. A number takes `relative N` to add to its value. `unset` drops what `setprop` set. `min_size` and `max_size` take two expressions over the window's size and place, as a `size` rule does, and the window is held to them at once. `opacity`, `opacity_inactive` and `opacity_fullscreen` take a fraction, and their `_override` flags a number, where `true` is 1. A border color takes one color, or with more than one token the colors and angle after the first, as in the pinned release, and `-1` is no color. A value that does not parse changes nothing.

These change the window: the opacities and `opaque`, `decorate`, which with 0 takes away the border, shadow, glow and a Group's tab bar, `no_focus`, `stay_focused`, `focus_on_activate`, which wins over `misc:focus_on_activate` for that window, `min_size`, `max_size`, `no_max_size`, `idle_inhibit`, `active_border_color` and `inactive_border_color`, `border_size`, `rounding`, `rounding_power`, `no_shadow`, `no_glow`, `no_wobble`, `no_blur`, which takes both the system backdrop and the `xray` backdrop off, `xray`, which turns `decoration:blur:xray` on or off for that window while `decoration:blur:enabled` is on, `no_dim`, which drops the inactive dim and keeps the modal and special workspace dims, `no_anim`, which moves, fades and recolors the window at once and draws its border, shadow and glow without turning or fading, and `no_follow_mouse`, which keeps the pointer from focusing the window when it moves onto it, though a click or a refocus after another window closes still does. `scroll_mouse` and `scroll_touchpad` replace the scroll factors over that window, described under input. `animation` sets the style the window opens and closes with (see [Animations](#animations)). `no_vrr` turns variable refresh rate off for the window's program. `sync_fullscreen` is honored, as [Fullscreen](#fullscreen) describes. The others are Windows limits, kept and reported; see [gaps.md](gaps.md).

`no_vrr` turns variable refresh rate off for that window's executable in the account's graphics settings, the `VRROptimizeEnable` flag of `HKCU\Software\Microsoft\DirectX\UserGpuPreferences`, and leaves every other flag in that value, such as `GpuPreference`, as it was. It is turned off while any window of that executable has the property, from a rule or `setprop`, and the value from before is put back when none does, when those windows close, and on a clean exit. The same value is put back on the next start after a run that did not exit cleanly. Windows applies the flag when the program next creates its swap chain, which is usually the next time it starts, where the pinned release turns the display's adaptive sync off at once and only while that window is fullscreen and the monitor's variable refresh rate mode is 1, 2 or 3. A window whose executable path cannot be read is left unchanged. `misc:vrr` of 0 or 1, or `off` or `on`, sets the same flag on the account-wide value `DirectXUserGlobalSettings` while Winland runs, and puts the previous value back when a loaded config does not set the option, and on a clean exit. It is left alone when the option is absent. 2 and 3, `fullscreen` and `fullscreen_game`, warn and change nothing: they follow whether a window is fullscreen, and 3 also a content type Windows does not report. A monitor rule's `vrr` warns and is not honored, since the graphics setting is not per display. Winland's `no_vrr` is broader than the pinned release because Windows cannot toggle a display per frame.

A window rule sets a property with the effect of the same name, as in the pinned release: `border_size`, `rounding`, `rounding_power`, `border_color`, `animation`, `scroll_mouse`, `scroll_touchpad`, and the bool properties such as `no_blur` or `decorate 0`. A bool effect with no value is true. `border_color` takes two colors for the active and inactive border, or a gradient: the colors up to the first angle are the active border and the rest the inactive one. A value that does not parse warns and the rule is skipped. A window's own `border_size`, from a rule or `setprop`, replaces the configured and workspace border around its tile, multiplied by its Monitor's scale like the configured one.

## Exec rule blocks

A rule block on `exec`, `exec-once`, `execr`, `execr-once`, `exec-shutdown`, or the `exec` and `execr` dispatchers applies to the first window mapped by that process or a child of it. Every effect a window rule honors is honored there too, including `move`, `size`, `center`, `monitor` and `no_close_for`. Any other effect warns and is skipped. The command still launches. An unclosed rule block warns and does not launch. A known effect with a bad argument warns and does not launch.

## Launching

`exec`, `exec-once` and `exec-shutdown` run the command through `cmd.exe /d /s /c "<command>"`, so cmd syntax such as `&&` and redirection works and every quote in the command is kept as written. `execr` and `execr-once` start the command line as a program, with no shell.

A console program started by `execr` gets a console window of its own. One started through `exec` shares cmd's console, which has no window, the way a program started by `sh -c` has no terminal, so a background tool stays out of sight and its redirections and pipes work. To see a console program, start it with `execr` or inside a terminal, for example `exec = wt pwsh`.

`misc:initial_workspace_tracking` defaults to 1. A program `exec`, `execr`, a config `exec` line or a workspace rule's `on-created-empty` starts opens its window on the Workspace it was started on, without switching to it, as in the pinned release. That is the special workspace the focused Monitor shows, or its Workspace, and for `on-created-empty` the new Workspace. `exec-once` and `exec-shutdown` start programs without it. Every process the program starts holds the same Workspace. With 1 the first window that opens uses it up, and it lapses after `misc:initial_workspace_token_timeout` seconds, 10 by default. With 2 every window of those processes opens where the first one is now, until the first one closes. 0 turns it off. A window rule's `workspace` wins over it, and a window that comes back after a restart keeps its own Workspace.

## Window placement

A new floating Client opens at the size it asked for, centered in the floating work area of its Monitor: the work area less `general:float_gaps`. One that has an owner, the window Windows names as its owner, such as an application's dialog, opens over the middle of that owner when the owner is a Client, as the pinned release opens a window with a parent. A window that reports no size opens at 640 by 400. A tiled Client is placed by its Layout. `togglefloating` floats a tiled Client around the center of its tile, at the size it last had while floating, or at the size it asked for when it has not floated yet, in every Layout.

`misc:new_float_force_onscreen` keeps a Client that opens floating on screen, also one a `move` rule places, and defaults to 2. `misc:float_force_onscreen` does the same when a floating Client starts floating, moves, is dragged or resizes, and defaults to 0. Both are measured against the floating work area, as in the pinned release. `misc:float_force_onscreen` counts the border around the frame, and `misc:new_float_force_onscreen` does not, because the pinned release applies it before the border is known. 0 leaves the Client where it is put. 1 acts only on a Client that would lie wholly outside the area, and moves it until its middle is on the nearest edge. 2 moves it, without resizing it, to lie wholly inside, so a Client larger than the area lines up with its right and bottom edges.

A Client that comes back after a restart keeps the rectangle it had, whether it floated, its pin and its fullscreen modes, as the recovery file recorded them, before the window rules. A recovery file written before these were recorded leaves them to the rules.

A Client whose application hides it, without minimizing it, stops being a Client, as an unmapped window does in the pinned release, and it is adopted again when the application shows it. The windows Winland hides itself, for a Workspace it does not show, stay Clients.

`size` and `move` take two expressions, x then y, split at the first whitespace, so an expression cannot contain a space. An expression is numbers, `+ - * / ^`, parentheses, a unary minus, the constants `_pi` and `_e`, the one-argument functions `abs`, `sqrt`, `sign`, `rint`, `exp`, `ln`, `log`, `log2`, `log10`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `sinh`, `cosh` and `tanh`, and the variables `monitor_w`, `monitor_h`, `window_x`, `window_y`, `window_w`, `window_h`, `cursor_x` and `cursor_y`. Positions are local to the Monitor the Client opens on. Numbers are physical pixels, like `min_size`. A `min_size` or `max_size` rule also takes two expressions, read when the window opens, as in the pinned release. A size below 1 leaves that limit unset. A rule that is not two expressions, or uses a name that is not listed, warns with its line number and is skipped. So does an expression nested more than 256 levels deep in parentheses, signs, exponents and functions. A `%` is not part of an expression, so `50%` warns. A value that cannot be computed, such as a division by zero, leaves the Client where it would open without the rule.

`persistent_size` keeps a floating window's size, as in the pinned release. When a floating window with the rule closes, its size is kept for its initial class and title, and a window of that class and title that opens floating with the rule opens at that size. The sizes last until Winland exits.

`size` sets a floating Client's size, then the minimum and maximum size clamp it. Every Layout keeps a floating Client inside its minimum and maximum, also when the window changes them. `window_w` and `window_h` are the size the window asked for. A tiled Client keeps that size as its pseudo size. `pseudo` toggles it in every tiled Layout, a custom one included: the Client stays in its tile and is shown centered at that size, or scaled down to fit the tile while keeping its aspect when the size is larger, as in the pinned release. With no size of its own it is 1280 by 720. Toggling again fills the tile. `move` places a floating Client's top left corner, and `window_w` and `window_h` there are the size after `size`. `center` centers a floating Client in the floating work area, which is also where it opens without a rule. `move` and `center` replace each other: the last matching one wins. A trailing `0` turns `center` off. Neither moves a tiled Client.

`monitor` opens the window on that Monitor, before a `workspace` rule picks the Workspace. It takes the same selectors as `focusmonitor`. Without a trailing `silent` that Monitor is focused. `unset` and a Monitor that does not exist keep the Monitor the window opened on.

`no_close_for` takes milliseconds. Until that time has passed since the window opened, `killactive` and `closewindow` answer `error: can't close window, it's not closeable yet (noclosefor)` and do not ask it to close. `killwindow` still ends the process.

`movewindowpixel` and `resizewindowpixel` take two numbers, a comma and a window selector. The numbers are added to the window's position or size. After `exact` they replace it. A trailing `%` is a percentage of the position or size, or of the focused Monitor after `exact`. Text that is not two numbers leaves the window as it is. `movewindowpixel` moves a floating Client and leaves a tiled one. `resizewindowpixel` resizes through the Layout, so a floating Client grows from its center and a tiled Client changes its split. A size below one pixel answers `error: Invalid size`, and a fullscreen or maximized Client answers `error: Window is fullscreen`. A selector that matches nothing answers `error: moveWindow: no window` or `error: resizeWindow: no window`.

`movewindow` with a direction moves a floating Client against that edge of the floating work area, with its border inside the area, as in the pinned release.

`centerwindow` centers the active floating Client in its Monitor's work area. A tiled or fullscreen Client answers `error: No floating window found`. Its argument is ignored.

A Workspace's floating Clients stay above its tiled ones, as the pinned release draws them, whichever is focused. Windows brings a window it focuses to the top, so when a tiled Client becomes the active window, the floating Clients shown are put back above it in their order. A floating Client that is focused comes to the top of the floating ones. One a fullscreen Client keeps under itself stays there. `bringactivetotop` raises the active Client above every window that is not topmost. `alterzorder` takes `top` or `bottom`, a comma and a window selector. After it, and after `bringactivetotop`, the pointer is handled as if it moved where it is, as the pinned release simulates a mouse move, so with `input:follow_mouse` the window now under the pointer takes the focus. The window under the pointer is the topmost floating one there, in the stacking order, before any tile. Without a match it uses the active Client when that Client floats, and otherwise does nothing. Any other position answers `error: Bad z-order position: <position>`. The adapter changes the z-order with `SetWindowPos` and `HWND_TOP` or `HWND_BOTTOM`, without moving, sizing or activating the window. `clients`, `activewindow`, `workspaces`, `activeworkspace` and `monitors` answer in the pinned release's text form without `j/` and in its JSON form with it, the same fields in both: a block per entry with its fields indented a tab, an address without its `0x`, and `yes`, `no`, `true`, `false`, `1` or `0` as the pinned release writes each. With no window `clients` answers `no open windows` and `activewindow` `Invalid`. `clients` lists the Clients from the bottom of the stacking order to the top, as in the pinned release: a new Client opens on top, and `bringactivetotop` and `alterzorder` move one. A window Windows raises by itself is not followed.

`movecursortocorner` warps the cursor to a corner of the active Client: 0 bottom left, 1 bottom right, 2 top right, 3 top left. Any other number answers `error: Corner must be 0 - 3`, and text that is not a number answers `error: moveCursorToCorner, arg has to be a number`.

## Border resize and floating snap

`general:resize_on_border` defaults to false. The grab ring is looked for on the Workspace shown on the Monitor under the pointer, its special workspace first when one is open there, as in the pinned release, the floating windows from the top of the stacking order down. While a maximized or fullscreen Client covers that Workspace only a floating window allowed over it has a ring. When it is on, a press in the grab ring around a Client resizes that Client. The ring is `general:border_size` plus `general:extend_border_grab_area` (0 to 100, default 15) outside the Client. A press inside the Client is left to the Client. Floating Clients are tested first, topmost first, so a floating Client's ring over a tile still resizes the floating Client. A rounded corner is not a grab: the ring is measured from the square frame. While a special workspace is open on the focused Monitor, only its Clients have a ring. A maximized or fullscreen Client has no ring, and neither do the Clients behind it, as in the pinned release.

`general:hover_icon_on_border` defaults to true and is used only while border resize is on. The outcome names the cursor for the edge under the pointer: `top_side`, `bottom_side`, `left_side`, `right_side`, `top_left_corner`, `top_right_corner`, `bottom_left_corner`, or `bottom_right_corner`. The corner zone is the border plus 10 pixels. While a drag holds a window the outcome names `grabbing` for a move and the grabbed corner for a resize, as the pinned release overrides its cursor. Windows lets a program set the pointer only over its own windows, so Winland shows these by replacing every system cursor with the matching Windows one, the four-headed arrow for `grabbing` and the two-headed arrows for the sides and corners, and loads the user's own cursors again when the outcome names none, at exit, and on the next start after a run that did not exit cleanly.

`general:resize_corner` defaults to 0. For a floating Client, 1, 2, 3, and 4 force the grab to the top left, top right, bottom right, and bottom left. 0 uses the corner nearest the pointer. Names `disable`, `top_left`, `top_right`, `bottom_right`, and `bottom_left` are the same values.

`general:float_gaps` is the gap between a floating Client and the monitor edges, as one to four integers, default 0. A negative side uses `general:gaps_out` instead. Floating Clients are kept inside that inset.

`general:snap:enabled` defaults to false. While a floating Client is moved or resized, `general:snap:window_gap` (default 10) snaps it to another Client and `general:snap:monitor_gap` (default 10) snaps it to the monitor. Both are 0 to 100, and 0 turns that snap off. On a side with reserved space, such as the taskbar, a monitor snap meets the edge of the work area, or the monitor's own edge past the reserved space when the Client is nearer that. `general:snap:border_overlap` defaults to false. When it is on, the snap meets the monitor so the border overlaps the edge. `general:snap:respect_gaps` defaults to false. When it is on, window snaps leave `general:gaps_in` between Clients and monitor snaps leave `general:gaps_out` at the edges.

## Mouse drag

A mouse button that runs a bind is swallowed, so the window under the pointer does not get it. `binds:pass_mouse_when_bound` defaults to false, and true lets the press and the release through to that window after the bind runs, as in the pinned release. A wheel notch that runs a bind is swallowed either way.

A drag that picks up a fullscreen or maximized Client ends that mode first, as in the pinned release. A floating Client is then put under the pointer: by its middle with `binds:drag_center_window`, and otherwise at the same fraction of the window as where the fullscreen surface was grabbed.

`bindm` binds a mouse button to `movewindow` or `resizewindow`. A press takes the Client under the pointer, or the one whose border is under it, as in the pinned release, focuses it, and drags it until that button is released. When Windows drops the mouse hook during a drag the release cannot be seen, so the drag ends where the pointer is once the hook is put back. The `mouse` dispatcher in an ordinary bind, as in `bind = SUPER, mouse:272, mouse, movewindow`, is the same action. It takes only `movewindow` or `resizewindow`. Bound to a key, as in `bind = SUPER, Z, mouse, movewindow`, it drags the window under the pointer while the key is held, as in the pinned release: the key's repeats are swallowed and its release drops the window. A press with no Client under the pointer does not drag, and when the drag is all its bind does the press goes on to whatever is under the pointer, the desktop say, and so does its release, as in the pinned release. The mouse hook asks the core without waiting, so a press made while the core is busy is kept. A Client that closes while it is dragged or resized, by a bind, its border or the system, ends that drag.

While a `movewindow` drag moves a Client, as soon as the Client's middle lies on a Monitor whose shown Workspace is not the Client's, the Client joins that Workspace, or the special workspace when one is open there, as in the pinned release, and `movewindow` is told each time. The drag continues on that Workspace. A tile the drag lifted stays floating until release, then drops into that Workspace's Layout at the pointer, and a floating Client keeps its rectangle. A floating `resizewindow` joins the same way when its middle crosses. A tiled resize does not. A release with no move, whose middle is already on another Monitor, still joins the Workspace that Monitor shows.

In the monocle Layout a floating Client moves and resizes with the pointer as in any other, the shown tile is lifted out of the stack on the first move and dropped back as the shown tile, and a tile does not resize, since every tile fills the area, as in the pinned release.

`binds:drag_threshold` defaults to 0. Above 0, the Client is not picked up until the pointer has moved farther than that many pixels from the press. The drag then starts from that point, so the Client does not jump. The same distance separates the `c` and `g` bind flags.

`movewindow` moves a floating Client with the pointer. A tiled Client is lifted out of the Layout and floats at its tiled size, centered on the pointer. With `binds:drag_center_window` false it is held instead by the point the pointer grabbed, at the same fraction of its size, as in the pinned release. On release it drops back into the Layout at the pointer. A Client that closes while it is dragged ends the drag, and nothing is dropped on release. The same happens when a dispatcher moves it to another Workspace during the drag. In dwindle it splits the tile under the pointer, or the nearest tile, and goes on the half the pointer is over. `dwindle:force_split` does not apply to a drop. `dwindle:precise_mouse_move` defaults to false. When it is on, a drop picks the side of the tile nearest the pointer, as `dwindle:smart_split` does, and splits keep their direction when the tree is refit.

A Client that the system moves by its title bar is dragged the same way. A tiled Client is lifted out of its Layout when the move starts, and the other tiles close the gap. When the move ends it is dropped back in where the pointer is, by the same rule as a `movewindow` drop in that Layout. A maximized or fullscreen Client leaves that mode when its title is taken. A floating Client stays where it is dropped, and one the system resizes keeps the size it is left at. `clients` and `activewindow` report that frame, and for a resize they follow the border while it is held. A drag that starts on a sizing border is a resize: a tiled Client changes its split while the border is held, as `resizewindow` does. The window is asked what is under the pointer when the drag starts. A window that answers with a border or with its title settles it. A window that answers with nothing or with its client area, as a terminal does when it snaps its size to its character grid as the sizing begins and so pulls its border out from under the pointer, is told by its first change: a change in its size is a resize, and a change in its position alone is a move. Its neighbours follow the border, the system sizes the Client itself, and the Client takes its Layout rectangle when the border is let go, and a maximized or fullscreen Client goes back to covering the area. Hyprland does the same for the move and resize requests of a client.

`resizewindow` resizes a floating Client from the grabbed corner. That is the corner nearest the pointer, or the one `general:resize_corner` forces. A tiled Client changes its split ratios instead. `resizewindow 1` keeps a floating Client's aspect ratio: the side that grew more sets the size and the other follows. `resizewindow 2` does not keep it. With no argument the `keep_aspect_ratio` window rule or property decides, as in the pinned release.

`dwindle:smart_resizing` defaults to true. A mouse resize of a tile moves the edges on the grabbed corner's side and keeps the opposite edges in place, so the tiles on the far side do not change. A tile against a monitor edge moves its other edge. `resizeactive` has no corner and moves the nearest split on each axis. `resizeactive exact` names the window's size, so a tile grows by the difference from the window it shows, not from the tile with its gaps and border. False always moves the nearest split, whichever corner is grabbed. `master:smart_resizing` defaults to true. Grabbing a tile's top edge in a vertical stack, or its left edge in a horizontal one, takes the space from the tiles before it. In the center orientation a grabbed master moves both master edges.

In the scrolling Layout `movefocus`, and the dispatchers that look for a neighbour in a direction, stop at the ends of the strip and of a column instead of wrapping around, so `movefocus` goes on to the neighbouring Monitor, as in the pinned release. Only `layoutmsg focus` follows `scrolling:wrap_focus`. `movefocus` scrolls the strip to the Client it focuses only with `scrolling:follow_focus` on, and `layoutmsg focus` always does. With `follow_focus` on, the strip follows focus that a dispatcher, a click or a Group change gives. Focus the pointer gives follows only when at least the `scrolling:follow_min_visible` fraction of the Client shows, as in the pinned release.

In the scrolling Layout a resize keeps the camera where it is. A column's far edge does not move past the viewport, and grabbing its near edge moves the camera with it so the far edge stays put. A row trades space with the row on the grabbed edge. `resizeactive` has no corner, so a row trades with the row before it, and the first row with the row after it.

## Cursor and input

These cursor keys are honored: `warp_on_change_workspace`, `warp_on_monitor_change`, `warp_on_toggle_special`, `no_warps`, `persistent_warps`, `inactive_timeout`, `hide_on_key_press`, `hide_on_touch`, `hide_on_tablet`, `invisible`, `warp_back_after_non_mouse_input`, `default_monitor`, `zoom_factor`, `zoom_rigid`, `zoom_detached_camera`, `zoom_disable_aa`, and `hotspot_padding`. Every other `cursor` key stays a Gap.

`hotspot_padding`, from 0 to 20 logical pixels and 0 by default, keeps the cursor that far from the outer edges of the monitors, as in the pinned release: a mouse move that would take it closer stops short, and the edges between monitors are crossed as before. The padding is multiplied by the largest monitor scale. Only the mouse is held back; a program that sets the cursor position itself, or touch and a pen, are not.

`warp_on_change_workspace` and `warp_on_toggle_special` default to 0. 1 warps to the middle of the last focused window, or to the cursor's last point in that window when `persistent_warps` is on. 2 does the same and still warps when `no_warps` is on. `warp_on_monitor_change` defaults to -1, which follows `warp_on_change_workspace`, and takes the same modes. A change that lands on another Monitor follows `warp_on_monitor_change`, and one on the same Monitor follows `warp_on_change_workspace`, as in the pinned release. `warp_on_toggle_special` warps when `togglespecialworkspace` shows or hides a special workspace.

`inactive_timeout` is seconds from 0 to 20, default 0. Above 0 the cursor hides once it has been still for longer than that. `hide_on_key_press` hides it on a key press until it moves. `invisible` never shows it. `hide_on_touch`, default true, hides it when a touch screen moves the pointer or touches down, and `hide_on_tablet`, default false, when a pen does, until the mouse moves, as in the pinned release. Windows tells them apart by the signature it puts on the mouse input it makes from touch and pens. Windows itself also hides the cursor while a touch screen is used, so with `hide_on_touch` false the cursor still hides then. The cursor is hidden through the system magnifier, so it is hidden over every program, and it comes back when Winland exits, even when Winland is killed. `warp_back_after_non_mouse_input`, default false, makes the first mouse move after something else moved the cursor start from where the mouse last left it, moved by that first step, as in the pinned release. Winland's own warps, touch, a pen, and moves another program sends are not the mouse. `default_monitor` warps once to the middle of the named monitor. An empty value does not warp, and `no_warps` does not block that warp.

`zoom_factor` zooms the Monitor under the cursor by that factor, from 1 to 10, default 1, which is no zoom. With `zoom_detached_camera`, on by default, the view keeps the point under the cursor in place when the factor changes, and follows the cursor only when it leaves the middle 90% of the view, or not at all with `zoom_rigid`. With `zoom_detached_camera` off the view zooms about the cursor, or keeps the cursor in its middle with `zoom_rigid`. The view never shows past the Monitor's edge, and the cursor points where it is drawn. The zoom is drawn by the system magnifier, which zooms the whole desktop as one surface, so while the Monitor under the cursor is zoomed, the others show what lies beside it at the same factor; in the pinned release only that Monitor zooms. A change of `zoom_factor` eases to the new factor with the `zoomFactor` animation, which inherits from `global`, and changes at once when that animation is off. It goes away when Winland exits. `zoom_disable_aa` turns off the system magnifier's bitmap smoothing, as Windows' own Magnifier does with "Smooth edges of images and text", so the zoomed picture keeps its hard pixel edges.

These input keys are honored: `repeat_rate`, `repeat_delay`, `numlock_by_default`, `left_handed`, `natural_scroll`, `accel_profile`, `sensitivity`, and `scroll_factor`. A key left unset does not change the system. The value it replaced is saved and put back on a clean exit, and again on the next start if the process crashed.

`kb_layout` lists the keyboard layouts by their XKB names, comma-separated, and `kb_variant` gives the variant of each at the same place. Each is matched to the Windows layout with that name, such as `us` to US, `se` to Swedish and `us` with `dvorak` to United States-Dvorak; a variant Windows has no layout for uses the plain layout, and a layout Windows has none for keeps its place in the list but loads nothing. Winland loads the layouts and switches to the first. `switchxkblayout KEYBOARD next|prev|INDEX` switches between them, as in the pinned release: `all`, or `main`, `active` or `current` for the first keyboard, or a keyboard's name from `devices` names the keyboard, `next` and `prev` wrap around, an index out of range answers `layout idx out of range of N`, and a switch emits `activelayout>>KEYBOARD,LAYOUT` with the layout's XKB description. Windows switches the input language of the window in the foreground. `devices` reports the keyboards and mice that Raw Input lists, as `hl.get_devices` does. Each is named as the pinned release names a device, from the manufacturer and product names its HID driver reports, such as `logitech-usb-receiver`, or else from the name Device Manager shows, such as `hid-keyboard-device`: in lower case, with a space or a comma as `-`, and `-1`, `-2` and so on after a name an earlier device has. A touchpad is a mouse there. Each keyboard reports the same layouts and `active_layout_index`, because Windows puts every keyboard through the same layout, and the first keyboard is the `main` one. An unset `kb_layout` leaves the system's layouts alone. Layouts Winland loaded are unloaded when the config drops them and on exit; the ones that were loaded before stay, and Windows still offers them in its own switcher, which Winland does not follow. Binds read the keys in the first layout `kb_layout` names, whichever layout is in use, as in the pinned release; `resolve_binds_by_sym` makes them read keys in the layout in use instead. With no `kb_layout`, binds read keys in the layout in use. `kb_options` takes these XKB options, comma-separated: `caps:escape`, `caps:escape_shifted_capslock` (as Escape), `caps:swapescape`, `caps:backspace`, `caps:super`, `caps:none`, `caps:ctrl_modifier`, `ctrl:nocaps`, `ctrl:swapcaps`, `altwin:swap_alt_win` and `altwin:swap_lalt_lwin` move keys, and `grp:alt_shift_toggle`, `grp:ctrl_shift_toggle`, `grp:ctrl_alt_toggle`, `grp:win_space_toggle`, `grp:alt_space_toggle`, `grp:alts_toggle` and `grp:caps_toggle` switch to the next layout, as `switchxkblayout all next` does. A moved key reaches the programs, and the binds, as the key it moves to. Any other option warns `XKB option 'NAME' is not honored.`

`repeat_delay` is milliseconds, mapped to the four system delays 250, 500, 750 and 1000. A tie takes the longer delay. `repeat_rate` is repeats per second, mapped onto system speed 0 through 31, where 0 is about 2.5 repeats per second and 31 is about 30. `sensitivity` from -1 to 1 maps onto pointer speed 1 through 20, and 0 maps to 10. `scroll_factor` from 0 to 2 maps onto wheel lines as the factor times 3. `accel_profile` `flat` turns pointer acceleration off. `force_no_accel` turns it off whatever `accel_profile` says, and like the other keys, only when it is set. `rotation`, 0 to 359, turns the mouse's motion clockwise by that many degrees, as the pinned release rotates a pointer device. Winland turns each move in its mouse hook, after Windows has accelerated it, and keeps what rounding leaves for the next move, unless a device sets its own `sensitivity` or `rotation`, described below. Touch and a pen are not turned. `adaptive` turns it on with thresholds 6 and 10. `custom` warns and does not curve the pointer; a profile that starts with `custom` still turns on `scroll_points`. `scroll_points` is the libinput scroll curve: a step and then the factors the mouse wheel is multiplied by, the first at speed 0 and each next one a step faster, interpolated in a straight line and held at the last factor past it. Speed is scroll units per millisecond, a notch being 15 units, measured over the time since the last turn of the same axis and direction; the first turn of a run, or one after half a second, is at speed 0. Winland takes each mouse wheel turn in its mouse hook and sends it again scaled, keeping what rounding leaves for the next turn, so the curve multiplies Windows' own wheel lines (`scroll_factor`). It needs at least two factors, none negative, and at most 64, or it is ignored and the wheel is left alone. The touchpad is not curved, and with no custom profile or no points the wheel is not touched. `emulate_discrete_scroll` turns the turns of a high resolution wheel, which Windows sends in parts of a notch, into whole notches: 0 leaves every turn alone, 1, the default, takes a turn that is not a whole multiple of 120 and 2 takes every mouse wheel turn, whole notches too. The touchpad is never taken. Winland takes the turn in its mouse hook and sends whole notches in its place: the first turn of a run, the same axis and direction with under half a second between turns, sends a notch at once, and after that one notch goes out for every 120 divided by `scroll_factor` units the turns add up to. Windows applies the wheel lines to each notch, so `scroll_factor` is not applied twice. A wheel that sends whole notches is untouched by the default. A pointing device that sends part-notch turns without being the precision touchpad, such as an older touchpad driver, is emulated like a high resolution wheel. A turn this takes is not curved by `scroll_points`. `off_window_axis_events` is about a wheel turn over the ring around a window, not inside it: the border and, with `resize_on_border`, the grab area around it (`border_size` plus `extend_border_grab_area`), where Windows would send the turn to whatever lies under the cursor, usually nothing. The lookup never waits for the core: when the core is busy the turn is left to Windows. `ignore` (0) drops it. `send` (1), the default, and `clamp` (2) both post a wheel message to the window at the nearest point inside its tile without moving the cursor. They differ in the reference only in the coordinates the window is given, which Windows apps cannot take outside their window, so here they are the same. `warp` (3) moves the cursor to that point and sends the turn again from there. A turn that runs a bind goes to the bind first. A turn over no window, such as a gap or the desktop, is left alone. `natural_scroll` reverses wheel direction as the event is handled. It is not a system setting. `left_handed` swaps the mouse buttons. `numlock_by_default` toggles Num Lock only when it is not already in that state. `scroll_method = on_button_down` scrolls by moving the mouse while the scroll button is held, as libinput does: `scroll_button` names it by its Linux code, 272 to 276, and 0, the default, is the middle button. The cursor stays where it is and every 15 pixels of motion is a wheel notch, reversed with `natural_scroll`. A press and release with no motion is a click. With `scroll_button_lock` such a click turns the scrolling on until the next click instead. Other scroll methods are touchpad settings Windows makes itself. The touchpad keys `tap-to-click`, `tap-and-drag`, `natural_scroll`, `disable_while_typing` and `clickfinger_behavior` set the Windows precision touchpad settings: tapping, tap and drag, the scroll direction (natural scrolling is Windows' default direction, so false reverses it), the touchpad sensitivity while typing (true is Windows' medium default, false the most sensitive, which never turns it off), and the right-click zone, which `clickfinger_behavior` turns off. Like the other input keys, an unset key leaves its setting alone and the replaced value is put back on exit.

A `device[name]` line sets `sensitivity`, `scroll_factor` or `rotation` for one pointer. The name is the spelling the `devices` reply uses, and a later line for the same device and field replaces that field. A field left unset keeps the global key. `sensitivity` scales the movement Windows has already applied, after acceleration, by the ratio of pointer speeds: the device's value maps as the global key does, divided by the speed Windows is using, which is the global `sensitivity` when that key is set. It is not its own acceleration curve. `scroll_factor` is from 0 to 100. Left unset it is the global factor, and 1 when that key is unset. The system's wheel lines stay the global key. Winland sends another wheel turn for the difference, so the two turns add up to the device's factor divided by the global one. A global factor of 0 leaves the lines at 0, and the device's factor cannot bring the wheel back. `rotation` turns that device's moves. When any device sets `sensitivity` or `rotation`, including a rotation of 0, the hook does not turn moves itself, because taking the move drops the raw packet that names the mouse. The turn is applied when that packet arrives, and a device that sets no rotation takes the global one. The hook does not name the mouse, so the packet is matched with the move the hook just let through, and a move older than 50 ms clears that queue. A move the hook takes, such as a touchpad flip, hotspot padding or button scrolling, is not matched, and neither is a move while a finger is on the precision touchpad. Touch and a pen are not changed. Two pointers that move together can be matched in the order the hook saw them. A wheel the hook takes, such as a bind, `scroll_points`, discrete emulation, the touchpad's own scale or off-window handling, is not corrected again. The listener starts when the config names one of these fields. The other device fields are Windows limits in [gaps.md](gaps.md).

`input:touchpad:tap_button_map` `lrm` turns on Windows' two-finger tap to right-click, and `lmr` turns it off and makes a two-finger tap a middle click instead: two fingers that touch and lift within 180 ms, neither moving 1.5 millimetres, unless `tap-to-click` is false. Unset or empty leaves Windows' setting alone. A three-finger tap stays Windows' own three-finger tap action, which no setting Winland can write changes. The other touchpad keys Windows has no setting for are carried out by Winland from the fingers the precision touchpad reports as raw input, because Windows hands the touchpad's cursor moves and wheel turns to the mouse hook with no device. A cursor move made while a finger is on the touchpad is the touchpad's, and so is a wheel turn made while two fingers are on it, or one that is not a whole notch within two seconds of two fingers lifting, which is Windows' scrolling coasting on. `flip_x` and `flip_y` turn the touchpad's cursor move around across and up and down, after `input:rotation` turns it. When a device sets `sensitivity` or `rotation` the hook does not turn the move, so the flip runs first, and a flip that takes the move is not corrected for that device. `scroll_factor`, 0 to 100, default 1, multiplies the touchpad's wheel turns: the hook takes each and sends it again multiplied, keeping what rounding leaves for the next. `input:scroll_factor` sets Windows' wheel lines, which a touchpad's wheel turns also go through, so the touchpad's factor is divided by it. A `scroll_factor` of 0 stops every wheel, the mouse's too, as in the pinned release, which takes every scroll as the touchpad's then. Applications that scroll with the touchpad themselves through Windows' direct manipulation, such as Edge, get no wheel turns, and their scrolling is not multiplied. A window's own `scroll_touchpad`, from `setprop` or a window rule, replaces `scroll_factor` for the turns made over it, and its `scroll_mouse` replaces `input:scroll_factor` for the mouse's, as in the pinned release. Over the window means the window under the cursor or the one whose ring, as `off_window_axis_events` reads it, the cursor is in. The hook sends such a mouse turn again multiplied by the window's factor divided by `input:scroll_factor`, so it is neither curved by `scroll_points` nor emulated as whole notches. The lookup never waits for the core, and when the core is busy the turn takes the configured factors. `drag_3fg` 1 drags with three fingers and 2 with four, as libinput's three-finger drag does: once the fingers' middle has travelled a millimetre the left button goes down, the primary one when the buttons are swapped, and the cursor follows the fingers at about 300 pixels per inch, turned around by `flip_x` and `flip_y`. Fingers lifted keep the button down for 700 ms, and putting them back down carries the drag on. A finger more, or the time running out, lets the button go. That finger count then makes no swipe or pinch gesture, as libinput sends none. Windows still reads the same fingers, so set its swipes for that count to Nothing, as for a swipe gesture.

`drag_lock` 1 or 2 locks a tap and drag, as libinput's does, when `tap-to-click` and `tap-and-drag` are not false. Windows' own tap and drag has no lock, so Winland turns it off while the lock is set, puts it back on exit, and does the tap and drag from the fingers: a tap of one finger (within 180 ms, moving under 1.5 millimetres), then a touch within 300 ms that moves 1.5 millimetres, presses the left button, the primary one when the buttons are swapped. Windows moves the cursor with the finger as always. Lifting keeps the button down: 1 lets it go after 300 ms, and touching again before then carries the drag on; 2 keeps it down until the next tap. A second finger lets it go at once. A second touch that lifts without moving is only Windows' own tap, so it presses nothing.

`middle_button_emulation` makes the left and right buttons pressed together a middle click. The mouse hook cannot tell a touchpad's buttons from a mouse's, so a press counts as the touchpad's when a finger is on the precision touchpad, which a clickpad's press always has. That first press is held back for 50 ms, as libinput holds it. If the other button comes in that time, both are swallowed and the middle button goes down, and up once both are released. Otherwise the held press is sent again, and a press released within 50 ms is sent as a click. A press with no finger on the touchpad, or with the other button already down, goes through at once, so a mouse's click is not delayed. The sent-again press and the middle button are injected input, so binds see them, but a program that tells hardware clicks from injected ones does. A touchpad press is up to 50 ms late with the option on, even when the other button never comes.

`input:tablet` maps every pen. Windows has no call that changes which display a pen maps to, so Winland moves the cursor the mouse hook sees, after Windows has mapped the pen. A program that reads the pen's own pointer messages still sees Windows' mapping, and the device stays enabled. `enabled`, default true, lets the pen move the cursor. False swallows the mouse input Windows makes from the pen and puts the cursor back where the mouse left it. `transform`, 0 to 6 and 0 by default, turns that position the way the pinned release does: 0 leaves it, 1 is a quarter turn clockwise, 2 a half turn, 3 three quarters, 4 flips it across, 5 swaps the axes, and 6 flips it down. `left_handed` then turns it a half turn more. `output` names the monitor, by its name or its description, or `desc:` and the start of the description, or `current` for the focused monitor. Empty, or `[[EMPTY]]`, maps it across every monitor, and so does a name that matches none, including a direction. `region_position` and `region_size` are physical pixels of the virtual screen. The position is an offset from the named monitor, or from the layout when no monitor is named, and the size replaces the area when both of its numbers are above 0. `absolute_region_position` makes that position the origin itself, and only when no monitor is named. `relative_input` moves the cursor by how far the mapped point moved, in pixels, rather than placing it: the mouse hook has no device units to move by. `active_area_position` and `active_area_size` are millimetres of the tablet. The size is the part of it that spans the area, and an odd `transform` swaps the tablet's axes first. The area is used only when both of its numbers are above 0 and Windows reports the tablet's size, so a pen whose size is unknown does not jump. The point Winland maps is where Windows already put the pen on its display, or on the monitor under the pen when Windows does not say.

`input:touchdevice` maps every touch screen the same way, for the cursor Windows makes from it and for a workspace swipe. `enabled`, default true, lets both through. False swallows that cursor and ignores the swipe, and the touch screen stays enabled; a program under the finger still gets the touch. `output` empty, `[[EMPTY]]` or `[[Auto]]` keeps the display Windows maps the touch screen to. `[[Auto]]` is the pinned release's unfinished autodetect, and on Windows that display is the one Windows already chose. A monitor name, a description, `desc:` or `current` maps the cursor and the swipe onto that monitor, and a name that matches none maps them across every monitor. `transform` is the same 0 to 6, applied after Windows has turned the touch screen with its display, and 0 leaves that as it is.

A long-press bind, with the `o` flag, runs once its key has been held for `repeat_delay` exactly, 600 ms by default, as in the pinned release. That wait is not rounded to a system delay.

`input:follow_mouse` defaults to 1. 0 leaves keyboard focus where it is when the pointer moves. 1 moves it to the Client under the pointer once the pointer has traveled farther than `input:follow_mouse_threshold` logical pixels. That distance accumulates while the pointer keeps moving and resets after the pointer has been still for half a second. 2 and 3 do not move keyboard focus when the pointer moves. 3 also keeps the focused Client when a click would take it. The names `disabled`, `follow`, `detached`, and `separate` are 0, 1, 2, and 3.

`input:follow_mouse_shrink` insets every Client except the focused one by that many logical pixels. The pointer in the inset does not move keyboard focus. The window under the pointer still receives pointer input.

On a Workspace with a maximized or fullscreen Client, that Client owns the pointer. The tiles behind it take no focus when the pointer passes over them. A maximized Client takes the focus only where it is drawn, and a fullscreen one wherever the pointer is.

`input:mouse_refocus` defaults to true. When it is false, mode 1 does not move keyboard focus back to the Client already under the pointer until the pointer crosses onto another Client.

`input:float_switch_override_focus` defaults to 1. In modes 0 and 2, moving between a tiled Client and a floating Client moves keyboard focus. 2 also does so between two floating Clients. 0 does not. Mode 3 does not use it.

`input:focus_on_close` defaults to 0. 0 focuses the nearest remaining tiled Client, or the nearest floating Client when no tiled Client is left, or the most recently focused Client when the one that closed was floating. 1 focuses the Client under the pointer. 2 focuses the most recently focused Client. The names `next`, `cursor`, and `mru` are 0, 1, and 2. A master layout with `master:focus_master_on_close` still focuses the master when the closed Client was tiled and the mode is 0.

`misc:mouse_move_focuses_monitor` defaults to true. Moving the pointer onto another Monitor focuses that Monitor. False leaves it until a Client there takes keyboard focus.

Modes 2 and 3 cannot choose which window receives pointer input. The window under the pointer still receives it. Those modes only decide keyboard focus.

The keyboard and mouse hooks run on a thread of their own. It only decides whether a key or button is swallowed and hands everything else to the bind worker, so a window that stops answering, or a reload, never holds up the keyboard or the mouse, or makes Windows drop the hooks for being slow. Pointer moves that arrive while the bind worker is busy collapse into the newest one.

A key's device is the keyboard raw input names for that press, the same name the `devices` reply uses. Windows names that keyboard only after the key is delivered, and swallowing the key produces no raw input, so a bind that would consume the key cannot depend on the device. The config warns once and does not register that bind, whether the list names a keyboard or a `device:tags` tag. A non-consuming device bind (flag `n`) is honored. The key goes on to the window, and the bind runs when the raw packet arrives on the input thread. `+` matches only the listed names and `-` matches every other named keyboard. A keyboard that is not named yet matches neither. A name is matched as written, in the spelling the `devices` reply uses. The press runs from the packet for the key going down. Repeats run from the hook after that packet, and repeats that arrived before it, at most eight, run with the packet. The release runs when the key goes up, on the keyboard of the press. If the key is already up when the packet arrives, the press and the release both run from that packet, and the packet for the key going up does not run them again. A pointer button and a wheel turn have no device, so a device bind on them does not run. A key `kb_options` moves is sent on as the key it becomes. The raw packet names the original key, which the hook swallowed, so a device bind does not see it. A chord runs from the packet when the keys were held together as the triggering key went down.

`auto_consuming` swallows the key and runs the dispatcher. When every such dispatcher fails, or a Lua function asks to pass the event, the hook injects the key so the focused window receives it. The injection is the trigger key, after the dispatcher has returned, and a key that is still held is injected as a press. A release bind that is auto-consuming does not swallow the press, and its release is not swallowed either, because Windows must see the release of a press it saw. A pointer button, a wheel turn and a long press that only an auto-consuming bind takes stay swallowed. A dispatcher that reports no error consumes the key even when it changes nothing. A key whose bind drags is swallowed for the drag and is not given back.


## Touchpad swipe

`gesture = fingers, direction, action` is honored for the `workspace`, `special`, `dispatcher`, `close`, `float`, `fullscreen`, `move`, `resize`, `cursorZoom` and `scrollMove` actions below, so `gesture = 3, horizontal, workspace` switches Workspace with a three-finger swipe. Fingers run from 2 to 9, and the directions are `swipe`, `horizontal`, `vertical`, `left`, `right`, `up` and `down`, and the pinches `pinch`, `pinchin` and `pinchout`, with the short names the pinned release accepts. `mod:` takes the modifiers that must be held, and `scale:` multiplies the distance, from 0.1 to 10 or, turning the gesture around, from -10 to -0.1. A scale nearer 0 warns and the gesture is skipped. A gesture matches once the fingers have moved 5 pixels: the larger axis and its sign pick the direction, and the first gesture whose direction, finger count and held modifiers all match takes the swipe. A gesture shadowed by an earlier one warns and is skipped, and `unset` removes the gesture with the same fingers, direction, modifiers, scale and flag. A swipe is a touchpad gesture of three or more fingers, so a two-finger swipe gesture never matches, as in the pinned release. A pinch takes two or more. A locked session does not swipe.

The swipe follows the configured direction, not the one the fingers took. `horizontal` reads rightward travel, `vertical` downward, `left` leftward, `up` upward and `swipe` the length of the movement. `gestures:workspace_swipe_invert` defaults to true, which turns that around, so fingers moving left go to the next Workspace and fingers moving right go to the previous one. The next and previous Workspaces are `m+1` and `m-1` on the focused Monitor, or `r+1` and `r-1` with `gestures:workspace_swipe_use_r`. There is no previous Workspace before the first.

`gestures:workspace_swipe_distance` is the travel of a full swipe, in pixels from 0 to 2000, default 300. A touchpad's travel is counted at about 300 pixels per inch, 12 per millimetre. When the fingers lift, the Workspace changes once the swipe has covered `gestures:workspace_swipe_cancel_ratio` of that distance (0 to 1, default 0.5), or when its average speed per update is at least `gestures:workspace_swipe_min_speed_to_force` (0 to 200, default 30, where 0 never forces). A swipe shorter than 2 pixels never changes the Workspace. `gestures:workspace_swipe_create_new` defaults to true. Swiping on past the last Workspace then creates the next one, unless the Workspace swiped from is empty. False stops at the last Workspace, and a Monitor with one Workspace does not swipe at all. `gestures:workspace_swipe_direction_lock` defaults to true. Once the swipe has moved `gestures:workspace_swipe_direction_lock_threshold` pixels (0 to 200, default 10), moving back the other way counts as no travel. `gestures:workspace_swipe_forever` defaults to false. True switches each time the swipe covers the full distance and keeps going from there.

While the fingers move, the Workspace swiped from follows them, as in the pinned release: a whole swipe moves it by the monitor's width and `general:gaps_workspaces`, and the Workspace it goes to comes in beside it, from the right for the next one and the left for the previous one. A `slidevert` or `slidefadevert` style on the `workspaces` animation swipes up and down instead. Pinned and minimized Clients stay where they are. When the fingers lift, a switch slides both Workspaces on from where they are with the `workspacesIn` and `workspacesOut` animations, and a swipe that falls short slides the Workspace back and the other one away, which is then hidden. This follows the fingers even with `animations:enabled` false; the lift then lands at once.

`dispatcher`, `close`, `float` and `fullscreen` act once the fingers lift, as in the pinned release. `gesture = 3, left, dispatcher, exec, kitty` runs the dispatcher and its arguments, at any distance. `close` closes the focused window once the fingers have gone 40 pixels along their direction. While they move, the window fades and shrinks toward where its `windowsOut` animation would leave it, all the way at 200 pixels, as in the pinned release. When they lift short of 40 pixels it comes back with the `windowsMove` and `fade` animations. Otherwise it closes from where the swipe left it, and a window still open after `gestures:close_max_timeout` milliseconds (10 to 2000, default 1000) is put back. `float` and `fullscreen` need 50: `float` takes `float`, `tile` or nothing to toggle, and `fullscreen` takes `fullscreen` or `maximize`. A shorter swipe does nothing. The pinned release also moves those two windows along with the fingers before they lift. Here they move only once they do.

`move` and `resize` act on the focused window while the fingers move, as in the pinned release. A floating window moves with the fingers, and `resize` resizes any window from the corner nearest the pointer, as a `movewindow` or `resizewindow` mouse drag does, with `scale:` multiplying the travel. A tiled window `move` takes shifts with the fingers by half their travel, at most 100 pixels each way, and when they lift it moves one place in the direction they went furthest, as `movewindow` does, animating from where it was shifted. A window that cannot move there goes back.

`gesture = fingers, direction, cursorZoom, ZOOM, MODE` changes the cursor zoom of every Monitor, as in the pinned release. With no mode it toggles between ZOOM and `cursor:zoom_factor` each time the gesture is made. `mult` multiplies the zoom by ZOOM. `live` follows a pinch: the zoom when the pinch began times how far the fingers spread, at once and without `animation:zoomFactor`, and anything below 1.05 is no zoom. The zoom a gesture sets lasts until the config is read again.

`scrollMove` moves the scrolling Layout's tape on the focused Monitor with the fingers, as in the pinned release. When they lift, the tape carries on by the swipe's speed, at most two views. `gestures:scrolling:move_snap_to_grid` (default true) then settles it on the nearest column, centered or fitted by `scrolling:focus_fit_method`, and focuses that column's window. A swipe that settles back on the column it started on goes back to where it started. Without snapping, the window of the column in the middle takes the focus. `gestures:scrolling:move_snap_cursor` (default true) moves the cursor to the window that took the focus.

`gesture = fingers, direction, special, name` shows the special workspace `special:name` with a swipe, or hides it when it is shown. An empty name, or none, is `special`. When the gesture matches, the special workspace is shown on the focused Monitor at once, and is created if it does not exist. If it is already shown on a Monitor, that one is used and it stays shown while the fingers move. The swipe reads the distance along the direction the fingers took, times `scale:`. A whole swipe is 150 pixels. When the fingers lift, a swipe that covered at least 30 percent of that keeps the special workspace it showed, or hides the one that was shown. A shorter swipe puts it back as it was. A special workspace hidden when the swipe ends, and empty, closes. If something else hides, replaces or moves the special workspace during the swipe, the swipe lets go of it and changes nothing when the fingers lift. The fade, dim and slide that follow the fingers in the pinned release are the `animations` Gap, and `cursor:warp_on_toggle_special` does not warp for a swipe, as in the pinned release. A locked session does not swipe.

Fingers that come down together are a swipe once their middle has travelled a millimetre, and a pinch once they have spread apart or closed together by 8 percent. Two fingers that travel are a scroll, which no gesture takes. A pinch picks its gesture once it has spread or closed by a tenth, as in the pinned release: spreading is `pinchin` and closing is `pinchout`, and `pinch` takes either. Any action then runs from the pinch as it would from a swipe. Its travel is the change of its scale times 400, times 1.6 for `pinch` and `pinchout`, and the movement of the fingers' middle moves a window with `move` or `resize`. Windows also reads a two-finger pinch as zooming the window under the pointer, which cannot be turned off.

`gestures:workspace_swipe_touch` (default false) switches Workspace with one finger swiped in from the edge of a touch screen, as in the pinned release. A finger that comes down at the left or right edge of the Monitor, inside `general:gaps_out` and `general:border_size`, starts a workspace swipe there, or the top or bottom edge with a `slidevert` or `slidefadevert` workspaces style. The Workspace then follows the finger as it does a touchpad swipe, and a whole swipe is the finger crossing the Monitor's width, which `gestures:workspace_swipe_distance` counts as that many pixels. A finger from the right edge moving left goes to the next Workspace, and `gestures:workspace_swipe_touch_invert` (default false) turns that around. Lifting the finger ends the swipe as lifting a touchpad's fingers does, and a touch screen that goes away puts the Workspace back. A finger that comes down during a touch screen or touchpad workspace swipe, or while such a finger is still down, is held: it neither drives nor ends the swipe, and starts none until it lifts. The Monitor is the one `input:touchdevice:output` names, or, when that is empty, `[[Auto]]` or `[[EMPTY]]`, the one Windows maps the touch screen to. `input:touchdevice:transform` turns the finger after Windows has turned it with its display, and `input:touchdevice:enabled` false ignores the finger. The focused Monitor is used when Windows does not say which display the touch screen is on and the output names none. A locked session does not swipe. Winland reads the touch screen as raw input too, so Windows also acts on the finger: an application under it gets the touch, and a swipe from the very edge of the display can also open Windows' own edge panels.

Winland reads the fingers as raw input from a precision touchpad. A touchpad that is not a precision touchpad does not swipe. Raw input cannot be consumed, so Windows also acts on the same fingers. Turn its gestures off for the finger count you configure: open Settings, then Bluetooth & devices, then Touchpad, expand Three-finger gestures (or Four-finger gestures), and set Swipes to Nothing. Otherwise a three-finger swipe both switches the Winland Workspace and switches apps or desktops in Windows.

## Special workspaces

`special` and `special:` address the special workspace named `special:special`. `special:name` addresses `special:name`. The same address works in `workspace`, `movetoworkspace`, `movetoworkspacesilent`, and a window rule's `workspace` effect. A trailing `silent` on the rule does not show the special workspace.

When the focused Client closes while a special workspace is open on its Monitor, a Client elsewhere does not take the focus: the special workspace's Client focused last does, as in the pinned release.

When a special workspace opens on a Monitor, a floating Client on it whose middle is off that Monitor is brought onto it, as in the pinned release: by the offset between the Monitors when its middle is on another one, and otherwise to the Monitor's middle.

`togglespecialworkspace` shows that special workspace on the focused Monitor, or hides it when it is already shown there. The argument is the name, and an empty name is `special`. `workspace special:name` shows it and does not hide it again. One special workspace is shown on a Monitor, over the normal Workspace, whose Clients stay shown. Showing a special workspace that is open on another Monitor moves it. The normal Workspace stays the active one.

`misc:close_special_on_empty` defaults to true. The special workspace closes when its last Client leaves. False leaves it open. `binds:hide_special_on_workspace_change` defaults to false. True hides the Monitor's special workspace when its normal Workspace changes. `input:special_fallthrough` defaults to false. Focusing a Client on the normal Workspace then closes the special workspace. True leaves the special workspace open and the focus moves. The pointer reaches the Clients of an open special workspace, tiled or floating, before the Clients of the normal Workspace under it. Where the special workspace has no Client, a pointer hit is not taken away from a window underneath it, so a click there still focuses that window and the option decides whether the special workspace closes.

Opening a special workspace emits `activespecial` and `activespecialv2` as `name,monitor` and `id,name,monitor`. Closing one emits them with an empty name. In events and text replies the unnamed special workspace is id -99, another special workspace -98, then -97, in name order, and a named Workspace counts down from -1. As in the pinned release, the JSON replies write a Workspace as its `address`, an `id` only when it is numbered, its `type`, `normal` or `special`, and its `name`. The `specialWorkspace` of a Monitor with none open has empty strings and no `id`.

A `workspace` rule is honored for `monitor`, `default`, `persistent`, `defaultName`, `on-created-empty`, `gapsin`, `gapsout`, `float_gaps`, `bordersize`, `border`, `rounding`, `decorate`, `shadow`, `layout`, and `layoutopt` when that option is a dwindle option that is already honored. A Workspace bound to a Monitor is shown there. A persistent Workspace stays when it is empty. As in the pinned release, it is made only once the Monitor its rule names is there, a Monitor that comes shows a Workspace of its own rather than an empty persistent one, and a special workspace is never persistent. `default` selects the Workspace a Monitor shows when it has none. `defaultName` is the name reported for that Workspace. `on-created-empty` runs when the Workspace is created with no Clients, and the command is aimed at that Workspace. `gapsin`, `gapsout`, `float_gaps` (or `floatgaps`) and `bordersize` replace the general values on that Workspace. `border:0` and `decorate:0` draw no border. `rounding:0` forces square corners. `shadow:0` turns the shadow off, as `no_shadow` does. `layout` names the Layout the Workspace uses in place of `general:layout`, as in the pinned release: `dwindle`, `master`, `scrolling` or `monocle`. Any other name warns and uses dwindle. The Layout is chosen when the Workspace is created and again when the config changes, and a Workspace that changes Layout keeps its Clients. Later rules for the same Workspace override earlier ones.

`animation` on a workspace rule stays the `animation` Gap. A `layoutopt` whose option is already a Gap warns and is not applied. Any other field is skipped.

`f[N]` in a workspace rule matches the Workspace's fullscreen state, as the pinned release's source tests it: `f[-1]` has no maximized or fullscreen Client, `f[0]` has a Client in fullscreen mode 2, whatever its client mode, and `f[1]` has a maximized one. The manual describes `f[2]` as fullscreen without the client mode, but the source tests nothing for it, so `f[2]`, like any other number, matches every Workspace. The rule is matched again when the state changes, also when the covering Client closes or moves to another Workspace, so `workspace = f[1], rounding:0` squares the corners of a maximized Client. A `w[]` rule counts the Clients and is matched again whenever a Client opens, closes, floats or moves, so `workspace = w[tv1], gapsout:0, gapsin:0` holds from the first Client a Workspace gets, as in the pinned release.

A workspace filter such as `r[1-3]` matches workspaces that already exist. It is not a workspace address, so `workspace`, `movetoworkspace` and `movetoworkspacesilent` do not switch on it.

A floating Client that `movetoworkspace` or `movetoworkspacesilent` moves onto a Workspace on another Monitor keeps its place relative to the Monitor, as in the pinned release.

## Monitors

A `monitor` position is in logical pixels. Windows reports the monitor rectangle in physical pixels. The layout width is that physical width divided by the monitor's scale, rounded half away from zero. A scale-2 monitor that is 3840 physical pixels wide is 1920 wide in the layout. The position that is stored is that logical position multiplied by the monitor's scale, because window placement stays in physical pixels.

`reserved_area` and `addreserved` take top, bottom, left and right, in logical pixels, and subtract them from the work area. Values below zero count as zero.

`disable` and `disabled` remove the monitor from the layout. The display stays powered on. When no monitor is left enabled, the Workspaces move to a `FALLBACK` Monitor of 1920x1080 at 0,0, as in the pinned release, and go back when a monitor is enabled again. Because the displays stay on, the Clients on it stay visible, placed in that area of the desktop.

When a Monitor is unplugged or disabled, each of its Workspaces moves intact onto the first Monitor that remains, with its Groups, fullscreen Clients and pinned Clients. They are hidden there, except a special workspace that was shown, which is shown on that Monitor in place of any special workspace shown there. A pinned Client stays shown on that Monitor; see [gaps.md](gaps.md). An empty Workspace that is not persistent is removed once it is hidden there, as in the pinned release. When the Monitor comes back, by the same name, its Workspaces move back to it and it shows the Workspace it showed when it left, as in the pinned release, or a new one when that one was removed.

A monitor rule's mode sets the display's resolution and refresh rate whenever the monitors are laid out, from the modes the display offers at its colour depth and rotation: `WIDTHxHEIGHT@RATE` takes that size at the nearest rate, `WIDTHxHEIGHT` that size at the fastest rate, `highres` the most pixels, `highrr` the fastest rate and `maxwidth` the widest. `preferred` leaves the display at the mode Windows has. A size the display lacks changes nothing, and a modeline warns "Custom monitor modes are not honored." A scale sets the display's Windows scale to the nearest step Windows offers (100%, 125%, 150%, 175%, 200%, 225%, 250%, 300% and on to 500%) when the display does not show that step already, and `auto` leaves it. Like a rotation, Windows keeps a mode and a scale after Winland exits.

A monitor rule's `cm` preset turns Windows' HDR and wide color switches for the display whenever the monitors are laid out, and the monitors reply reports it as `colorManagementPreset`. A rule that names none reports `srgb`. `auto` is reported as `auto` and leaves the switches as Windows has them. `hdr` turns HDR on. `hdredid` turns HDR on when the display can show it, and both switches off when it cannot. `wide`, `edid`, `dcip3`, `dp3` and `adobe` turn HDR off and wide color on: Windows manages that color by the display's EDID and has no setting for a particular gamut. `srgb` turns both off. A display that already shows the switches the preset asks for is left alone. A display that cannot show the preset is left alone too, and the log says so. Wide color has its own switch from Windows 11 24H2 on; before it only HDR can be turned, and a wide preset turns HDR off and the log says wide color cannot be shown.

`bitdepth, 10` asks for 10-bit color. Windows has no switch for the bits per channel. When the two switches exist and the display can show wide color, 10-bit turns wide color on, which composes the desktop above 8 bits without changing the picture, and leaves HDR as it is. It never turns HDR on, which would change the whole picture. Without a wide color switch it turns nothing and the log says the display cannot show 10-bit color. Any other `bitdepth`, including 8, turns nothing. Together with `cm srgb`, which turns both switches off, 10-bit cannot be shown, and the log says so; the switches still go off. The monitors reply's bit depth is the one Windows reports for the link, which turning wide color or HDR on does not always raise, and its `currentFormat` is `XRGB2101010` when that depth is at least 10, `XRGB8888` when a depth below 10 is known, and empty when it is not.

`supports_wide_color` and `supports_hdr` are -1, 0 or 1. -1 says the display cannot, 1 says it can, and 0 uses what Windows reported. They change what a preset and `bitdepth, 10` will turn. HDR requires wide color, except before the two switches exist, where wide color has no bit of its own and only `supports_wide_color, -1` takes HDR away. On their own they turn nothing. The monitors reply's `hardwareDetails` are `backend` `windows`, `hdr` from whether the display can show HDR, `chroma` from whether Windows reported color primaries, `bt2020` from whether it can show wide color, and `vrrCapable` false. Those two fields do not change `hardwareDetails`.

`sdrbrightness` and `sdrsaturation` default to 1, `sdr_min_luminance` to 0.2 and `sdr_max_luminance` to 80. The monitors reply reports them. They are multipliers the pinned release applies while it draws. Windows publishes no equivalent Winland can set: the SDR white level it reports cannot be written, and Winland does not tonemap, so they do not change the picture. `min_luminance`, `max_luminance` and `max_avg_luminance` at or above 0 replace the mastering luminance Winland stores for that display. Windows has no call that sets it, and the monitors reply does not carry those three. Below 0, or left out, keeps what Windows reported, or -1 when it reported none.

A switch Winland changes is put back when the rule no longer asks for it, when Winland exits cleanly, and on the next start when the previous run did not. A switch that already had the value the rule asks for is not remembered, so exiting leaves it as it was. `icc` and `sdr_eotf` warn "Monitor color management other than its cm preset is not honored."

Transforms 0, 1, 2 and 3 ask for a rotation of 0, 90, 180 and 270 degrees. Winland sets the display to that orientation with the system display settings whenever the monitors are laid out, and changes nothing when the display already has it. Transforms 4, 5, 6 and 7 flip the picture. They warn "Flipped monitor transforms are not honored." and are not applied.

A monitor rule's `mirror, NAME` makes the monitor show the same picture as the monitor NAME, a display name or `desc:`, as in the pinned release. Winland asks Windows to show the two displays as one, as Duplicate in Display settings does, and does not save that, so the layout Windows keeps stays as it was. Windows picks a resolution both displays can show, so the source can change resolution too. The mirror is not part of the layout: its Workspaces move to the first other Monitor, `monitors` leaves it out, and `monitors all` lists it with `disabled` false and `mirrorOf` the id of the Monitor it shows. The mirror's own position, mode, scale, transform and `cm` preset are not applied. A monitor cannot mirror itself, a mirror, or a monitor that is disabled or not connected, and a monitor another one mirrors cannot become a mirror. A rule whose source is not connected yet mirrors once it is, and a mirror whose source goes away is a Monitor of its own again. Windows shows two displays as one only when one graphics adapter drives both; when it cannot, the log says why, the displays are left alone, and Winland tries again once the rule has gone away and come back. When the rule goes away or Winland exits, the display gets back the picture it showed, at its old resolution and position. After Winland stops without cleaning up, the next start does it.

A monitor rule's `vrr`, `misc:vrr` of 2 or 3, an ICC profile and `sdr_eotf` stay Gaps. `misc:vrr` of 0 or 1 is honored; see [Window properties](#window-properties).

## Dispatchers

`winlandctl` reads an argument that starts with `-` as a flag unless it is a number. A number may have a fraction and one trailing comma, so `winlandctl dispatch splitratio -0.1` and `winlandctl dispatch moveactive -50, 0` pass their numbers to the dispatcher.

In dwindle, `layoutmsg splitratio` changes the split of the focused Client's parent, by a delta or with `exact` to a value, clamped from 0.1 to 1.9. As in the pinned release, it answers `error: splitratio requires an arg` without a ratio, `error: cannot alter split ratio on no / single node` for a Client with no sibling, and `error: bad layoutmsg 'splitratio'` for a ratio that does not parse, in that order.

`movecursor X Y` puts the cursor at that point on the desktop and handles it as a pointer move, so focus follows it as it follows the mouse, as in the pinned release. `cursor:no_warps` does not stop it. Coordinates may be split by a space or a comma.

`forcerendererreload` returns ok and does nothing. Reloading a renderer has no Windows meaning.

A window selector `tag:` takes a pattern that must match one of a Client's tags in full. `stableid:` takes the `stableId` that `clients` reports, in hex, and matches it exactly.

Window tags are kept as in the pinned release. `tagwindow tag [window]` tags the window, or the focused one: `+tag` sets the tag, `-tag` clears it, and a bare tag toggles it. A `tag` window rule gives a dynamic tag, which `clients` lists with a trailing `*`, beside a static tag of the same name. The tag rules are matched again whenever a window's state changes, so `tag +fs, fullscreen:1` tags a window only while it is fullscreen. `tag:` in a window rule matches a static or a dynamic tag, and `tag:negative:name` matches a window without it. `clients` lists the tags in order.

The `content` window rule gives a window a content type: `none`, `photo`, `video` or `game`, or 0 to 3, and anything else is none. Windows reports no content type, so a window has one only from a rule, set when it opens. `content:` matches the type's number or its name, and `clients` reports the name as `contentType`.

Besides the property effects, `opacity`, `opaque`, `idle_inhibit`, `no_focus` and `stay_focused` are matched again as a window's state changes, as in the pinned release.

`killwindow` ends the process that owns the Client, read from the window again when the kill runs. A Store app's frame belongs to ApplicationFrameHost, which hosts every Store app, so its Client's process, `pid` in `clients` and the `pid:` selector are the app hosted in the frame. ApplicationFrameHost itself is never ended: a frame that hosts no app is left alone.

`cyclenext` focuses the next Client on the focused Client's Workspace, in the order the Clients opened, and wraps around, as in the pinned release. A window selector after a comma names the Client instead, and the cycle runs on that Client's Workspace, then focuses the Client it lands on and shows that Workspace when it was not the one on screen. `prev` goes the other way. `tiled` or `floating` alone takes only that kind of Client, and both or neither take either. Minimized Clients, hidden Group members and `nofocus` Clients are skipped. `tiled` from a tile in master or monocle runs that Workspace's `cyclenext` or `cycleprev` instead. With nothing focused, the first Client on the focused Monitor's Workspace takes focus. Other words are ignored.

`swapwindow` exchanges two Clients, by a direction or a window selector. A Client on another Workspace trades Workspaces with the focused one, each taking the other's slot, as in the pinned release, and the focus stays on the shown Workspace with the Client that came onto it. A Client in a Group does not swap across Workspaces. The answers are the pinned release's: `error: Can't swap fullscreen window`, `error: No window to swap with in that direction`, `error: No window to swap with` and `error: Can't swap a window with itself`.

`dpms` asks for display power on, off, or toggled. An empty monitor list addresses every display. A monitor name that matches none of the enabled monitors still addresses every enabled monitor. The adapter posts `SC_MONITORPOWER` to Winland's own window, which turns every display off or on together, and does not wait for any other window. Turning the displays on also sends a zero mouse move, because Windows does not reliably honor the "on" command. Tests do not send either. `misc:mouse_move_enables_dpms` turns every display back on at the first pointer move or swipe after `dpms` turned them off, and `misc:key_press_enables_dpms` at the first key press or release, as in the pinned release. Both default to false. Windows itself still wakes the displays on any input, so with them false the displays come back on, but `dpmsStatus` stays false until a `dpms` turns them on. `animation:fadeDpms`, on by default as the `fade` it inherits from, fades every display to black before they turn off and from black after they turn on, as the pinned release does. The black is a click-through window over all of them. The fade from black starts when Windows says the displays show again, or 1.5 seconds after they were turned on. Input that wakes the displays by itself also fades the black away, so it never stays over displays that are on. A `dpms on` during the fade to black fades back from where it got to.

`movefocus` in dwindle and master, and `movewindow` in master, with a direction from a tiled Client look at the Clients whose edge touches or slightly overlaps that side and shares more than a pixel of it. `binds:focus_preferred_method` decides among them. It defaults to 0, which picks the one focused most recently, and a Client that was never focused comes after every one that was. 1 picks the one that shares the longest edge. A tie goes to the Client that opened first.

In dwindle and master, `movefocus` and `swapwindow` with a direction from a floating Client look only at floating and covering Clients, as in the pinned release. A candidate's center must lie within 90 degrees of the direction. One within 54 degrees beats a wider one, and among those the nearest center wins. A tile is never picked.

`general:no_focus_fallback` defaults to false. True makes a `movefocus` that finds nothing to focus, on its Workspace or on a neighbouring Monitor, answer `error: Nothing to focus to in direction left`, or `right`, `up` or `down`, as in the pinned release.

`movefocus`, `cyclenext`, `focusurgentorlast` and `focuscurrentorlast` move the cursor to the middle of the window they focus, or to its last point there with `cursor:persistent_warps`, as the pinned release's switch to a window does. Leaving a fullscreen window for another on its Workspace does not move the cursor, and `cursor:no_warps` stops it.

`binds:window_direction_monitor_fallback` defaults to true. `movefocus` continues onto the neighbouring Monitor when nothing in that direction can take focus. There it focuses the Client that shares the most of the edge, where a fullscreen Client covers its whole Monitor, floating or not, and a tie goes to the Client focused most recently, as in the pinned release. `movewindow` continues when the point just outside the Client lies on another Monitor, and the Client goes in at that point there, as in the pinned release. As in the pinned release, a tile that meets the edge of the work area less `gaps_out` reaches the Monitor's edge for that point, so it crosses. The Workspace it left is laid out again. Master, monocle and scrolling also continue when the move cannot be made inside the Workspace. False stops at the Monitor edge. A window selector after a comma names the Client, which moves on its own Workspace and Monitor. A direction leaves the focus where it was when that Client is not the focused one, except in master, where a swap with the focused Client leaves the focus on the tile the focused Client held. A direction onto the neighbouring Monitor does not follow when the Client was not focused. `mon:` follows unless silent. A relative monitor selector stays relative to the focused Monitor.

A Workspace with a fullscreen or maximized Client offers no window to `movefocus` in a direction, as in the pinned release, so focus continues onto the neighbouring Monitor or stays. When the scrolling Layout holds that Client, `movefocus` moves in the direction if `binds:movefocus_cycles_fullscreen` is on and `misc:on_focus_under_fullscreen` is not 0. `binds:movefocus_cycles_fullscreen` (default false) makes `movefocus` from a fullscreen or maximized Client the default way focus the next window on its Workspace in the order they opened, or the previous one for `l` and `u`. `misc:on_focus_under_fullscreen` then decides what happens to the fullscreen mode.

`workspace` naming a Workspace another Monitor shows focuses that Monitor and moves the cursor onto it, as in the pinned release. `binds:workspace_center_on` decides where: 1, the default, the middle of the Client it focuses, and 0 or a Workspace without a Client, the middle of the Monitor. A cursor option that warps after a Workspace or Monitor change, such as `cursor:warp_on_change_workspace`, wins over it. `cursor:no_warps` stops it, as it stops every warp the pinned release does not force.

`binds:workspace_back_and_forth` defaults to 0. With 1 or `all_monitors`, `workspace` and `focusworkspaceoncurrentmonitor` asking for the Workspace the focused Monitor shows go to the Workspace visited before it, on any Monitor. With 2 or `per_monitor` they go to the one visited before it on the focused Monitor. Without such a Workspace the Monitor stays where it is. The history keeps a visit to a Workspace that was removed until it is read for a previous Workspace, as in the pinned release. That read drops the visits to removed Workspaces, except the newest one of each Monitor before that Monitor is seen again further down. `true` and `false`, as older configs write it, are 1 and 0. `binds:allow_workspace_cycles` defaults to false, and true records a Workspace visited again right after itself as visited again, so it takes the Monitor it is on now, as in the pinned release. It does not change the order of the history.

`renameworkspace WORKSPACE NAME` gives a Workspace a new name, as in the pinned release. `WORKSPACE` is its number, its name with or without `name:`, or `special` or `special:name`. Everything after it is the new name, and none leaves the name empty. The Workspace keeps its address, so `workspace`, workspace rules and the other dispatchers still find it by the name it was created with, not the new one, and the `workspaces` reply shows the address in `address` and the new name in `name`. A rule's `defaultName` no longer replaces the new name. A rule selector that reads the name, such as `n[s:...]`, reads the new one. Renaming a special workspace does nothing and returns ok. A Workspace that does not exist is an error. A rename emits `renameworkspace>>ADDRESS,NAME`.

`changeworkspaceid WORKSPACE ID` gives a numbered Workspace a new number, as in the pinned release. `WORKSPACE` is read as `renameworkspace` reads it. The new number must be positive and no Workspace may have it, and a named or special Workspace cannot change its number. A refused change is an error. The Workspace keeps its Clients, its Monitor and its place in the Workspace history, so `workspace previous` reaches it under the new number. The workspace rules for the new number apply. A Workspace that was not renamed takes the new number as its name. The change emits `changeworkspaceid>>OLD,NEW` and no other event. A number goes up to 4294967295, as in the pinned release, which keeps a Workspace number in 32 unsigned bits, and the rest of the Workspace addressing takes the same range.

`focusmonitor`, `movecurrentworkspacetomonitor`, `moveworkspacetomonitor` and `swapactiveworkspaces` address a Monitor by its name, a `desc:` prefix of its description, a direction, `current`, a relative `+N` or `-N`, or its id. Changing the focused Monitor emits `focusedmon`. `focusmonitor`, and `movefocus` onto another Monitor, put the pointer in the middle of a Monitor with nothing to focus, as in the pinned release, unless `cursor:no_warps` is set. A Monitor with a special Workspace open gives the focus to that Workspace's window. Moving a Workspace onto another Monitor emits `moveworkspace`. `workspace` and `workspacev2` are emitted when a Monitor's shown Workspace changes and the focus may follow that change, and when `swapactiveworkspaces` changes the Workspace the focused Monitor shows. Focusing a Monitor that already shows its Workspace emits `focusedmon` and not `workspace`. `setworkspace` on a Monitor that is not focused does not emit `workspace` for the Workspace it shows; when that takes the Workspace the focused Monitor was showing, `workspace` names the Workspace that Monitor shows next. A Monitor coming or going emits neither.

Moving the Workspace a Monitor shows onto another Monitor leaves its pinned Clients on the source Monitor, on the Workspace that Monitor shows next, as in the pinned release. Moving or swapping a normal Workspace does not move the special Workspace shown on that Monitor. The cursor is not forced to the center of the destination Monitor. Warps follow the cursor settings.

`pin` toggles whether a floating Client is pinned. A fullscreen or maximized Client does not qualify, as in the pinned release. `enable` and `on` pin it. `disable` and `off` unpin it. A window selector after that word, or in place of it, chooses the Client. A tiled Client does not qualify. Changing the pin emits `pin` with the address and `1` or `0`. The same request again emits nothing. A pinned Client moves onto the Workspace its Monitor is showing, and it is not hidden when that Monitor switches Workspace. Unpinning leaves it on that one Workspace. A pinned Client that is focused stays focused across the switch. Changing whether a Client floats clears the pin and does not emit `pin`. `movetoworkspace` and `movetoworkspacesilent` do not move a pinned Client onto a special workspace, as in the pinned release, and `movetoworkspace` still opens that special workspace on the focused Monitor and keeps the Client focused, as there.

`binds:allow_pin_fullscreen` is honored, as in the pinned release. With it on, a pinned Client that goes fullscreen or maximized is unpinned while in that mode, and `clients` shows it with `pinFullscreened`. Leaving the mode pins it again, and it follows the Monitor's Workspace as before. With it off, the default, `fullscreen` and `maximize` do nothing to a pinned Client while `sync_fullscreen` is true, and `fullscreenstate` sets only its client mode. While `sync_fullscreen` is false, they leave the client mode and set the internal mode back to 0. A pinned Client is not raised above other windows. Placement does not change z-order. A window owned by a pinned Client, such as its dialog, opens pinned when it floats, as the pinned release pins the child of a pinned parent.

## Fullscreen

`fullscreen` toggles the focused Client. An argument of `1`, `maximize`, or `maximized` toggles maximize. Any other argument, including `0` and `2`, toggles fullscreen. A second argument `set` or `unset` forces that mode on or off. An unrecognized second argument does nothing. A last word `default` asks for the default fullscreen below instead of the Layout's. `maximize` is the same toggle as `fullscreen 1`.

Mode 0 is the layout slot. Mode 1 resizes the Client to its Workspace's work area less `gaps_out`, or less `general:float_gaps` for a floating Client, and keeps its border inside that area, as in the pinned release. A maximized Group member leaves room for its bar, floating or tiled. Mode 2 resizes it to the monitor rectangle and drops the border. The window's frame style comes back when it leaves mode 2, when it stops being a Client, and on a clean exit. The style it had is recorded, and after a crash the next start writes it back. While a Client is in mode 1 or 2, the dwindle tree is not refit, and mode 0 restores that same slot. `movewindow` in a direction, `swapwindow`, and the dwindle `togglesplit`, `swapsplit`, `rotatesplit` and `movetoroot` refuse a Client in mode 1 or 2, as in the pinned release. `rotatesplit` refuses without an error. One covering Client replaces another on the same Workspace. Moving that Workspace onto another Monitor resizes the covering Client to the destination. A Client moved to another Workspace or Monitor keeps both its modes there and replaces a covering Client already there, as in the pinned release. A Layout change on reload keeps them too.

`fullscreenstate` takes an internal mode and a client mode. `-1` keeps the current value. Any other value is clamped to 0, 1, or 2, so a 3 is fullscreen. Passing the pair the Client already has turns both modes off. A kept value counts as the current one there, as in the pinned release, so on a Client at `1 0`, `fullscreenstate -1 0` and `fullscreenstate -1 -1` turn both modes off. An optional third word `set`, `toggle` or `unset` follows the pinned release's actions instead: `set` applies the pair unless the Client has it, `toggle` turns off each mode that already has its value and sets the other, and `unset` turns both off when the Client has the pair. A word `default` after that asks for the default fullscreen. A window selector after that, such as `fullscreenstate 1 1 set class:kitty`, picks the Client instead of the focused one. As in the pinned release, a maximized Client given client mode 2 is marked, and asked for client mode 0 while marked it gets client mode 1 instead. The mark goes once its internal mode is not 2. The internal mode is the placement above. The client mode is stored and reported as `fullscreenClient`. It is not sent to the application. Windows has no fullscreen state separate from the window rectangle, so a client mode by itself does not move the Client and cannot make an application believe it is fullscreen.

On a Workspace with the scrolling Layout, a tile that goes fullscreen or maximized is laid out by the Layout, as in the pinned release. It moves to a column of its own, which becomes as wide as the Monitor when fullscreen and as wide as the view when maximized, and the column is centered or fitted by `scrolling:focus_fit_method`. The Client covers the Workspace only while its column fills the view. A fullscreen one then fills the Monitor without a border. A maximized one fills the work area less `gaps_out`, keeps its border, and leaves `gaps_in` on each side that has a column next to it. When focus moves to another column the strip scrolls as usual, and the Client keeps its mode, its height and its place on the tape. Several tiles can hold such a mode at once, and a floating Client that goes fullscreen does not end it. Leaving the mode gives the column back the width it had and fits it into view again. A tile that comes to share its column, by `consume` or a move, leaves the mode. A floating Client, a tile in another Layout, and a request with `default` use the default fullscreen. `clients` reports which in `fullscreenHandler`: `scrolling` for a Client the scrolling Layout holds and for a tile in that Layout that is not fullscreen, and `default` otherwise. A fullscreen Client that moves to another Workspace keeps the default fullscreen, and keeps the scrolling Layout's when it lands in another scrolling Layout.

Each window has the pinned release's `allowedOverFullscreen` flag, which `clients` reports and which is true until a fullscreen takes it. When a Client goes fullscreen or maximized the default way, every other window on its Workspace that is not pinned loses the flag, and gets it back when that ends. On a scrolling Workspace, the floating windows that were open when a tile went fullscreen lose it, while floating windows opened after keep it; showing another held tile, or a floating fullscreen ending, applies that again. A floating window that opens, floats, is raised with `alterzorder top` or is focused over a default fullscreen gets the flag, and `alterzorder bottom` takes it. A window without the flag while a Client covers its Workspace is reported as neither `visible` nor `acceptsInput`. A floating one is lowered behind the covering Client then, and raised again when it gets the flag back.

`misc:on_focus_under_fullscreen` decides what happens when a tiled Client is focused on a Workspace where another Client is fullscreen or maximized, as in the pinned release. That covers `focuswindow`, a window that takes the foreground, and a tiled window that opens there. `0` or `ignore` keeps the covering Client focused, and a new window opens without focus. `1` or `take_over` moves the covering Client's mode to the focused Client. `2` or `exit_fullscreen`, the default, ends the covering Client's mode. A floating Client is focused over the covering one and changes nothing, and a window that opens with a fullscreen rule takes its own mode. Focusing a tile beside a Client the scrolling Layout holds fullscreen changes nothing either: the strip scrolls to the tile. A tiled window that opens there still follows the option.

`misc:exit_window_retains_fullscreen` passes the mode of a focused fullscreen or maximized Client that closes to the Client that takes the focus, as in the pinned release. `0`, `false` or `disable`, the default, passes nothing. `1`, `true` or `enable` always passes it. `2` or `only_when_grouped` passes it only to the next member of the closed Client's Group, and `3` or `only_when_nongrouped` only to a Client outside it. Without it, the Group member that takes a closed member's place does not take its mode.

`sync_fullscreen` defaults to true. While it is true, `fullscreen` and `maximize` store the client mode equal to the internal mode, and a maximize request from the window does too. While it is false, they change only the internal mode and leave the client mode. A window rule `fullscreen` or `maximize` does the same when the window opens. `fullscreenstate` stores the two modes as given, then sets `sync_fullscreen` as `setprop` would: true when the modes it left are equal and false when they are not. A `fullscreen_state` window rule stores the two modes and sets the property false while that rule matches, ahead of a `sync_fullscreen` rule. `setprop` still wins over both. The client mode is still not sent to the application. A window rule `suppress_event` is not honored. An application that asks to be fullscreen is not observed, so a maximized Client does not return to maximized after the application leaves fullscreen on its own.

Hyprland has no minimize, so Winland has none either. When a Client is minimized, by its button, `Win+Down`, `Win+M` or a double click, Winland restores it at once and the Client keeps its place. A window that is already minimized when Winland starts is not adopted until it is restored, and a minimized window is not put back into the Layout when Winland restarts.

A Client's maximize request is maximize mode 1, as in Hyprland: its maximize button, `Win+Up` or a double click on the title bar maximizes it, and asking again leaves it. It acts on that Client, whichever window has focus. The system's own maximized state is undone, so the Client fills the work area as `fullscreen 1` does. A window that opens maximized while Winland runs asked for it before it mapped, which the pinned release ignores, so it is tiled like any other window. Its maximize button works as usual afterwards. A window that was maximized before Winland started is adopted maximized.

A `fullscreen` window rule requests mode 2. A `maximize` window rule requests mode 1. A trailing `0` turns that flag off. `fullscreen_state` sets the two modes, for example `2 0`, and wins over those flags. A popup window with no caption that already covers its monitor is not adopted.

## Plugins

`winlandctl plugin install <git-url> [revision]` clones the repository and builds the plugins its manifest lists, then installs them. A repository that is already installed is refused. A revision checks out that commit, branch or tag. `update` rebuilds a repository only when its commit changed, or every repository with `--force`. `remove` takes a repository URL or one of its plugin names and removes the whole repository. `list --installed` lists the installed repositories and their plugins. The manifest, the build and the approval are in [plugins.md](plugins.md).

## Modifiers

A modifier list in a bind, a gesture's `mod:` and `sendshortcut` is read as the pinned release reads it: the list is upper-cased and each modifier name found anywhere in it counts, so `SUPER SHIFT`, `SUPER_SHIFT`, `SUPER+SHIFT`, `$mainMod_SHIFT` with `$mainMod = SUPER`, and `super shift` are the same. `SUPER`, `WIN`, `LOGO`, `MOD4` and `META` are the Windows key, `ALT` and `MOD1` are Alt, `CTRL` and `CONTROL` are Ctrl, and `SHIFT` is Shift. `CAPS` is the Caps Lock key and `MOD2` the Num Lock key while they are held, not their lock, as the pinned release reads the modifiers held and latched and not the ones locked. `MOD5` is AltGr held, on a keyboard layout that has it, where the right Alt key is `ISO_Level3_Shift` and not Alt. No key holds `MOD3`, as on the pinned release's default keymap, so a bind that needs it never fires. `binds` reports them in `modmask` with the pinned release's bits: 2, 16, 32 and 128. `sendshortcut` and `pass` send a key without them, since holding Caps Lock or Num Lock down would turn its lock over. A list that names none of them warns `Invalid modifier` and the bind is skipped.

A bind on a modifier key, such as `Super_L`, is matched on its press without that key's own modifier, so `bind = , Super_L` runs when Super goes down alone. On the release the mask includes the key's own modifier, as in the pinned release, so `bindr = SUPER, Super_L` runs when Super is let go and `bindr = , Super_L` never runs: its press swallows Super, and its release matches nothing and is swallowed too. Super and its release still reach Windows under `bindr = SUPER, Super_L`, so Winland sends a mask key before the release, and Start does not open.

A release bind matches the modifiers its key went down under, as in the pinned release, so `bindr = SUPER, Q` does not run for a Q pressed before Super. A release bind on one key is skipped when, while its key is held, a bind catches another key or any other key is let go: `bindr = ALT, Alt_L` does not run after Alt+P ran `bind = ALT, P`, and `bindr = SUPER, Q` does not run when Super is let go before Q.

## Several keys

A bind with the `s` flag and its keys joined by `&`, such as `binds = , Tab&T, exec, kitty`, runs once its keys are held in that order, with no other key held, when the last one goes down. The keys are matched in the order they went down, so `B`, `A`, `C` does not run `A&B&C`. A press that starts or extends the chord is swallowed unless the bind has the `n` or `r` flag. A key that does not extend it reaches the window. A bind on one key that a longer chord starts with waits: `bind = SUPER, Q` beside `binds = SUPER, Q&K` runs when Q is released alone, and not at all once K completes the chord. A completed chord stops the shorter binds inside it from running on the release of its keys. With the `r` flag the chord is armed when its last key completes it in order, and runs when that key is released.

While a key with a bind is held, another key pressed under the same modifiers is swallowed, as in the pinned release: with `bind = SUPER, Q` held, Super+H reaches no window.

## Sending keys

`pass` sends the key of the bind that ran it to the Client the window selector names. The press goes on when the key goes down and the release when it comes up, so a `pass` bind runs on the release too without the `r` flag. The modifiers the user holds are left as they are. A selector that matches no Client answers `pass: window not found`.

`sendshortcut` takes modifiers, a key, and a window selector. It sends the key with exactly those modifiers down. A modifier the user holds that is not named is let go around the key and pressed again after it, if the user still holds it then. A `sendshortcut` bind presses the key on the press and releases it on the release. From the pipe it presses and releases at once. A number above 9 and `code:N` are keycodes, `mouse:272` to `mouse:276` are the left, right, middle, side and extra buttons, and anything else is a key name in the focused window's keyboard layout. An empty selector sends to the focused window. A bad argument answers `invalid args`, `invalid modifiers`, `invalid mouse button`, `invalid key`, `key not found`, or `window not found`, after the dispatcher name.

`sendkeystate` takes modifiers, a key, a state, and a window selector. `down` presses the key, `repeat` presses it twice, and `up` releases it. Any other state is an error.

A sent key is tagged, so Winland's own hooks let it through and it never runs a bind.

Every 2 seconds, and on unlock, Winland lets go of a modifier that Windows holds down but the user is not holding, such as one whose release was lost. A modifier a `sendkeystate` left down on purpose is kept. The check waits while the keyboard hook may have missed a key.

## Urgency

A window that takes the foreground is handled as an activation request, as in the pinned release, which honors one only with a fresh input serial. A window that takes the foreground with no click or key just before it has none, so the focus goes back, whatever `misc:focus_on_activate` says. A window of one program that takes it right after a click in a Client of another program has one: it keeps the focus only with `misc:focus_on_activate`, default false, or a `focus_on_activate` window rule or property, which wins. Any other change after a click or key is the user's own: a click on the window itself, a key such as Alt+Tab, a click on a window Winland does not manage such as the taskbar, the Start menu or a notification, and a window of the program that was clicked. A Client is urgent when it flashes for attention, and when it takes the foreground and the focus is sent back. Each emits `urgent` with the Client's address. The focused Client flashing is not urgent. Focusing a Client clears its urgency.

`focusurgentorlast` focuses the first urgent Client in Workspace order and switches to its Workspace. With none, it reads the focus history from its oldest end, as the pinned release does: with a Client focused it takes the second oldest, and with none the oldest. That is the Client focused before the current one only while two Clients have been focused, and it can be the focused Client itself, which changes nothing. With neither it answers `error: window not found`.

`focuscurrentorlast` focuses the Client focused before the newest one in the focus history, and switches to its Workspace, as the pinned release does. With fewer than two Clients in the history it answers `error: History too short`. `hl.dsp.focus({ last = true })` writes it.

## Swallowing

`misc:enable_swallow` defaults to false. `misc:swallow_regex` is the class a parent Client must match in full, and an empty value swallows nothing. `misc:swallow_exception_regex` is a title that keeps a parent from being swallowed. With swallowing on, a new Client whose process descends from a parent Client's process swallows that parent: the parent leaves its Layout, so the child takes its place, and the parent is hidden. When more than one parent matches, the one focused most recently is swallowed. A parent that is already swallowed is not swallowed by a second child. A parent shown in a Group hands its place in the Group to the child, and the Group stays in the Layout, so the child is placed in that tile and the other members stay in the Group. The parent takes the place back when the child closes. A hidden member is not swallowed. A parent whose Group is on another Workspace is swallowed the same way: the child leaves the Workspace it opened on and takes that place, and when that Workspace is not shown and the open is not silent, focus follows the child there. A Group that denies new windows, or that the child may not join, keeps its parent unswallowed. A child that swallows its parent does not join the focused Group under `group:auto_group`: in the pinned release a swallow and auto-grouping are alternatives. A child that took its parent's place in a Group does not also join the focused one. The process tree is read up to 25 levels, as in the pinned release.

The child reports its parent as `swallowing` in `clients`. The parent stays in `clients` as hidden, on the child's Workspace, and a window selector finds it, but it is out of the Layout, so the Workspace's `windows` count leaves it out, as in the pinned release. A child can be swallowed in turn. When it closes while hidden, the parent it swallowed comes back on the Workspace of the child that hid it. When the child closes, including when its process ends without closing it, the parent returns to the child's Workspace, is shown, and takes the focus if the child had it. A child that has joined a Group since gives the parent back as its own tile, and the Group goes on without the child. A parent that shows itself while swallowed is hidden again. A parent that closes while swallowed is forgotten.

A swallowed parent is a hidden Client, so it is shown on a clean exit, and after a crash it is shown on the next start. A child still open at that start swallows it again.

`toggleswallow` shows the parent of the focused Client, or hides it again. On a shown parent it hides the parent again and focuses the child, as in the pinned release. A parent shown this way stays when the child closes. A child that took its parent's place in a Group trades places with it instead: the parent comes back into the slot and the child is hidden, still listed and still `swallowing` it, and the next `toggleswallow` trades back. The slot's internal fullscreen mode stays with the slot, and each Client keeps its own client mode, as in the pinned release. When the parent closes while it holds the slot, the child takes the slot back.

## Idle inhibit

The `idle_inhibit` window rule takes `none`, `always`, `focus`, or `fullscreen`. `always` keeps the system and the display awake while the Client is open, on any Workspace. `focus` does so while it is the focused Client. `fullscreen` does so while it is fullscreen or maximized on a shown Workspace. `none` does nothing. Any other mode warns and the rule is skipped. The last matching rule wins. `clients` reports `inhibitingIdle` for each Client.

## Animations

`animations:enabled` defaults to true. False, or the Windows setting **Animation effects** turned off, moves every window at once. `animations:workspace_wraparound` defaults to false. When it is on, a switch between the lowest and highest numbered Workspaces slides as if they were neighbours.

`bezier = NAME, X0, Y0, X1, Y1` names a cubic Bézier curve. `default` (0, 0.75, 0.15, 1) and `linear` are always defined. `animation = NAME, ONOFF, SPEED, CURVE[, STYLE]` sets one node of the animation tree. SPEED is in tenths of a second. A node that is not set takes the values of its nearest set parent, and `global` starts at on, 8, `default`. Both lines are read in config order and may also be written inside `animations { }`. A missing node, a speed that is not above 0, or a curve not defined above the line warns and is skipped. A CURVE of `spring:NAME` names a spring curve, from a spring `hl.curve`: a mass on a spring with damping, let go at rest and pulled to its goal, solved exactly as the pinned release's animation library steps it. A node on a spring runs until the spring is within 0.001 of its goal and slower than 0.001 a second, so its SPEED changes nothing, as in the pinned release, and an underdamped spring overshoots and bounces before it settles. A style that is not valid for its node warns and is still kept.

These nodes animate:

- `windowsIn` and `fadeIn` when a window is adopted. The default style `popin [N%]` grows it from N percent of its size, at least 5 pixels, around its middle. `slide [top|bottom|left|right]` brings it in from the nearest monitor edge or the side named, and `gnomed` unfolds it from a line across its middle. The window fades in from transparent.
- `windowsOut` and `fadeOut` when Winland closes a Client. The window plays the same style in reverse and fades out, and is then asked to close. A window's own `animation` style, from an `animation` window rule or `setprop`, replaces the `windowsIn` and `windowsOut` style it opens and closes with, as in the pinned release, and keeps the node's curve and speed. A window that is still shown 1.5 seconds later is put back on its Layout rectangle at its full alpha.
- `windowsMove` when a shown Client gets a new Layout rectangle, from wherever it is at that moment. A dwindle tile that `resizeactive` or `resizewindowpixel` resizes, and the tiles that make room for it, move at once, as the pinned release's dwindle resize warps them, unless `misc:animate_manual_resizes` is true. Master tiles and floating Clients animate either way, as there. A window dragged or resized with the mouse moves at once. The windows its Layout moves to make room for a tile lifted out by a drag, or dropped back in, animate, as in the pinned release, and a mouse resize moves every window at once. A Client going into or out of fullscreen mode 2 moves between its rectangle and the Monitor's the same way, as in the pinned release: its frame is dropped or put back when the motion starts, and it is drawn by a stand-in while its size changes. One that stays fullscreen, such as on a Monitor change, is put in place at once.
- `workspacesIn` and `workspacesOut` when a Monitor switches Workspace, and `specialWorkspaceIn` and `specialWorkspaceOut` when a special workspace is shown or hidden. Styles are `slide`, `slidevert`, `fade`, `slidefade` and `slidefadevert`, with an optional travel percentage such as `slidefade 20%` and an optional side. A Workspace with a higher number comes in from the right. A `slide` or `slidevert` travels the monitor's width or height and `general:gaps_workspaces` more, so the two Workspaces keep that gap between them; a `slidefade` travels the monitor alone. A special workspace also fades. A leaving window is hidden when its motion ends. A workspace rule's `animation:` style replaces the node's style, as in the pinned release: a switch plays the style of the Workspace switched to, for the Workspace that leaves too, and a special workspace shows with its own style and hides with the style of the special workspace that replaces it on its Monitor, or its own.
- `fadeSwitch` when a Client's opacity changes, for example between `active_opacity` and `inactive_opacity`, and `fadeDim` when its dim changes: `dim_inactive`, `dim_modal` and `dim_special` coming or going. Dimming is folded into the window's alpha, so the alpha is the opacity times what the dim leaves, and each part eases on its own node's curve and speed over the same change. `fadeDim` falls back to `fade` and then `global`, as in the pinned release, and a part whose node is off applies at once while the other eases.
- `border` when a Client's border color changes. The colors blend in the OkLab space.

The adapter moves each window with `SetWindowPos` and sets its alpha with `WS_EX_LAYERED`, once per composed frame, on a thread of its own, so binds and window events are never kept waiting. A frame does not wait for the window to take it, so a window that is slow to lay itself out does not hold up the others, and a window still busy with the last frame skips the next ones until it catches up or three frames have passed. A frame that keeps the size only moves the window. The steps of a drag that is still held are sent the same way, and the drag's end places every window exactly. A window already on its Layout rectangle is not moved again, and the moves Winland makes are not taken for the user's, so the window's size limits are not read again for them. A motion that starts while another runs carries on from where the window is. A placement that arrives without a motion stops the window's movement, so the window always ends on its newest Layout rectangle, and a hidden window is put back on its Layout rectangle while hidden. A window cannot be made smaller than its own minimum size, so a small `popin` start or `gnomed` starts at that minimum.

A window whose size changes during a motion is given the size it rests at when the motion starts, as Hyprland sends a window its goal size, so it lays itself out once: a window that grows, one that shrinks, and the `popin` and `gnomed` styles of `windowsIn` and `windowsOut`. A closing window keeps its size and is not moved at all. Until the motion ends the window is made transparent and a window of Winland's own shows its picture in each frame's rectangle, scaled to it, as Hyprland draws the surface of a window that animates its size: the picture is stretched to the animated box, a window that has not yet painted its new size is shown at its painted size times the box's share of the final size, and one larger than its final size is squeezed into the box. A window takes several frames to paint a new size, so a window resized on every frame would show its unpainted area along its growing edges or lay itself out on every frame. The window's border, shadow and glow follow the stand-in's rectangle each frame, not the window's own, and the border and glow are stacked on the stand-in. The window's system backdrop moves to the stand-in for the motion, so it blurs what is behind the stand-in. The backdrop does not fade, so it shows only while the window is fully opaque. While a motion fades a window, its border, shadow and glow are drawn with the same alpha. A window its program already made layered cannot be made transparent, and is resized on every frame instead, and so is one whose picture cannot be shown. A motion that only moves a window, such as a slide, moves the real window, unless the window has wobble or motion blur (see [Wobble and motion blur](#wobble-and-motion-blur)). When a closing window's motion ends it stays transparent while it is asked to close; one that stays open is put back on its Layout rectangle.

### Wobble and motion blur

`decoration:wobble:enabled` and `decoration:motion_blur:enabled` default to false. With either on, a window that moves or resizes is drawn with it, by a stand-in that is not a DWM thumbnail, because a thumbnail can only be scaled and faded. The window is captured with Windows.Graphics.Capture (without the cursor or the capture border), the picture is drawn with Direct3D 11 on the machine's graphics adapter, and the frame is shown in a click-through layered window of Winland's own, just above the window, with the window's alpha. The real window is given the rectangle it rests on when the motion starts and made transparent, as for a window that changes size (see above), and shows again when the effects are done. A window that the pointer drags or resizes is drawn the same way, each step behind the pointer, and it wobbles on after the drop. A fullscreen Client has neither effect. A Client with the `no_wobble` property, from a window rule or `setprop`, does not wobble but is still blurred.

The wobble is the pinned release's deformable mesh. The window's picture is laid over a grid of `decoration:wobble:mesh` points per edge (default 12, from 2 to 32). Each frame the window moves or resizes, every point is pushed against the move, by the move times a weight that is 0.45 along the window's top and bottom edges for a sideways move (its left and right edges for a vertical one) and 1 across its middle, plus the change of the edge nearest it, times `decoration:wobble:intensity` (default 0.2, from 0 to 2), and no further than a quarter of the smaller side of the window, from 16 to 160 pixels. While a pointer drags the window the push is scaled by each point's distance from where the pointer holds the window, so the held point follows it. A move of more than one and a half times the window's size is a jump and does not wobble. A damped spring pulls each point back to rest, with `stiffness` (default 200), `damping` (12) and `mass` (1), advanced by the exact solution of the spring for the time since the last frame. The wobble ends when every point is within `value_epsilon` (0.25) pixels of rest and `velocity_epsilon` (2) pixels per second of still. It goes on after the motion or drag ends, until then, and a new motion of the window takes it over from where it is. A value past its limit is clamped.

The motion blur averages `decoration:motion_blur:samples` pictures (default 7, from 1 to 64, where 1 draws no blur) of the window, drawn at the boxes between where the window was a frame ago and where it is now. A step of 2 pixels or less on every edge draws no blur, a step older than 100 ms is not blurred, and a pixel the samples do not all cover is partly transparent, as in the pinned release. Dropping a dragged window ends its blur. Wobble and blur together blur the wobbling window.

Everything is drawn in physical pixels of the screen, so a window over two Monitors is one picture. The window's border, shadow and glow are drawn into the same frames as the window, as the pinned release draws them into the window's buffer, so they wobble and blur with it: they are painted round the stand-in's rectangle, the shadow under the window, the glow over its edges and the border round it, and the mesh covers them too. Their own layered windows hide while the frames show and come back when the stand-in ends. When they cannot be drawn into the frames, those windows follow the stand-in's rectangle as a straight box instead. The stand-in's alpha follows `fadeIn`, `fadeOut`, `fadeSwitch` and `fadeDim` as the thumbnail's does. When the effects cannot be drawn, the window shows through a thumbnail without them: the machine has no hardware graphics adapter, Windows will not capture the window or returns no picture, the adapter is removed or reset, or a frame fails. A later motion tries again, and the adapter is asked again after half a minute.

## Groups

A Group is one tile that holds several Clients. Only the shown member is in the Layout. The other members are hidden and keep their Workspace, so they are listed by `clients` with `hidden` true and their `grouped` list. They are recorded as hidden, shown again on a clean exit, and shown again after a crash, like any hidden Client. A Group is not rebuilt after a restart; its members come back as separate Clients.

`togglegroup` makes the focused Client a Group of one, and on a grouped Client ends the Group. Ending a Group leaves the tile to the last member, as the pinned release does, and gives every other member its own tile. A fullscreen Client leaves fullscreen first. Making a Group emits `togglegroup>>1,ADDRESS` and ending it emits `togglegroup>>0,ADDRESS` with the first member, one address only, as the pinned release's source does.

`changegroupactive` shows the next member, or the previous one with `b` or `prev`. A number picks the member at that position, counted from 1, and 0 or less picks the last. The shown member keeps the tile's place, size, floating and fullscreen state in every Layout. Each time the shown member is placed, the hidden members are placed at the same frame, as in the pinned release, so a member is already in place when it is shown. A hidden window stays hidden when it is moved. Focus moves to the newly shown member when the Group was focused. A window that is not grouped is an error, and so is a Group of one. `movegroupwindow` swaps the shown member with the next one, or the previous one with `b` or `prev`, in the Group order. `focuswindow` on a hidden member shows it first. When the focused shown member closes, the member focused most recently is shown and focused, as in the pinned release, and otherwise its neighbour.

`moveintogroup` with `l`, `r`, `u`, `t`, `d` or `b` moves the focused Client into the Group of the Client in that direction. The moved Client becomes the shown member and is focused, and it emits `moveintogroup`. `moveintoorcreategroup` makes that neighbour a Group first. With nothing in that direction on its Workspace, and `binds:window_direction_monitor_fallback` on, the Client looks onto the Monitor in that direction, joins the Group of the Client there that shares the most of the edge, and takes the focus on that Monitor, as in the pinned release. `moveoutofgroup` takes the focused Client, or the Client a window selector names, out of its Group into its own tile, next to the Group, and emits `moveoutofgroup`. `group:focus_removed_window` (default true) focuses the removed Client; false focuses the Group. `movewindoworgroup` moves into a Group in that direction, out of the Group when the neighbour is not grouped, and otherwise moves the Client like `movewindow`. A window selector after a comma names the Client.

A `movewindow` mouse bind pressed on a tab of a Group of more than one takes that member out of the Group and drags it alone, as the pinned release begins a window drag on its group bar, and it is dropped as any dragged window is. On a Group of one, between tabs, or with `resizewindow`, the drag takes the window under the pointer as anywhere else. A window dragged with a `movewindow` mouse bind, or by its title bar, and dropped on a Group joins it, as in the pinned release. `group:drag_into_group` defaults to 1: a window dropped on a member joins after the current member, and one dropped on the tab bar joins at the tab under the pointer. 2 takes it only on the tab bar, and 0 never. A dragged Group brings every member, unless `group:merge_groups_on_drag` (default true) is off, and on a tab bar only with `group:merge_groups_on_groupbar` (default true). A floating window does not join a tiled Group, except on its tab bar with `group:merge_floated_into_tiled_on_groupbar` (default false). A locked Group, either Group locked, all Groups locked, or a rule that denies the window keeps it out.

`lockgroups` locks every Group: no argument, `lock` or `lockgroups` lock, `toggle` toggles, anything else unlocks. It emits `lockgroups>>1` or `lockgroups>>0`. `lockactivegroup` locks the focused Group with `lock`, toggles with `toggle`, and unlocks otherwise. `denywindowfromgroup` stops other windows from joining the focused Group with `on`, toggles with `toggle`, and allows them otherwise. A locked Group refuses `moveintogroup`, `moveoutofgroup` and new windows. `binds:ignore_group_lock` (default false) lets the dispatchers pass a lock. `setignoregrouplock` does nothing, as in the pinned release. `binds:movefocus_cycles_groupfirst` (default false) makes `movefocus l` and `movefocus r` show the previous or next member until the first or last member is focused, and then leave the Group. A Group with nothing beside it on a single Monitor keeps cycling.

`group:auto_group` defaults to true, as in the pinned release's source. A window that opens while a Client of an unlocked Group is focused, on the same Workspace, joins that Group as its shown member. A dialog does not join, and a floating window does not join a tiled Group. `group:insert_after_current` (default true) puts a new member after the shown one; false puts it last. `group:group_on_movetoworkspace` (default false) puts a Client moved onto a Workspace whose only visible Client is an unlocked Group into that Group. Moving the shown member to another Workspace or Monitor takes the whole Group with it.

The `group` window rule takes the options `set`, `new`, `lock`, `invade`, `barred`, `deny`, `override`, `unset` and `always`, separated by spaces. `set` opens the window as a Group, and `lock` locks it. `barred` stops it from joining the focused Group, `deny` stops it from joining any Group, and `invade` lets it join a locked one. The last matching rule wins. `group` with no options is `set`, as the manual says.

`group:col.border_active`, `group:col.border_inactive`, `group:col.border_locked_active` and `group:col.border_locked_inactive` color the border of a grouped Client. The locked defaults are the ones in the pinned release's source, which swaps the manual's two values. `general:col.nogroup_border` and `general:col.nogroup_border_active` color a Client with a `group deny` rule. A gradient keeps its first color.

Winland draws the tab bar itself, in its own window just above the shown member in the z-order, and puts it back there whenever the shown member is raised or shown, or any window changes its place in the z-order, so a window raised over the member's tile covers the bar too and the member raised again brings it back, as the pinned release draws the bar with its window. A tiled Group's bar takes the top of the tile and the shown member is placed below it. A floating Group's bar sits above the window. From the bottom up the bar is `gaps_out`, the indicator (`indicator_height`), `indicator_gap`, the title row (`height`, when `render_titles` or `gradients` is on) and, with `keep_upper_gap`, another `gaps_out`. Tabs share the width with `gaps_in` between them. `stacked` gives each tab its own such row across the whole width instead, the first member at the top, so the bar is one row per member plus the upper gap; a click or a drop picks the row as the pinned release does. Sizes are logical pixels multiplied by the Monitor's scale. The tab of the focused Client uses `col.active` and `text_color`, and the others use `col.inactive` and `text_color_inactive`; a locked Group uses the `locked_` colors. A color's alpha is kept. `rounding` (default 1) and `rounding_power` (default 2, a circle) round the indicators' corners. With `round_only_edges`, on by default, and more than one tab, only the outer corners of the first and last indicator are round. `gradients` fills each tab's title row behind its title with a vertical gradient of that tab's `col.*` colors: the first color nearest the bottom, and a single color filling the row. It is rounded by `gradient_rounding` (default 2), `gradient_rounding_power` and `gradient_round_only_edges` in the same way. The indicators take only the first color of a `col.*` gradient. `blur`, default false, puts a blurred backdrop behind the bar. Winland first asks for DWM's acrylic system backdrop (`DWMSBT_TRANSIENTWINDOW`, the one `decoration:blur:enabled` gives a Client), which the bar's layered window takes, and only if DWM refuses it uses the window composition accent `ACCENT_ENABLE_ACRYLICBLURBEHIND`. A system that refuses both leaves the bar as it was, without a message. The bar's own colors, with their alpha, and its titles draw over the blur. The blur covers the whole bar, the gaps between tabs and the title rows included, where the pinned release blurs only the tab rectangles it fills; the blur is the system's, so its strength and tint cannot be tuned. `font_family` (default `misc:font_family`), `font_size`, `font_weight_active`, `font_weight_inactive`, `text_offset` and `text_padding` are honored. Titles are antialiased: they are drawn white on black into a mask with grayscale antialiasing, and each title's color is laid over the bar as much as the mask covers each pixel, so their edges blend with the strip and the tab colors under them. Titles are read from the windows and redrawn within a second of a change. `enabled` false or `disable_when_only` with one member draws no bar and takes no space. A fullscreen Client in mode 2 has no bar, and neither has a Group whose shown member has `decorate 0`, from a window rule, `setprop` or its workspace rule, as in the pinned release. `priority` (0 to 6, default 3) places the bar among the decorations on a window's top edge. The bar is the only one, as in the pinned release without a plugin that adds one, so the value is kept and changes nothing.

A click on a tab focuses that member, and a click between tabs focuses the shown member. A middle click closes the member when `middle_click_close` is on. The wheel shows the next or previous member when `scrolling` is on, and moves the focus to it only when the member it replaces had the focus, as the pinned release's `moveCurrent` does.

## IPC pipe

A client has 5 seconds after it connects to send its request line, as in the pinned release. One that sends nothing in that time is disconnected. After the reply the Daemon waits up to 30 seconds for the client to close. Each client is served on its own and an idle `events` subscriber holds no thread, so a slow or silent client never keeps another, or a bind, waiting.

The pipe refuses clients on other machines. When another process already holds the pipe name, the Daemon fails to start and says so, instead of sharing the name with it.

`keyword NAME VALUE` applies one config line at once, as in the pinned release. An option such as `misc:focus_on_activate` replaces its value. A line that may repeat, such as `windowrulev2`, `workspace`, `monitor` or a bind, is added after the lines already read, so a window rule applies to the windows that open next and a workspace rule merges into the rule for the same Workspace. A `windowrulev2` or `workspace` line that carries `ruleid` is the exception, as [extensions.md](extensions.md) describes: that window rule's dynamic effects are matched again on windows already open, and that workspace rule is stamped onto the workspaces already there. `exec` and its variants, `env`, `source` and `plugin` answer `error: keyword 'NAME' is not applied live`, because they launch a program, load a file or set the environment, which happens only when the config is read. A keyword the config would warn about answers with that warning. A keyword with no value answers `error: invalid keyword`, but for the `input:kb_` options, which it sets to nothing. `reload` drops every line `keyword` added.

`misc:font_family`, default `Sans`, is the font of the text Winland draws: the error bar, and the tab bar when `group:groupbar:font_family` is empty. The generic names `Sans`, `sans-serif` and `system-ui` are Segoe UI, `Serif` is Cambria and `Monospace` is Consolas; any other name is used as it is.

`rollinglog` answers with the last 4096 characters Winland wrote to its log, the standard error the run script keeps in `winland.err.log`, as the pinned release answers with its rolling log. With `-j` it is the pinned release's form, `[` and a line break, then `"log":` with the text as a JSON string, then `]`. Following the log as it grows is not honored. `debug:disable_logs` false, true by default, also writes the log to `winland.log` beside the state file, emptied at each start, and with `debug:enable_stdout_logs` to standard output too. `debug:disable_time` false, true by default, starts each of their lines with the time, `[HH:MM:SS.mmm]`, which `debug:colored_stdout_logs`, true by default, dims on standard output. Winland's standard error is written whatever these say, since it is where Windows tools and the run script find its errors, and an elevated Winland writes no log file, since a folder the user can change could send a write by name where only administrators may write.

`kill` waits for a click, as in the pinned release: the next press of any mouse button ends the program of the Client under the pointer, emits `kill>>ADDRESS`, and goes to neither window, nor does its release. Escape gives up instead and goes no further. A click on no Client ends nothing. Either way the wait is over. The pointer keeps its shape while it waits.

`notify ICON TIME_MS COLOR [fontsize:SIZE] MESSAGE` shows a notification at the top right of the focused Monitor's work area, as in the pinned release: a black card with the message in white in the `misc:font_family` font, a strip at its left and a progress line along its bottom in the color, sliding in, and sliding out when its time is up. The icons 0 to 5 are the pinned release's text icons `[!]`, `[i]`, `[Hint]`, `[Err]`, `[?]` and `[ok]`, and any other number is none. A color of 0 takes the icon's color. The text size is the font size, default 13, for each 1920 pixels of the Monitor's width, from 8 to 40. Notifications stack downwards, oldest first. `dismissnotify` takes them all away, and `dismissnotify N` the oldest N. Pausing one holds its timeout, so the progress line and the slide out wait, and dismissing one takes that card away. `hl.notification` does this, and changes the text, color, icon, font size and timeout of a card (see [the Lua config](#lua-config)). Bad arguments answer as the pinned release does, such as `invalid arg 2` or `not enough args`. The cards take no clicks.

`seterror COLOR MESSAGE` shows an error bar across the top of the focused Monitor, or its bottom with `debug:error_position` 1 (`bottom`), as in the pinned release. It is a dark strip with a two-pixel border in that color, rounded at its ends, with the message in light text. The text size is 10 pixels for each 1920 pixels of the Monitor's width, from 8 to 40. The message keeps its first `debug:error_limit` lines, 5 by default and 0 to 20, and says how many more there are. The bar's height and its 10-pixel margin are taken off the top, or the bottom, of that Monitor's work area, which `monitors` reports as reserved, and the bar and the space follow the focus to another Monitor. `seterror` alone or `seterror disable` takes it away, and another word alone answers `var 1 not color or disable`. A color that does not parse draws no border. The bar takes no clicks. A config that is read or reloaded with errors shows them in the bar in the pinned release's error color, `0xffff6666`, after `Your config has errors:`, one `line N: message` each, up to 15 lines and then `... more`, unless `debug:suppress_errors` is true. A warning that a keyword or feature is a Gap is not an error in the pinned release, so it is only logged. A config read without errors takes the bar away, one `seterror` showed too, as in the pinned release.

A batch, `[[BATCH]]` or `winlandctl --batch`, splits as in the pinned release: at every `;`, brackets or not, and each command is trimmed. `\;` puts a `;` in a command and `\\` a backslash, and a backslash before anything else stays as it is. So a Windows display name in a batch is written `\\\\.\\DISPLAY1`, and a rule block with more than one rule `[float\; tile]`. The replies are joined by two empty lines, and a command left empty, as after a last `;`, replies as an unknown command does. With `-j`, `winlandctl` puts `j/` before each command the batch splits into.

With no window, `clients` replies `no open windows` and `activewindow` replies `Invalid`, as in the pinned release. With `j/` they reply `[]` and `{}`.

`submap` answers the submap binds run in, or `default` outside one, as in the pinned release. With `j/` the name is a JSON string.

`animations` lists every node of the animation tree, with whether a line set it, its curve, whether it is on, its speed and its style, and then every curve with its two control points, in the pinned release's text and JSON forms. The nodes follow the tree, and the curves come newest first.

`descriptions` answers a JSON array of every option the pinned release has, in that order. Each object has `name`, `description`, `default` and `current`, written as the pinned release writes that type, and an integer also has `min`, `max` and `map`, a float or a css gap also `min` and `max`. The description is the pinned release's, with the window manager's name changed to Winland. `current` is the value Winland uses when it reads the option, and otherwise the value set in the config, or the default. `getoption` answers every one of those options. An option Winland does not read is the pinned release's JSON for its type, and `set` is true when the config set a value it accepts.

## Virtual desktops

Winland's Workspaces are not Windows virtual desktops. A shown Client that a virtual desktop switch cloaks stops being a Client, and it is adopted again when it is uncloaked. A Client Winland has hidden stays a Client on its Workspace while it is cloaked, so it comes back when its Workspace is shown.

## Daemon

One Daemon runs per session. A second `winland` started in the same session prints "Winland is already running in this session." and exits with code 1. A Daemon started with a different `WINLAND_PIPE` counts as a separate instance.

Saving the config or a file it sources reloads it. `misc:disable_autoreload` defaults to false, and true leaves a saved config unread until `winlandctl reload`. Setting it back to false, with `keyword` or that reload, makes saving reload again, as in the pinned release.

On log off and shut down, Winland shows its hidden Clients and puts back what it changed only once Windows says the session is ending, not when it first asks. A shutdown that another program cancels leaves Winland running as it was. Closing Winland's console does the same cleanup on the Daemon's message loop. Windows ends the process five seconds after the console closes. A loop that does not take the cleanup within three seconds has it run on the closing thread instead, and a cleanup the loop has started is waited for until four and a half seconds have passed. Once the cleanup has put a frame, an effect, an alpha or a border back, a command or a key that is still being handled does not change it again before the process ends.

An error that nothing handles still shows every hidden Client and puts back the frames, effects, alpha, taskbar and input settings Winland changed before the process ends. When the error is on another thread than the main one, the state file is kept, so the next start rejoins the Clients to their Workspaces. A process that is killed outright cannot do this, and the next start shows what it left hidden. The state file is written on a thread of its own, with the newest state, at most four times a second, so a process killed within that quarter second can leave a slightly older state. A hidden Client is shown again on that start when its process and window class match, even if its title changed; a shown Client rejoins its Workspace only when its title matches too.

The state file is `%LOCALAPPDATA%\Winland\state.json`, or the file `WINLAND_STATE` names. Winland writes, replaces and deletes it with administrator rights, so an elevated Winland uses only a folder the user could already empty: one the user owns, or may delete and rename entries in. It follows `WINLAND_STATE` only to such a folder, and otherwise logs why and uses the default. A folder only administrators can write is refused, because any program the user runs can set `WINLAND_STATE`, and the file it names would be replaced and then deleted. The folder is checked where it really is, through a junction on the way, and the file and its `.tmp` are never followed when they are links: a link there is deleted itself, and nothing is read through it.
